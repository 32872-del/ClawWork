# 第一篇：先建立正确直觉

## 第 2 章：网页、浏览器和服务器到底在做什么
### 2.0 本章在主流程中的位置

第 1 章把爬虫拆成“确定目标 -> 找到入口 -> 发送请求 -> 接收响应 -> 解析数据”的流水线。本章主要补的是“找到入口”之前的底层直觉：浏览器和服务器到底怎样把一个页面交到你手里。

后面第 3-6 章会开始真正写请求、看响应、解析 HTML 和 JSON。如果这一章没有理解清楚，后面看到 URL、请求头、响应体、接口、静态页面和动态页面时，就容易把它们混在一起。所以本章的产出不是代码，而是一张脑内地图：你要知道数据从服务器到浏览器，中间经历了哪些环节。

### 2.1 为什么这一章必须先讲

很多新手写爬虫遇到的第一个大坑，不是 Python 不熟，也不是 `requests` 不会用，而是对“网页到底是怎么来的”没有建立清晰认识。

最常见的情况是这样的：

你打开浏览器，输入一个网址，页面正常显示，标题、价格、评论、图片都在。然后你兴冲冲写代码：

```python
import requests

response = requests.get("https://example.com/products/1001", timeout=10)
print(response.text)
```

结果打印出来的内容里根本没有你看到的价格，也没有评论，甚至只有一堆看不懂的脚本。于是你开始怀疑：

- 是不是请求头不对？
- 是不是编码不对？
- 是不是被反爬了？
- 是不是 `requests` 有问题？
- 是不是网页加密了？

这些都有可能，但很多时候，真正原因更基础：**浏览器里看到的页面，不等于最开始返回给你的 HTML**。

现代网页经常不是服务器一次性把完整页面发给浏览器，而是先发一个页面骨架，再由浏览器执行 JavaScript，再继续请求接口，把数据一点点填进去。你在浏览器里看到的是“最终渲染结果”，而 `requests` 默认拿到的是“初始响应内容”。两者不是同一个层面的东西。

如果这个问题没想明白，后面你会反复被同一个问题困住：页面明明有，代码就是没有。

所以这一章要做的事，不是教你写很多代码，而是帮你建立网页运行的底层直觉。你以后遇到任何页面，都能先判断：

- 数据是在 HTML 里？
- 数据是在 JSON 接口里？
- 数据是 JavaScript 算出来的？
- 数据是登录后才出现的？
- 数据是滚动、点击后才加载的？

有了这个判断力，你才不会一上来就乱试。

### 2.2 先用一个生活比喻理解网页加载

假设你去一家餐厅吃饭。

你坐下后，服务员先给你一张菜单。菜单上有菜名和图片，但不一定有所有细节。你点菜后，后厨开始做菜。中间服务员可能再给你拿调料、饮料、小票。最后摆在你桌上的，是菜单、菜品、调料、餐具共同组成的一顿饭。

网页加载也类似。

当你访问一个网址时，服务器可能先返回一个 HTML。这个 HTML 像菜单或框架，它告诉浏览器页面大概有哪些区域。然后浏览器会继续下载 CSS、JavaScript、图片、字体。JavaScript 运行后，可能再向接口请求商品价格、评论列表、库存状态。最后你看到的完整页面，是很多东西组合出来的结果。

所以，网页不是“一次拿完”的概念，而更像“分批组装”。

这个比喻很重要。因为爬虫要做的，不一定是拿最终画面，而是找到数据真正来自哪里。

### 2.3 浏览器访问一个网页时发生了什么

当你在浏览器地址栏输入一个网址，比如：

```text
https://example.com/products/1001
```

背后大致会发生这些事情。

#### 第一步：浏览器解析 URL

URL 不是一整块无意义文本，它包含多个部分：

```text
https://example.com/products/1001?color=black&page=1
```

可以拆成：

- `https`：协议。
- `example.com`：域名。
- `/products/1001`：路径。
- `color=black&page=1`：查询参数。

浏览器首先要知道：我要用什么协议，去哪个服务器，请求哪个路径，带哪些参数。

#### 第二步：找到服务器

人记域名，机器认 IP。浏览器会通过 DNS 把 `example.com` 解析成服务器 IP。你可以把 DNS 理解成通讯录：你知道名字，DNS 帮你查电话号码。

这一步通常很快，但如果 DNS 出问题，你会看到“无法解析域名”之类的错误。

#### 第三步：建立连接

浏览器找到服务器后，要建立网络连接。如果是 HTTPS，还会进行 TLS 握手，用来建立加密通信。

你现在不需要深入 TLS 的每个细节，只要知道：HTTPS 不是简单的 HTTP 加个字母，它多了一层安全通信过程。

#### 第四步：发送 HTTP 请求

连接建立后，浏览器发送请求。请求里不仅有 URL，还包括请求方法、请求头、Cookie、参数等信息。

比如浏览器可能会告诉服务器：

- 我是 Chrome。
- 我能接受 HTML。
- 我的语言偏好是中文。
- 我从哪个页面跳过来。
- 我带着哪些 Cookie。

这就是为什么同一个 URL，不同客户端访问时，返回结果可能不同。

#### 第五步：服务器返回响应

服务器返回响应，里面通常包括：

- 状态码。
- 响应头。
- 响应体。

响应体可能是 HTML，也可能是 JSON、图片、文件、错误页、跳转页。

#### 第六步：浏览器解析 HTML

如果返回的是 HTML，浏览器开始解析标签，构建 DOM 树。DOM 可以理解成浏览器内部对网页结构的理解。

比如 HTML 里有：

```html
<h1>商品标题</h1>
<div class="price">￥199</div>
```

浏览器会把它们组织成树状结构，后续 JavaScript 可以操作这棵树。

#### 第七步：继续加载资源

HTML 里通常会引用其他资源：

```html
<link rel="stylesheet" href="/static/main.css">
<script src="/static/app.js"></script>
<img src="/images/product.png">
```

浏览器看到这些标签后，会继续请求 CSS、JS、图片等文件。

#### 第八步：执行 JavaScript

JavaScript 可以修改页面，也可以继续发请求。

比如页面初始 HTML 里可能只有：

```html
<div id="app"></div>
<script src="/static/app.js"></script>
```

真正的商品信息，是 `app.js` 运行后调用接口拿到的。

#### 第九步：接口返回数据，页面继续渲染

JavaScript 可能请求：

```text
https://example.com/api/products/1001
```

接口返回：

```json
{
  "id": "1001",
  "title": "机械键盘 A",
  "price": 199.0,
  "stock": 35
}
```

然后 JavaScript 把这些数据插入页面。最终你看到完整商品信息。

这就是为什么浏览器能看到，而简单 `requests.get(页面 URL)` 可能看不到。

### 2.4 HTML、CSS、JavaScript、DOM、JSON 分别是什么

这些词你会反复遇到。先不要背复杂定义，我们用最直白的方式讲。

#### HTML：网页的骨架

HTML 负责描述结构。

比如：

```html
<h1>机械键盘 A</h1>
<p>这是一款适合办公和游戏的键盘。</p>
```

它告诉浏览器：这里是标题，这里是一段文字。

HTML 像房子的骨架，决定哪里是客厅、哪里是卧室、哪里是门窗。

#### CSS：网页的装修

CSS 负责样式。

比如：

```css
.price {
  color: red;
  font-size: 20px;
}
```

它告诉浏览器：价格显示成红色，字号大一点。

CSS 像装修，决定墙刷什么颜色、灯装在哪里、家具怎么摆。

#### JavaScript：网页的动作和逻辑

JavaScript 负责交互和动态逻辑。

比如：

- 点击按钮后弹窗。
- 滚动到底部加载更多。
- 输入关键词后搜索。
- 请求接口获取价格。
- 根据登录状态显示不同内容。

JavaScript 像房子里的电器和控制系统。它让页面“动起来”。

#### DOM：浏览器眼里的网页结构

DOM 是浏览器解析 HTML 后形成的树状结构。

你可以把 HTML 理解成“图纸文本”，DOM 理解成“浏览器按照图纸搭起来的模型”。JavaScript 操作的通常不是原始 HTML 字符串，而是 DOM。

这就是为什么页面最终内容可能和原始 HTML 不一样：JavaScript 可以修改 DOM。

#### JSON：程序更喜欢的数据格式

JSON 是结构化数据格式。

比如：

```json
{
  "title": "机械键盘 A",
  "price": 199.0,
  "stock": 35
}
```

它不像 HTML 那样关心展示效果，而是直接描述数据。爬虫通常很喜欢 JSON，因为它比 HTML 更容易解析，字段也更清楚。

### 2.5 页面源码和最终页面为什么不同

很多新手会右键查看网页源码，然后发现里面没有浏览器里看到的数据。

这是正常的。

网页源码通常是服务器最开始返回的 HTML。浏览器最终显示的页面，则可能经过 JavaScript 多次修改。

我们用一个极简例子说明。

#### 初始 HTML

```html
<html>
  <body>
    <div id="app">加载中...</div>
    <script>
      document.getElementById("app").innerText = "机械键盘 A - ￥199";
    </script>
  </body>
</html>
```

如果你只看初始 HTML，会看到：

```text
加载中...
```

但浏览器执行 JavaScript 后，页面上显示的是：

```text
机械键盘 A - ￥199
```

这就说明：页面展示内容可能是运行后生成的。

再进一步，JavaScript 还可能不是直接写死数据，而是请求接口。

#### 初始 HTML

```html
<html>
  <body>
    <div id="app">加载中...</div>
    <script src="/static/product.js"></script>
  </body>
</html>
```

#### product.js 做的事

```javascript
fetch("/api/products/1001")
  .then(response => response.json())
  .then(data => {
    document.getElementById("app").innerText = data.title + " - ￥" + data.price;
  });
```

#### 接口返回

```json
{
  "title": "机械键盘 A",
  "price": 199
}
```

这种页面里，真正的数据在 `/api/products/1001`，而不是初始 HTML。

### 2.6 `requests` 拿到的是什么

`requests` 默认只做 HTTP 请求。它不会像浏览器一样解析 CSS，也不会执行 JavaScript，更不会自动把接口数据填进 DOM。

所以当你写：

```python
import requests

response = requests.get("https://example.com/products/1001", timeout=10)
print(response.text)
```

你拿到的是服务器对这个 URL 的原始响应。通常是初始 HTML。

这不是 `requests` 弱，而是它职责不同。

`requests` 像一个快递员，负责把包裹拿回来。  
浏览器像一个装修队，拿到材料后还会组装、执行脚本、加载资源、把页面渲染出来。

如果你的目标数据就在原始 HTML 里，`requests` 非常合适。  
如果目标数据是 JavaScript 后加载的，你就要去找接口，或者使用浏览器自动化。

### 2.7 如何判断数据在哪里

这是爬虫入门最重要的判断题之一。

你可以按下面顺序排查。

#### 第一步：查看页面源码

在浏览器中右键“查看网页源代码”，然后搜索目标字段。

比如页面上有“机械键盘 A”，你就在源码里搜索这个词。

如果能搜到，说明数据很可能在初始 HTML 里。用 `requests` 抓页面，再用 HTML 解析器提取，通常就够了。

如果搜不到，不要急。继续下一步。

#### 第二步：打开开发者工具，看 Elements

Elements 面板显示的是当前 DOM，也就是浏览器运行后的结构。

如果 Elements 里有数据，但源代码里没有，说明数据很可能是后续由 JavaScript 填进去的。

这时你要去 Network 面板找接口。

#### 第三步：看 Network 里的 XHR / Fetch

打开 Network 面板，刷新页面，筛选 XHR 或 Fetch。然后搜索目标字段。

如果某个接口响应里包含你要的数据，那它就是更合适的数据入口。

这一步非常关键。很多新手一看到动态页面就想上浏览器自动化，其实很多时候直接请求接口就可以了。

#### 第四步：观察页面交互

如果数据是点击、滚动、切换 tab 后才出现的，就在做这些操作时观察 Network。很多接口只有在用户动作触发时才会出现。

比如：

- 滚动到底部后出现下一页接口。
- 点击“评论”后出现评论接口。
- 切换规格后出现库存接口。
- 输入关键词后出现搜索接口。

#### 第五步：判断是否需要浏览器自动化

如果数据必须依赖浏览器环境、复杂交互、渲染后 DOM，或者接口很难单独复现，才考虑 Playwright、Selenium 这类工具。

记住这个顺序：

```text
HTML 能拿到 -> 用 requests + HTML 解析
接口能拿到 -> 用 requests/httpx 请求接口
必须浏览器执行 -> 用 Playwright/Selenium
```

这个顺序很实用，因为它是从低成本到高成本排列的。

### 2.8 HTTP 请求到底长什么样

HTTP 请求不是只有 URL。我们可以把它拆开看。

一次请求大概包含：

```text
GET /products/1001?page=1 HTTP/1.1
Host: example.com
User-Agent: Mozilla/5.0
Accept: text/html
Cookie: sessionid=abc123
```

这里面有几个关键部分。

#### 请求方法

比如：

- GET：获取数据。
- POST：提交数据。
- PUT：更新数据。
- DELETE：删除数据。

爬虫里最常见的是 GET 和 POST。

#### 请求路径和参数

```text
/products/1001?page=1
```

路径表示你要哪个资源，参数表示额外条件。

#### 请求头

请求头是附加说明。

比如：

- `User-Agent`：客户端信息。
- `Accept`：希望接收的内容类型。
- `Cookie`：会话信息。
- `Referer`：来源页面。
- `Accept-Language`：语言偏好。

这些信息会影响服务器返回什么。

### 2.9 HTTP 响应到底长什么样

响应也可以拆开看。

```text
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Set-Cookie: sessionid=abc123

<html>
  <body>...</body>
</html>
```

它包括：

- 状态码。
- 响应头。
- 响应体。

#### 状态码

状态码告诉你这次请求大体结果。

常见状态码：

```text
200  成功
301  永久重定向
302  临时重定向
400  请求参数错误
401  未认证
403  被拒绝
404  不存在
429  请求过多
500  服务端错误
502  网关错误
503  服务不可用
504  网关超时
```

不要只看响应内容。状态码是第一层判断。

#### 响应头

响应头告诉你返回内容的元信息。

比如：

- `Content-Type`：返回内容类型。
- `Set-Cookie`：服务器设置 Cookie。
- `Location`：跳转地址。
- `Cache-Control`：缓存策略。

#### 响应体

响应体才是真正内容。可能是 HTML、JSON、图片、文件、错误信息。

### 2.10 一个离线例子：同一个商品，两种数据来源

为了避免受真实网站影响，我们用两个字符串模拟页面和接口。

#### 2.10.1 HTML 页面

```python
html = """
<html>
  <body>
    <h1>商品详情</h1>
    <div id="app">加载中...</div>
    <script src="/static/product.js"></script>
  </body>
</html>
"""
```

这个 HTML 里没有价格，也没有库存。它只是一个壳。

#### 2.10.2 JSON 接口

```python
api_json = {
    "id": "1001",
    "title": "机械键盘 A",
    "price": 199.0,
    "stock": 35
}
```

真正数据在接口里。

#### 2.10.3 新手错误做法

新手可能会在 HTML 里找价格：

```python
from bs4 import BeautifulSoup

html = """
<html>
  <body>
    <h1>商品详情</h1>
    <div id="app">加载中...</div>
    <script src="/static/product.js"></script>
  </body>
</html>
"""

soup = BeautifulSoup(html, "html.parser")
price = soup.select_one(".price")
print(price)
```

输出是：

```text
None
```

这不是选择器错了，而是 HTML 里根本没有 `.price`。

#### 2.10.4 正确思路

正确思路是：先判断数据不在 HTML，再找接口。

如果接口返回 JSON：

```python
api_json = {
    "id": "1001",
    "title": "机械键盘 A",
    "price": 199.0,
    "stock": 35
}

print(api_json["title"])
print(api_json["price"])
print(api_json["stock"])
```

这样就能直接拿到数据。

这个例子虽然简单，但它说明了一个非常核心的原则：

> 不要在错误的数据层里找字段。

数据在 HTML，就解析 HTML。  
数据在 JSON，就请求 JSON。  
数据在 DOM，就考虑浏览器渲染结果。  
数据在文件，就按文件格式处理。

### 2.11 开发者工具怎么用来判断数据入口

浏览器开发者工具是爬虫开发的基本工具。不同浏览器界面略有差异，但核心面板类似。

#### Elements 面板

Elements 看到的是当前 DOM。它适合观察页面最终结构。

你可以用它找到：

- 某个字段在页面哪个位置。
- 标签 class 是什么。
- 页面结构怎么嵌套。

但要注意：Elements 里看到的内容不一定在原始 HTML 里。

#### Network 面板

Network 是爬虫分析最重要的面板之一。

它能看到页面加载过程中发出的所有请求：

- HTML 请求。
- CSS 请求。
- JS 请求。
- 图片请求。
- XHR / Fetch 接口请求。
- 字体文件。
- 其他资源。

你可以在这里观察：

- 哪个接口返回目标数据。
- 请求方法是 GET 还是 POST。
- 参数是什么。
- 请求头带了什么。
- 响应是 JSON 还是 HTML。

#### Console 面板

Console 可以执行 JavaScript，也能看页面报错。新手阶段用得少一点，但分析动态页面时会很有用。

#### Application 面板

Application 可以看 Cookie、localStorage、sessionStorage、IndexedDB 等浏览器存储。涉及登录态、token、前端缓存时，这里很重要。

### 2.12 判断采集方案的三层模型

你以后拿到一个页面，可以先按三层模型判断。

#### 第一层：静态 HTML

如果数据在 HTML 源码里，方案最简单：

```text
requests -> HTML 解析 -> 保存
```

这是成本最低、速度最快、最稳定的一类。

#### 第二层：接口 JSON

如果数据来自接口：

```text
分析 Network -> 请求接口 -> JSON 解析 -> 保存
```

这是企业项目里非常常见的方式。只要接口参数不复杂，它通常比解析 HTML 更舒服。

#### 第三层：浏览器渲染

如果必须执行 JavaScript，或者数据必须通过复杂交互出现：

```text
Playwright/Selenium -> 操作页面 -> 读取 DOM 或监听接口 -> 保存
```

这类方案更重，资源消耗更高，维护成本也更高。不要一开始就用它，但该用的时候也别硬扛。

### 2.13 为什么不能盲目复制浏览器请求

很多新手在 Network 里看到接口后，会右键复制为 cURL，然后把所有请求头都搬进代码里。

这种方法有时能救急，但不应该成为长期习惯。

原因是：

1. 有些请求头是浏览器自动维护的。
2. 有些字段和当前环境绑定，过一会儿就失效。
3. 有些 Cookie 或 token 有时效性。
4. 复制太多字段会让代码变得难维护。
5. 你不知道哪个字段是真正必要的。

更好的方式是：

- 先复制最少必要信息。
- 保留 URL、方法、参数、必要 Cookie。
- 逐步验证哪些字段不能少。
- 把动态字段找出来，单独处理。

这样你才是在理解请求，而不是机械复制。

### 2.14 常见排查场景

#### 场景一：浏览器能看到，requests 没有

排查顺序：

1. 查看网页源码是否有目标字段。
2. 如果没有，查 Network 的 XHR / Fetch。
3. 搜索接口响应是否有目标字段。
4. 如果接口有，优先请求接口。
5. 如果接口没有，考虑是否由 JS 计算或浏览器渲染生成。

#### 场景二：requests 返回登录页

表现可能是状态码 200，但内容是登录页面。

这说明请求成功了，但身份不对。你需要检查：

- 是否需要 Cookie。
- 登录态是否过期。
- 是否发生了 302 跳转。
- 响应 URL 是否已经变成登录页。

#### 场景三：接口返回空数据

可能原因：

- 参数缺失。
- 分页参数不对。
- 需要登录。
- 需要特定 Referer。
- 请求方法错了。
- 接口有时间戳或 token。

不要一看到空就以为没有数据。先对照浏览器里的真实请求。

#### 场景四：返回内容是乱码

可能是编码识别问题。后面章节会详细讲编码。现在先知道：乱码不一定是没抓到，而可能是解释文本的规则错了。

#### 场景五：返回 403

403 表示服务器拒绝了这次访问。可能原因很多，包括权限、登录态、请求头、频率、来源限制等。不要直接把它等同于“被反爬”，先从基础请求差异排查。

### 2.15 这一章和后面章节的关系

这一章讲的是判断力。

后面第 3 章会讲怎么用 `requests` 发第一个请求。  
第 4 章会讲请求头、参数和编码。  
第 5 章会讲 HTML 解析。  
第 6 章会讲 JSON 接口采集。  
第 7 章会讲分页、详情页和任务拆分。

你会发现，这些章节其实都是围绕本章的问题展开：

> 数据到底在哪一层？我应该用什么方式拿？

只要这个问题判断对了，后面技术选择就清楚很多。

### 2.16 本章重点回顾

这一章要记住的内容很多，但最核心的是下面几条：

1. 浏览器最终看到的页面，不一定等于服务器最初返回的 HTML。
2. 现代页面常常是 HTML、CSS、JavaScript、接口数据共同组成的结果。
3. `requests` 默认不会执行 JavaScript，它只拿原始响应。
4. 数据可能在 HTML、JSON 接口、DOM、文件、浏览器存储等不同位置。
5. 分析页面时，先判断数据来源，再决定技术方案。
6. 能直接用 HTML 或接口拿数据，就不要一上来使用浏览器自动化。

### 2.17 课后练习

请找一个你常访问的网页，做下面的观察练习。不需要写复杂代码，只要训练判断力。

1. 打开页面，找一个你想采集的字段，比如标题、价格、发布时间。
2. 右键查看网页源代码，搜索这个字段。
3. 如果源码里没有，打开开发者工具的 Elements 面板，看 DOM 里有没有。
4. 打开 Network 面板，刷新页面，筛选 XHR / Fetch。
5. 在接口响应里搜索目标字段。
6. 判断这个数据更可能来自 HTML、接口还是 JavaScript 渲染。
7. 写下你会选择的采集方案：`requests + HTML`、`requests + JSON`，还是 `Playwright`。

这个练习做三到五个网页，你就会明显感觉自己看页面的方式变了。你不再只是看页面长什么样，而是在看它背后的数据流。
