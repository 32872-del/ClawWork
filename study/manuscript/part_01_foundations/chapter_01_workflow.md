# 第一篇：先建立正确直觉

## 第 1 章：爬虫开发的真实工作流

### 1.1 先说清楚：这本书里的“爬虫”到底指什么

很多人第一次听到“爬虫”这个词，会很自然地想到一句话：写程序去网页上抓数据。

这个理解没有错，但它太粗了。粗到什么程度呢？就像说“做饭就是把食物弄熟”。这句话当然没错，但如果你真的要做一桌菜，只知道“弄熟”是不够的。你还要知道买什么菜、怎么洗、怎么切、火候怎么控制、什么时候放调料、怎么装盘、做多了怎么保存、客人反馈不好怎么调整。

爬虫也是这样。

如果只是学习阶段，你写几行代码，访问一个网页，打印出 HTML，这当然可以叫爬虫。但在真实开发里，尤其是企业级项目里，爬虫通常指的是一套完整的数据采集系统。它不只是“拿一次网页”，而是要长期、稳定、可维护地把目标数据变成可使用的数据资产。

这一点非常重要。

因为很多新手会把学习重点放在“怎么请求成功”上，却忽略了后面更重要的问题：

- 请求成功后，怎么确认数据是对的？
- 今天能抓，明天页面改了怎么办？
- 抓到一半程序崩了，下次从哪里继续？
- 数据重复了怎么办？
- 字段缺失了怎么办？
- 抓取速度太快导致失败怎么办？
- 多个任务同时跑，怎么调度？
- 出错了怎么知道错在哪里？

这些问题才是真实项目里每天会遇到的东西。

所以，这本书里说的爬虫，不只是一个脚本，而是一条从“数据源”到“可交付数据”的流水线。

### 1.2 一个新手最容易误解的地方

新手常常会把“能抓到一次”当成“爬虫写好了”。

比如你写了下面这样的代码：

```python
import requests

response = requests.get("https://example.com", timeout=10)
print(response.text)
```

它运行成功了，终端里打印出一大段 HTML。你会很开心，觉得自己已经会爬虫了。

这种开心是对的，因为你确实完成了第一步。但你要马上意识到：这只是第一步。

它只能证明几件事：

- 你的 Python 环境能运行。
- 你的网络能访问这个地址。
- 这个地址返回了内容。
- `requests` 这个库能正常工作。

它还不能证明：

- 你拿到的是目标数据。
- 数据字段是完整的。
- 这个代码明天还能用。
- 多页数据都能抓。
- 出错时程序能恢复。
- 数据能被后续系统使用。

所以，“跑通一次”是入门，不是完成。

这就像你第一次开车，把车从停车位开出来了。值得高兴，但这不代表你已经能跑长途、能上高速、能处理雨天、能倒车入库、能应对复杂路况。

### 1.3 把爬虫看成流水线

为了让你从一开始就建立正确直觉，我们把爬虫拆成一条流水线。

```text
确定目标
  ↓
找到入口
  ↓
发送请求
  ↓
接收响应
  ↓
解析数据
  ↓
清洗数据
  ↓
去重校验
  ↓
保存数据
  ↓
调度任务
  ↓
监控维护
```

你现在可能还不能完全理解每一步，但没关系。我们先建立一个大图。后面的章节会逐步把每一步拆开讲。

### 1.3.1 这一条流程怎么贯穿全书

这本书后面的章节不是随便排的，而是沿着这条流程一步一步展开。

| 流程环节 | 主要章节 | 你会学到什么 |
| --- | --- | --- |
| 确定目标、定义字段 | 第 1 章 | 先把问题说清楚，知道采什么、为什么采、采到什么算完成 |
| 找到入口、发起请求 | 第 2-6 章 | 知道数据是在 HTML、接口还是浏览器里，学会把请求真正发出去 |
| 分页、登录、重试、存储、清洗、断点 | 第 7-13 章 | 把脚本做成能长期运行的小工具 |
| 并发、异步、Scrapy | 第 14-17 章 | 解决单机太慢的问题，但仍然保持秩序 |
| 动态页面、浏览器自动化 | 第 18-20 章 | 处理页面渲染、交互和等待 |
| JS 分析与 AST | 第 21-24 章 | 找到参数生成逻辑，理解脚本结构 |
| 浏览器指纹 | 第 25-26 章 | 理解环境差异为什么会影响访问结果 |
| 验证码、行为风控、Cloudflare | 第 27-29 章 | 理解风控信号和处置方式 |
| 代理、限速、礼貌采集 | 第 30-31 章 | 控制访问压力和出口治理 |
| Redis 队列与分布式 | 第 32-34 章 | 把任务拆成可分发、可追踪、可恢复的单元 |
| 平台化 | 第 35-37 章 | 管任务、管日志、管配置、管权限 |
| 测试与维护 | 第 38-40 章 | 让系统能长期改、长期跑、长期交接 |

你可以把后面的每一章都看成这条流水线上的一个节点。学到某个节点时，先想它接的是哪一步，输出给谁，下一步会不会直接用到。这样整本书就不会变成零散知识点，而会像一个完整系统。

### 1.4 第一步：确定目标

写爬虫之前，第一件事不是打开编辑器，而是问清楚：我到底要什么数据？

这听起来很普通，但实际项目里非常关键。

比如你说“我要采集商品数据”，这句话还不够清楚。商品数据可能包括：

- 商品标题
- 商品价格
- 商品 ID
- 品牌
- 规格参数
- 库存
- 评论数量
- 评分
- 图片地址
- 类目
- 店铺名称
- 上架时间

如果你不先确定字段，后面就会反复返工。写到一半发现还要评论，抓完发现缺库存，入库后发现没有唯一 ID，这些都是目标没定义清楚带来的问题。

更好的方式是先写一个字段表：

```text
字段名        含义          是否必填      示例
product_id    商品 ID       是            1001
title         商品标题      是            机械键盘 A
price         价格          是            199.00
brand         品牌          否            KeyPro
stock         库存          否            35
detail_url    详情页链接    是            https://example.com/products/1001
```

这张表看起来简单，但它会让你的开发目标非常明确。

很多人写爬虫写到后面混乱，不是技术不行，而是一开始没有定义清楚“什么叫采集完成”。

### 1.5 第二步：找到入口

确定字段之后，要找数据从哪里来。

入口可能有很多种：

- 静态 HTML 页面
- JSON 接口
- 搜索结果页
- 列表页
- 详情页
- 文件下载地址
- WebSocket 推送
- App 接口

新手通常会先盯着浏览器里看到的页面。但真实开发里，页面只是表现层，数据可能来自别的地方。

比如一个商品页面，浏览器里看起来是一个完整网页。但里面的价格、库存、评论可能是页面加载后通过接口请求回来的。你如果只抓最开始的 HTML，可能根本看不到这些字段。

所以找入口不是“复制地址栏 URL”这么简单，而是要判断：

- 数据在页面源码里吗？
- 数据在接口里吗？
- 数据是滚动后加载的吗？
- 数据需要登录后才能看到吗？
- 数据是否分散在多个接口里？

后面我们会专门讲浏览器开发者工具和 Network 面板。现在你先记住一句话：

> 找入口，就是找数据真正出现的位置，而不是只看用户眼前的页面。

### 1.6 第三步：发送请求

找到入口以后，爬虫要模拟客户端向服务器请求数据。

请求不是只有 URL。一次 HTTP 请求通常还包括：

- 请求方法，比如 GET、POST。
- 请求头，比如 User-Agent、Cookie、Accept。
- 请求参数，比如 page、keyword、size。
- 请求体，比如表单数据或 JSON 数据。
- 超时时间。
- 代理设置。
- 重试策略。

新手容易把请求想得太简单，以为只要有 URL 就够了。但真实项目里，同一个 URL，带不同参数、不同 Cookie、不同请求头，返回结果都可能不同。

举个例子。

你去一家办事大厅办业务，只说“我要办业务”是不够的。你还要说明：

- 你是谁。
- 你要办哪类业务。
- 你有没有预约。
- 你带没带证件。
- 你是不是在正确窗口。

HTTP 请求也是这样。URL 是地址，但请求头、参数和 Cookie 才是完整上下文。

### 1.7 第四步：接收响应

服务器收到请求后，会返回响应。

响应通常包含三层信息：

1. 状态码。
2. 响应头。
3. 响应体。

状态码告诉你这次请求大体结果：

- 200 表示成功。
- 301/302 表示跳转。
- 401 表示认证失败。
- 403 表示拒绝访问。
- 404 表示资源不存在。
- 429 表示请求太频繁。
- 500 表示服务器错误。

响应头告诉你返回内容的元信息，比如：

- 返回的是 HTML 还是 JSON。
- 有没有设置 Cookie。
- 有没有跳转地址。
- 是否启用了缓存。

响应体才是真正内容，比如 HTML、JSON、图片、文件等。

为什么要强调这个？因为很多新手只看响应体，不看状态码和响应头。结果程序拿到一个登录页，还以为是目标页面；拿到一个错误页，还以为解析规则错了。

成熟的排查顺序应该是：

1. 先看状态码。
2. 再看响应头。
3. 最后看响应体。

不要倒过来。

### 1.8 第五步：解析数据

拿到响应后，你要把目标字段提取出来。

不同响应格式有不同解析方式：

- HTML 用 BeautifulSoup、lxml、XPath、CSS Selector。
- JSON 用 `response.json()` 转成字典或列表。
- CSV 用 csv 模块。
- PDF、Word、Excel 等文件要用专门库。
- 浏览器渲染后的内容可能要用 Playwright。

解析看起来像技术细节，但它其实是爬虫里非常重要的稳定性来源。

如果你选择器写得太脆，页面稍微改一层结构就坏。  
如果你字段判断不严，拿到空值也不知道。  
如果你没有保留原始样本，出问题后很难复盘。

解析不是“取出来就行”，而是要考虑：

- 字段不存在怎么办。
- 字段格式变化怎么办。
- 页面结构变化怎么办。
- 多个同名字段怎么区分。
- 解析结果怎么验证。

### 1.9 第六步：清洗数据

原始数据往往不能直接用。

比如价格字段：

```text
￥199.00
199元
  199.00 
暂无报价
```

如果你直接保存，这些值后续很难计算。更合理的做法是把它们统一成数字：

```text
199.00
199.00
199.00
None
```

再比如时间字段：

```text
2026-06-01
2026/6/1 10:30
刚刚
3分钟前
```

这些也需要统一。

清洗的目的不是让数据看着漂亮，而是让它能被后续程序稳定使用。

你可以把清洗理解成做菜前的处理。菜市场买回来的菜可以吃吗？理论上可以。但你通常要先洗、切、去皮、去坏叶。数据也一样。

### 1.10 第七步：去重和校验

爬虫很容易产生重复数据。

原因包括：

- 同一个详情页出现在多个列表页。
- 分页数据更新导致重复。
- 程序失败后重跑。
- 同一个接口返回重复项。
- 不同入口指向同一条数据。

如果不去重，数据库会慢慢变脏。

去重的关键是找到唯一标识。常见唯一标识包括：

- 商品 ID
- 文章 URL
- 评论 ID
- 用户 ID
- 文件哈希
- 来源站点 + 原始 ID

不要随便用标题去重。标题可能重复，也可能变化。唯一键应该尽量稳定。

校验则是确认数据是否符合预期。比如：

- 必填字段不能为空。
- 价格必须是数字。
- URL 必须是合法链接。
- 时间不能是明显错误值。

去重和校验是数据质量的基础。

### 1.11 第八步：保存数据

保存数据也有很多选择。

练习阶段可以用 CSV：

```text
id,title,price
1001,机械键盘 A,199.00
```

如果字段比较灵活，可以用 JSONL：

```json
{"id": "1001", "title": "机械键盘 A", "price": 199.0}
{"id": "1002", "title": "无线鼠标 B", "price": 89.0}
```

如果要查询、更新、去重，可以用数据库：

- SQLite 适合本地小项目。
- MySQL / PostgreSQL 适合长期项目。
- MongoDB 适合文档型数据。
- Elasticsearch / OpenSearch 适合搜索和分析。

存储不是最后才考虑的事情。字段设计、唯一键设计、数据类型设计，都会影响前面的解析和清洗。

### 1.12 第九步：调度任务

当数据量小的时候，你可以写一个 `for` 循环。

当数据量变大时，你就需要调度。

调度要解决的问题包括：

- 哪些 URL 等待抓取。
- 哪些 URL 已经抓过。
- 哪些 URL 抓失败了。
- 失败任务要不要重试。
- 任务是否有优先级。
- 同时跑多少个任务。
- 程序重启后怎么恢复。

一开始你可以用列表、文件或数据库保存任务。后面可以用 Redis 队列、消息队列、Scrapy 调度器、Celery 等工具。

调度本质上是“管理工作顺序”。没有调度，爬虫只能像一个人拿着纸条干活；有了调度，它才像一个小团队，有任务池、有状态、有失败回收。

### 1.13 第十步：监控和维护

爬虫上线后，真正的工作才刚开始。

因为目标站点会变化。你必须知道系统什么时候坏了。

监控通常要看：

- 请求成功率。
- 解析成功率。
- 入库成功率。
- 平均响应时间。
- 错误码分布。
- 每天采集数量。
- 字段缺失率。
- 重复数据比例。

如果今天本来应该采 10 万条，结果只采了 500 条，程序没有崩也不代表正常。没有监控，你可能过好几天才发现数据断了。

所以企业项目里，监控不是锦上添花，而是基本能力。

### 1.14 一个完整的小案例：采集公开商品目录

假设我们要采集一个公开商品目录，目标字段是：

- 商品 ID
- 标题
- 价格
- 品牌
- 详情页链接

正确的思考流程应该是这样。

**第一步，确认字段。**

先写字段表，确认哪些必填，哪些可选。

**第二步，找入口。**

打开列表页，观察商品是否直接在 HTML 里。如果不在，打开 Network 看接口。

**第三步，验证单页。**

只抓第一页，确认能拿到商品卡片和详情链接。

**第四步，解析详情页。**

进入一个详情页，确认品牌和商品 ID 在哪里。

**第五步，设计任务流。**

列表页产生详情任务，详情页产生最终数据。

**第六步，保存结果。**

先保存 JSONL，方便调试。稳定后再入库。

**第七步，加日志和重试。**

记录每页抓了多少条、哪些详情失败。

**第八步，做去重。**

使用商品 ID 或详情 URL 去重。

**第九步，做断点续爬。**

保存当前页码或已完成 URL。

这个案例还没有写具体代码，但它已经是一个真实项目的骨架。后面的章节会把每一步都写成代码。

### 1.15 新手最常见的错误

#### 错误一：一上来就追求高级技术

很多人刚开始就想学 JS 逆向、指纹、验证码、Cloudflare。不是不能学，而是顺序错了。

如果你连请求、解析、分页、存储、重试都不熟，直接看高级内容，很容易变成“知道很多名词，但做不出稳定项目”。

高级技术应该建立在基本功上。

#### 错误二：只看页面，不看接口

浏览器展示的是结果，不一定是数据源。很多数据来自接口。只看页面源码，可能会走很多弯路。

#### 错误三：不保存中间结果

新手喜欢一边抓一边解析一边保存，所有东西都在内存里。程序一崩，什么都没了。

更稳妥的做法是保留关键中间结果，比如详情任务、原始响应样本、失败 URL。

#### 错误四：没有日志

没有日志的爬虫，一出错就只能猜。日志不是为了好看，而是为了让你知道程序做过什么。

#### 错误五：没有数据质量意识

抓到很多数据不等于抓得好。重复、缺字段、格式混乱的数据，后面一样没法用。

### 1.16 真实项目开始前，要先问清楚哪些问题

很多新手写爬虫时，习惯直接打开网页、打开编辑器、开始写代码。这样做在练习时没问题，但在真实项目里很危险。

因为你还不知道这个任务到底要交付什么。

一个企业里的采集需求，通常不是一句“帮我抓一下这个网站”就能开始。你至少要问清楚下面这些问题。

#### 1.16.1 要采什么字段

这是最基础的问题。

不能只说“采商品数据”，要具体到字段：

```text
商品 ID
商品标题
价格
品牌
库存
评分
评论数
详情页 URL
采集时间
来源站点
```

字段越清楚，后续开发越稳。字段不清楚，后面一定返工。

#### 1.16.2 每个字段从哪里来

字段可能来自不同位置。

比如：

```text
商品标题：列表页和详情页都有，但详情页更完整
价格：接口返回
库存：切换规格后接口返回
评论数：评论接口返回
品牌：详情页 HTML 中
```

这一步特别重要。因为它决定你要抓几个页面、几个接口、是否需要浏览器自动化。

如果所有字段都在列表页，那项目很简单。  
如果字段分散在列表页、详情页、评论接口、库存接口，那项目复杂度立刻上升。

#### 1.16.3 采集频率是多少

采一次和每天采完全不一样。

常见频率包括：

- 一次性采集。
- 每天采一次。
- 每小时采一次。
- 近实时采集。
- 发现新数据后增量采集。

频率决定系统设计。

如果只是一次性采集，你可以接受手工启动、手工检查。  
如果是每天采集，你需要定时任务、日志、失败重跑。  
如果是近实时采集，你可能需要队列、监控、增量游标。

#### 1.16.4 数据量大概多少

采 100 条、10 万条、1 亿条，完全不是同一个项目。

你需要问：

- 总量大概多少？
- 每天新增多少？
- 每页多少条？
- 是否有历史数据回溯？
- 是否需要全量补采？

数据量决定存储、并发、调度、去重和成本。

小数据可以保存 CSV。  
中等数据可以用 SQLite 或 PostgreSQL。  
大数据可能要考虑分布式任务、消息队列、对象存储和数据仓库。

#### 1.16.5 结果给谁用

这是很多技术同学容易忽略的问题。

同一批数据，给不同人用，交付方式可能不同。

如果给运营看，可能需要 Excel 或可视化页面。  
如果给算法用，可能需要 JSONL、Parquet 或数据库表。  
如果给业务系统用，可能需要 API 或定时同步。  
如果给风控团队用，可能需要保留原始响应和采集证据。

所以，存储格式不是你想怎么存就怎么存，而要看下游怎么用。

#### 1.16.6 允许的失败范围是多少

真实系统不可能永远 100% 成功。关键是业务能接受什么。

你要问：

- 允许漏多少？
- 允许延迟多久？
- 失败后多久必须恢复？
- 哪些字段缺失可以接受？
- 哪些字段缺失必须报警？

比如价格字段缺失，可能是严重问题。  
商品图片缺失，可能只是中等问题。  
某些可选标签缺失，可能可以接受。

这些标准不提前定清楚，后面就会出现争议：开发觉得任务完成了，业务觉得数据不能用。

### 1.17 什么叫“采集完成”

很多项目混乱，是因为一开始没有定义完成标准。

新手常常以为“代码跑完了”就是完成。但真实项目里，“跑完”不等于“交付”。

一个更合理的完成标准应该包括：

```text
1. 目标字段已经采集完整。
2. 必填字段缺失率在可接受范围内。
3. 重复数据比例可控。
4. 失败任务有记录。
5. 原始样本或日志可追溯。
6. 数据已经按约定格式保存。
7. 下游能正常读取。
8. 运行方式有文档。
9. 异常情况有处理方案。
```

你可以把它理解成“交付清单”。没有清单，项目就容易变成口头感觉。

#### 1.17.1 一个简单的完成标准示例

假设我们采集公开商品目录，可以这样定义：

```text
采集范围：公开商品列表前 100 页
采集字段：product_id、title、price、brand、detail_url、crawl_time
必填字段：product_id、title、detail_url
可选字段：price、brand
去重规则：product_id 唯一
输出格式：JSONL
失败记录：保存到 failed_tasks.jsonl
验收标准：
  - 总记录数不少于列表页商品数的 98%
  - product_id 缺失率为 0
  - title 缺失率为 0
  - 重复 product_id 数量为 0
  - 失败任务可重跑
```

这比“把商品抓下来”清楚得多。

有了这个标准，开发、测试、业务都知道什么叫完成。

### 1.18 爬虫项目里有哪些角色

小项目可能一个人全干。但企业项目里，爬虫往往涉及多个角色。

#### 1.18.1 需求方

需求方负责说明要什么数据、用来做什么、多久更新一次、准确率要求是多少。

很多时候，需求方并不知道技术细节，所以开发者要帮他们把模糊需求翻译成字段、范围和交付标准。

#### 1.18.2 爬虫开发

爬虫开发负责找到入口、写请求、解析字段、处理异常、保存数据、维护任务。

这本书主要面向这个角色。

#### 1.18.3 数据开发

数据开发可能负责把采集结果接入数据仓库、做清洗、建表、同步到下游系统。

如果爬虫输出格式乱，数据开发会很痛苦。所以字段命名、类型、唯一键要提前约定。

#### 1.18.4 运维或平台工程

当爬虫需要定时运行、部署到服务器、接入监控告警时，就会涉及运维或平台工程。

他们关心：

- 怎么启动。
- 怎么停止。
- 日志在哪里。
- 配置在哪里。
- 失败怎么报警。
- 资源占用多少。

#### 1.18.5 安全与合规

企业项目里，采集行为通常需要考虑授权、频率、数据使用范围、账号权限、隐私保护和审计记录。

这不是为了吓唬你，而是为了让项目长期可运行。一个没有边界的采集系统，后期很容易变成风险源。

### 1.19 开发前的风险预判

正式写代码前，可以先做一个简单风险评估。它不需要很复杂，但能帮你提前发现坑。

#### 1.19.1 数据入口风险

要判断：

- 数据是否在 HTML 里？
- 是否依赖 JavaScript？
- 是否需要登录？
- 是否需要点击、滚动、切换条件？
- 是否分散在多个接口？

入口越复杂，项目越容易超出预期。

#### 1.19.2 稳定性风险

要判断：

- 页面结构是否经常变化？
- 接口参数是否复杂？
- 字段是否稳定？
- 分页是否容易重复或漏数据？
- 是否有大量动态参数？

稳定性风险越高，越要重视样本保存、测试和监控。

#### 1.19.3 数据质量风险

要判断：

- 必填字段是否容易缺失？
- 是否存在重复数据？
- 是否有脏格式？
- 是否有多语言、多币种、多时间格式？
- 是否需要人工校验？

数据质量风险高时，清洗和校验就不能等到最后再做。

#### 1.19.4 运行成本风险

要判断：

- 数据量有多大？
- 每次采集要请求多少页面？
- 是否需要浏览器自动化？
- 是否需要大量存储？
- 是否需要并发？

浏览器自动化比普通请求重很多。如果一个任务能用接口解决，就不要一上来开浏览器。

### 1.21 一个从 0 到 1 的最小项目路线

如果你完全从零开始，不知道应该按什么顺序练，可以按下面路线走。

#### 第一步，只抓一个页面

目标是学会发请求、看状态码、保存 HTML。

不要急着解析。

#### 第二步，只解析一个字段

比如只解析标题。

目标是学会 BeautifulSoup 或 JSON 字段访问。

#### 第三步，解析一条完整记录

比如一个商品的标题、价格、链接。

目标是理解字段结构。

#### 第四步，解析一个列表页

从一页里提取多条记录。

目标是理解循环和容器。

#### 第五步，处理分页

抓第 1 页、第 2 页、第 3 页。

目标是理解任务拆分。

#### 第六步，进入详情页

列表页只产出详情链接，详情页补全字段。

目标是理解列表页和详情页分工。

#### 第七步，保存 JSONL

每条记录保存一行。

目标是让数据离开内存，真正落地。

#### 第八步，加重试、日志和失败记录

目标是让程序开始具备恢复能力。

#### 第九步，加去重和断点续爬

目标是让程序能长期运行，而不是每次从头开始。

这条路线比一上来学复杂框架更稳。你会知道每一个能力为什么出现，而不是为了学工具而学工具。

### 1.22 本章的自查清单

读完这一章，你可以用下面清单检查自己是否真的理解。

```text

我是否知道写代码前要先定义字段？

我是否知道响应要先看状态码和响应头？

我是否知道保存中间结果的重要性？
```

### 1.23 这一章的重点回顾

这一章没有让你写很多代码，因为它的目标是建立“工程直觉”。

你现在要记住：

1. 爬虫不是一个请求，而是一条流水线。
2. 能跑一次不等于能长期运行。
3. 写代码前要先定义字段和入口。
4. 请求、解析、清洗、存储、调度、监控都很重要。
5. 真正的企业级爬虫，核心能力是稳定、可维护、可恢复、可观察。
6. 项目开始前要问清楚字段、范围、频率、交付格式和质量标准。
7. 采集完成不是代码跑完，而是数据能被下游稳定使用。

### 1.24 课后练习

找一个你熟悉的网站，不需要真正写代码，先做分析。

请写下：

1. 你想采集哪些字段。
2. 哪些字段是必填，哪些是可选。
3. 数据可能在列表页，还是详情页，还是接口里。
4. 如果要分页，你猜它可能是哪种分页。
5. 哪个字段适合作为唯一键。
6. 如果程序中途失败，你希望保存哪些进度。
7. 你会用什么格式交付数据，CSV、JSONL 还是数据库？
8. 你会如何定义“采集完成”？
9. 哪些情况需要报警？
10. 这个任务最可能的风险是什么？

这个练习很重要。因为真正的爬虫开发，不是从敲代码开始，而是从理解数据流开始。
