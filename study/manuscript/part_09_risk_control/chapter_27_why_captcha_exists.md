# 第 27 章：验证码为什么存在
## 本章在主流程中的位置

验证码出现在第 1 章流水线的“接收响应”阶段：你以为会收到数据，实际收到的是人工确认要求。它不是普通解析问题，也不是简单重试能解决的问题。

本章承接第 25、26 章的环境差异和风险信号，后面第 28、29 章会继续讲行为风控和边缘安全系统。遇到验证码时，流程应该进入暂停、审计、人工确认或正式接口路线。

## 背景介绍

验证码是很多爬虫开发者都会遇到的拦路口。它会让自动化流程停下来，让脚本无法继续提交表单、登录账号、翻页或获取数据。新手很容易把验证码理解成“网站专门为难爬虫”，但如果从系统防御角度看，验证码其实是在解决一个更大的问题：如何在风险升高时确认访问者是不是正常用户。

互联网系统每天面对的不只是普通用户访问，还包括很多自动化滥用行为：

- 批量注册账号。
- 撞库登录。
- 短信接口滥用。
- 恶意评论和垃圾内容。
- 刷票、刷赞、刷榜。
- 抢库存、占库存。
- 优惠券和活动套利。
- 高频接口扫描。
- 批量枚举数据。

这些行为不一定都叫“爬虫”，但它们都有一个共同点：依赖自动化、大量重复、低成本试探。验证码的作用，就是在系统认为风险升高时，提高继续操作的成本，或者把请求转入人工确认。

所以验证码不是孤立组件，它通常是风控体系的一部分。一个成熟系统不会只靠验证码判断风险，而是把验证码放在风险评分、账号画像、设备指纹、访问频率、业务动作和人工审核之间。

本章不会讲如何绕过第三方验证码，也不会接入打码平台。我们会讲验证码的类型、触发原因、工程处理流程、自建模拟示例、人工审核队列、监控指标，以及自有系统如何降低误伤。

## 本章目标

学完本章后，你应该能做到：

1. 理解验证码在风控体系里的位置。
2. 认识常见验证码类型和它们考察的能力。
3. 知道验证码通常由哪些风险信号触发。
4. 在合规采集系统里设计“遇到验证码后的暂停和人工处理流程”。
5. 为自有系统设计验证码触发日志、审核队列和误伤评估。
6. 明确验证码相关工作的安全和合规边界。

## 适用场景

本章适合：

- 自有系统验证码方案设计。
- 内部自动化任务误触验证码时排查原因。
- 授权测试环境中的验证码可用性评估。
- 合规采集项目中的异常处理流程设计。
- 安全团队理解验证码与风险评分的关系。

## 不适用场景

本章不用于：

- 绕过第三方验证码。
- 批量规避登录、支付、评论、库存等风控。
- 未授权分析生产系统验证码逻辑。
- 使用外部打码服务绕开访问控制。

遇到验证码时，企业级系统的默认动作应该是暂停、记录、评估、降频、申请授权或切换正式接口，而不是继续自动尝试。

## 验证码在风控体系中的位置

可以把风控处置想象成一组台阶：

```text
正常访问
  -> 记录风险信号
  -> 轻度限速
  -> 二次确认
  -> 验证码
  -> 人工审核
  -> 临时阻断
  -> 账号或 IP 处置
```

验证码通常不是第一步，也不是最后一步。它常常出现在“系统不确定，但又不想直接拒绝”的位置。

例如：

- 登录失败次数变多，但还不能确定是攻击。
- 注册行为较密集，但可能是活动高峰。
- 页面访问频率较高，但可能是内部工具。
- 设备或网络环境异常，但用户可能正在出差。

验证码给系统一个折中选择：不直接封禁，而是要求额外确认。

## 常见验证码类型

### 文本验证码

文本验证码要求用户识别图片中的字符并输入。

它考察的是人类视觉识别能力。早期系统中很常见，实现简单，但用户体验不太好，对视觉障碍用户不友好，也容易受到 OCR 技术影响。

自有系统使用文本验证码时，要考虑：

- 字符是否过度扭曲。
- 是否有语音替代。
- 错误提示是否清晰。
- 是否容易误伤正常用户。

### 图片点选验证码

图片点选要求用户选择符合条件的图片或点击图片中的目标，例如“请选择所有包含红绿灯的图片”。

它考察的是图像理解能力和点击行为。缺点是用户体验容易不稳定：图片模糊、目标边界不清、题目表达不明确时，真实用户也会失败。

### 滑块验证码

滑块验证码要求用户拖动滑块到指定位置。很多新手以为滑块只考察“缺口坐标”，但真实防御通常还会关注拖动过程：

- 起始位置。
- 移动速度。
- 加速度变化。
- 停顿。
- 轨迹是否机械。
- 事件是否来自真实交互环境。

因此，从防御视角看，滑块不是一张图片题，而是一组视觉和行为信号的组合。

### 拼图验证码

拼图验证码和滑块类似，但交互更复杂，可能需要把碎片放到正确位置。它同样会结合轨迹、时间和环境信号。

### 语音验证码

语音验证码常作为无障碍替代方式，也用于某些场景的二次验证。自有系统要注意防滥用，同时不能破坏无障碍访问。

### 逻辑题验证码

例如简单算术、文字问答、顺序点击。这类方案实现简单，但如果题库固定、规则简单，很容易被自动化处理。它更适合低风险场景，不适合高价值业务边界。

### 无感验证

无感验证尽量不打扰用户。系统先根据设备、网络、行为、账号历史打分，低风险直接通过，高风险再升级为显式验证。

现代风控更倾向这种分层方式，因为它能减少正常用户被打断的次数。

## 验证码通常为什么触发

验证码一般不是随机出现的。常见触发因素包括：

| 触发因素 | 解释 |
| --- | --- |
| 请求频率过高 | 短时间内访问、提交、搜索、登录次数异常 |
| 登录失败过多 | 撞库或密码猜测风险 |
| 新账号高频操作 | 新注册账号立刻大量访问敏感功能 |
| IP 或出口风险 | 出口信誉差、频繁变化、来自高风险网络 |
| 设备环境异常 | 指纹不稳定或信号组合不一致 |
| 行为轨迹机械 | 点击、滚动、输入节奏过于固定 |
| 访问路径异常 | 绕过正常页面流程，直接访问大量详情或接口 |
| 敏感业务动作 | 注册、登录、发短信、下单、评论、提现等 |

成熟系统会综合这些信号，而不是因为一个字段异常就立刻弹验证码。

## 合规采集遇到验证码怎么办

### 第一步：暂停当前任务

验证码出现后，不要继续自动重试。继续重试通常会让风险分更高。

### 第二步：记录现场

记录：

- 任务 ID。
- 目标 URL。
- 当前账号或 Token。
- 出口 IP 或网络环境。
- 请求频率。
- 最近状态码。
- 页面截图。
- 响应头。
- 触发前操作链路。

### 第三步：进入人工审核

把任务放入人工审核队列，让负责人判断：

- 是否仍在授权范围内。
- 是否访问频率过高。
- 是否应切换官方 API。
- 是否需要联系数据方。
- 是否应该暂停该目标。

### 第四步：选择降级策略

可能的处理：

- 降低频率。
- 只采低风险页面。
- 改用官方 API。
- 使用专用授权 Token。
- 停止采集。
- 等待业务方确认。

默认策略不应是“继续尝试”。

## 自建示例：验证码触发流程模拟

下面写一个本地服务，模拟“短时间请求过多后进入人工审核”。它不是真验证码，只用于教学。

`captcha_flow_demo.py`：

```python
from http.server import BaseHTTPRequestHandler, HTTPServer
import json
import time


WINDOW_SECONDS = 10
MAX_VISITS = 5
VISITS = {}


class CaptchaFlowHandler(BaseHTTPRequestHandler):
    def do_GET(self):
        client = self.client_address[0]
        now = time.time()

        visits = [
            timestamp
            for timestamp in VISITS.get(client, [])
            if now - timestamp < WINDOW_SECONDS
        ]
        visits.append(now)
        VISITS[client] = visits

        if len(visits) > MAX_VISITS:
            self.send_json({
                "ok": False,
                "need_review": True,
                "reason": "too many requests in a short time",
                "window_seconds": WINDOW_SECONDS,
                "max_visits": MAX_VISITS,
            })
            return

        self.send_json({
            "ok": True,
            "data": {
                "message": "normal response",
                "visit_count": len(visits),
            },
        })

    def send_json(self, payload):
        body = json.dumps(payload, ensure_ascii=False).encode("utf-8")
        self.send_response(200)
        self.send_header("Content-Type", "application/json; charset=utf-8")
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)


if __name__ == "__main__":
    server = HTTPServer(("127.0.0.1", 8050), CaptchaFlowHandler)
    print("captcha flow demo running at http://127.0.0.1:8050")
    server.serve_forever()
```

客户端：

```python
import json
import time
from pathlib import Path

import requests


REVIEW_FILE = Path("review_tasks.jsonl")


def save_review_task(payload):
    with REVIEW_FILE.open("a", encoding="utf-8") as file:
        file.write(json.dumps(payload, ensure_ascii=False) + "\n")


for index in range(8):
    response = requests.get("http://127.0.0.1:8050", timeout=10)
    payload = response.json()
    print(index, payload)

    if payload.get("need_review"):
        review_task = {
            "task_id": f"demo-{index}",
            "url": "http://127.0.0.1:8050",
            "reason": payload["reason"],
            "status": "pending",
            "created_at": time.strftime("%Y-%m-%d %H:%M:%S"),
        }
        save_review_task(review_task)
        print("task paused and saved to manual review queue")
        break

    time.sleep(1)
```

这个示例表达的重点不是验证码本身，而是流程：出现高风险信号后，任务暂停，现场进入审核队列。

## 人工审核表设计

真实平台可以设计：

```text
review_tasks
  id
  task_id
  target_url
  account_id
  reason
  screenshot_path
  response_status
  response_headers
  status
  created_at
  reviewed_at
  reviewer
  decision
  note
```

状态：

- `pending`：待处理。
- `approved`：人工确认可以继续。
- `paused`：暂停任务。
- `switched_to_api`：改用正式接口。
- `rejected`：停止采集。

审核结论必须写清原因，否则下一次还会重复踩坑。

## 自有系统如何设计验证码触发

如果你是防御方，不建议把验证码作为唯一防线。更合理的是风险分层：

```text
低风险：直接放行
中低风险：轻微限速
中风险：无感验证或二次确认
高风险：显式验证码
严重风险：人工审核或临时阻断
```

设计时要关注两个指标：

- 拦截率：拦住了多少异常行为。
- 误伤率：影响了多少正常用户。

只看拦截率会让系统越来越严格，最后真实用户也用不了。

## 监控指标

采集侧可以监控：

- 验证码触发次数。
- 触发率。
- 按任务分布。
- 按账号分布。
- 按出口分布。
- 触发后的处理时长。
- 触发后的降级决策。

防御侧可以监控：

- 验证码通过率。
- 验证码失败率。
- 用户放弃率。
- 验证耗时。
- 误伤反馈。
- 不同规则命中次数。

如果验证码通过率很低，不一定说明机器人多，也可能是题目太难或体验太差。

## 常见错误

### 错误一：验证码一出现就继续重试

验证码出现说明风险已经升高。继续请求可能让账号、IP、任务进入更高风险状态。

### 错误二：只关注识别，不关注触发原因

比“怎么处理验证码”更重要的是“为什么触发验证码”。频率、路径、账号、设备、权限都要检查。

### 错误三：没有人工流程

合规系统要有审核队列、截图、日志、状态流转。否则任务卡住后没人知道，也没人负责。

### 错误四：验证码设计不考虑可访问性

自有系统要考虑视觉障碍用户、移动端用户、老年用户、网络较差用户。安全不能完全牺牲可用性。

### 错误五：把验证码当唯一防线

验证码只是风控体系的一部分。服务端权限、频率限制、账号安全、业务规则和审计同样重要。

## 调试方法

### 记录触发上下文

没有上下文，就很难判断是频率问题、权限问题、页面改版还是规则变化。

建议记录：

```text
task_id
run_id
url
account_id
ip_or_exit
request_rate
last_status_code
current_page_title
screenshot_path
response_headers
```

### 对齐服务端日志

如果是自有系统，前端截图要和服务端风险日志对齐。看命中的规则、风险分、账号状态、IP 信誉和处置结果。

### 小流量复现

不要用高频任务复现问题。用测试账号、小流量、测试环境复现，避免造成真实影响。

## 工程化扩展

### 任务暂停规则

出现验证码后，可以写入暂停规则：

```text
scope_type: task
scope_value: product_daily
reason: captcha triggered
until: 2026-06-01 18:00:00
created_by: system
```

调度器看到暂停规则后，不再派发该任务。

### 触发率告警

告警示例：

```text
任务 product_daily 最近 30 分钟验证码触发率达到 8%，超过阈值 2%。
建议：暂停任务，检查频率、登录态和目标规则变化。
```

### 审核后的补采

如果任务暂停期间漏采数据，需要根据游标、时间范围或失败任务队列补采。补采也要限速，不能一次性补爆。

## 安全与合规注意

验证码背后通常是访问控制和风险处置。绕过第三方验证码可能违反服务条款、合同和法律，也可能损害目标系统和用户权益。

企业级项目应优先选择：

- 官方 API。
- 授权数据。
- 合作接口。
- 白名单。
- 专用 Token。
- 数据导出。
- 人工审核。

技术能力应该服务于可靠交付，而不是制造不可审计的风险。

## 本章小结

验证码存在的原因，是在风险升高时增加确认步骤。它不是孤立组件，而是风控体系的一部分。

对采集侧来说，遇到验证码应暂停、记录、告警、人工介入或改用正式渠道。对防御侧来说，验证码要和风险评分、误伤控制、可访问性、人工复核一起设计。
