# 第 28 章：行为风控信号
## 本章在主流程中的位置

行为风控会贯穿“发送请求、调度任务、监控维护”。它关注的不只是单个请求对不对，还包括频率、路径、账号、时间、失败率等整体行为。

本章会反过来约束前面的并发、异步、浏览器自动化和分布式队列：系统越强，越需要低扰动和可审计。第 31 章的礼貌采集会继续把这个思想落到限速和配额上。

## 背景介绍

浏览器指纹回答的是“访问环境像不像一个合理设备”，验证码回答的是“风险升高后如何确认”。行为风控关注的是另一个维度：访问过程本身是否合理。

真实用户使用网站时，行为通常有目的、有路径、有节奏。例如一个用户想买课程，可能会先搜索关键词，再浏览列表，点进详情，停留一会儿，看价格和评价，再返回列表继续筛选。这个过程有上下文。

自动化任务如果只按固定间隔请求接口，或者每次都走完全相同的路径，就会显得机械。风控系统不一定知道“你是不是爬虫”，但它能观察到一些异常模式：

- 请求非常密集。
- 访问路径缺少上下文。
- 同一账号不断切换设备和网络。
- 页面停留时间不符合业务动作。
- 错误率、提交频率、敏感操作次数异常。

本章不是教你模拟真人行为来绕过系统。我们从两个正当视角讲行为信号：

1. 防御侧：自有系统如何识别异常、降低误伤、设计可解释风险评分。
2. 采集侧：合规采集如何降低扰动、明确身份、可审计运行。

成熟的行为风控不是“抓住所有机器人”，而是在安全、体验、成本和业务连续性之间做平衡。

## 本章目标

学完本章后，你应该能做到：

1. 理解请求行为、页面交互行为、账号画像、设备画像、网络画像的区别。
2. 知道行为风控为什么要看信号组合，而不是单点判断。
3. 写一个自建风险评分示例。
4. 设计风险事件表和行为日志表。
5. 为合规采集设计低扰动策略。
6. 理解内部自动化任务为什么应该使用明确身份。

## 适用场景

本章适合：

- 自有系统风险评分设计。
- 内部自动化任务误伤排查。
- 合规采集策略设计。
- 平台监控和告警建设。
- 安全团队分析异常访问模式。

## 不适用场景

本章不用于：

- 绕过第三方行为风控。
- 构造伪装真人轨迹。
- 批量规避验证码或拦截规则。
- 未授权测试生产系统。

行为风控知识应该用于防御理解、授权排障和低扰动工程设计。

## 行为信号分类

### 请求频率

请求频率是最基础的行为信号。

常见维度：

- 每秒请求数。
- 每分钟请求数。
- 每小时请求数。
- 单接口请求频率。
- 单账号请求频率。
- 单 IP 请求频率。
- 单设备请求频率。

频率阈值必须按业务设置。登录接口一分钟 10 次可能很高，静态资源一分钟 100 次可能很正常。不要用一个阈值套所有接口。

### 访问路径

访问路径描述用户从哪里来、到哪里去。

正常路径可能是：

```text
首页 -> 搜索页 -> 列表页 -> 详情页 -> 返回列表页
```

异常路径可能是：

```text
详情页 1 -> 详情页 2 -> 详情页 3 -> 详情页 4
```

连续访问详情页不一定恶意，但如果没有列表页来源、没有搜索、没有停留、没有正常导航，就值得关注。

### 停留时间

用户阅读页面需要时间。一个账号每 100 毫秒打开一个详情页，不符合正常阅读行为。

但停留时间不能单独判断。监控探针、内部测试工具、搜索引擎、合作方接口同步都可能快速访问。关键是身份是否明确、是否授权、是否受限速控制。

### 点击、滚动和输入

页面交互信号包括：

- 点击位置。
- 点击间隔。
- 滚动距离。
- 滚动速度。
- 输入节奏。
- 焦点切换。
- 页面可见性变化。

这些信号常用于识别机械操作。但它们也容易误伤，例如键盘高手、辅助工具用户、网络卡顿用户、移动端用户。所以行为信号应作为风险评分的一部分，而不是单独封禁依据。

### 账号画像

账号画像包括：

- 注册时间。
- 历史登录地区。
- 常用设备。
- 常用访问时段。
- 历史业务行为。
- 风险事件记录。

新账号、高频操作、频繁换设备、高价值动作密集出现，组合起来风险更高。

### 设备画像

设备画像包括浏览器指纹、Cookie、localStorage、设备 ID、登录历史等。它回答的是：这个访问环境是不是该账号平时使用的环境。

同一个账号短时间内在多个完全不同设备上高频操作，通常比单次设备变化更可疑。

### 网络画像

网络画像包括：

- IP。
- ASN。
- 地理位置。
- 是否代理或云服务出口。
- 出口稳定性。
- 历史信誉。

网络画像不能单独决定风险，因为真实用户也会使用 VPN、公司网络、移动网络。但它是组合信号中的重要部分。

## 信号组合比单点更重要

单个信号异常并不一定代表恶意：

- 用户出差导致地区变化。
- 用户换了新手机。
- 页面刷新导致短时间请求增加。
- 公司内网出口让很多用户共享 IP。

但多个信号同时异常，就值得关注：

```text
新账号 + 高频详情访问 + 无列表路径 + 设备频繁变化 + 出口频繁变化
```

这就是风险评分的基本思想：每个信号加一点分，组合起来决定处置。

## 自建示例：可解释风险评分

下面写一个简化评分器。它不是生产模型，只用于理解行为信号组合。

```python
from dataclasses import dataclass


@dataclass
class VisitContext:
    requests_per_minute: int
    detail_pages_per_minute: int
    has_list_page_before_detail: bool
    average_dwell_seconds: float
    account_age_days: int
    device_changed_recently: bool
    ip_changed_recently: bool
    failed_login_count: int
    is_internal_token: bool


def score_risk(ctx: VisitContext):
    score = 0
    reasons = []

    if ctx.is_internal_token:
        return 0, ["authorized internal task"]

    if ctx.requests_per_minute > 120:
        score += 30
        reasons.append("high request rate")

    if ctx.detail_pages_per_minute > 60:
        score += 25
        reasons.append("many detail pages in a short time")

    if not ctx.has_list_page_before_detail:
        score += 15
        reasons.append("detail access without list path")

    if ctx.average_dwell_seconds < 0.5:
        score += 15
        reasons.append("very short dwell time")

    if ctx.account_age_days < 3:
        score += 10
        reasons.append("new account")

    if ctx.device_changed_recently:
        score += 15
        reasons.append("device changed recently")

    if ctx.ip_changed_recently:
        score += 15
        reasons.append("ip changed recently")

    if ctx.failed_login_count >= 5:
        score += 30
        reasons.append("many failed login attempts")

    return score, reasons


def decide_action(score):
    if score < 30:
        return "allow"
    if score < 60:
        return "rate_limit"
    if score < 90:
        return "challenge"
    return "manual_review"
```

使用：

```python
examples = [
    VisitContext(20, 5, True, 8.0, 300, False, False, 0, False),
    VisitContext(200, 120, False, 0.1, 1, True, True, 0, False),
    VisitContext(500, 300, False, 0.1, 0, True, True, 8, True),
]

for ctx in examples:
    score, reasons = score_risk(ctx)
    print(score, decide_action(score), reasons)
```

第三个样本虽然请求频率很高，但 `is_internal_token=True`，所以直接识别为授权内部任务。这是企业系统非常重要的设计：内部自动化应该有明确身份，而不是伪装成普通用户。

## 逐段解释

```python
if ctx.is_internal_token:
    return 0, ["authorized internal task"]
```

内部自动化、监控、测试、采集任务应该使用专用身份。这样服务端可以给它独立额度、审计和限速策略。

```python
if ctx.average_dwell_seconds < 0.5:
```

停留时间过短可能表示机械访问。但不要单独用它封禁，因为某些工具型页面、内部系统、监控任务本来就停留很短。

```python
reasons.append(...)
```

原因记录非常重要。没有原因的风险分是黑箱，无法排查误伤，也无法向业务解释。

```python
decide_action(score)
```

评分和处置分开。评分告诉你风险高低，处置告诉你怎么处理。这样更容易调整策略。

## 风险事件表设计

```text
risk_events
  id
  subject_type
  subject_id
  request_id
  score
  action
  reasons
  created_at
```

`subject_type` 可以是：

- account
- ip
- device
- task
- token

`reasons` 建议保存 JSON：

```json
["high request rate", "device changed recently"]
```

这样后续可以统计哪些规则误伤最多。

## 行为日志表设计

```text
behavior_logs
  id
  account_id
  device_id
  ip
  path
  method
  status_code
  referer
  dwell_seconds
  event_type
  created_at
```

注意最小化采集。不要为了风控把所有用户行为无限期保存。字段、用途、保存期限和访问权限都要明确。

## 合规采集如何降低扰动

### 控制频率

低频、稳定、可预期的访问对目标系统影响更小。不要短时间打满请求。

### 做增量采集

保存游标，只采新增或变化数据。不要每天全量扫一遍。

### 使用缓存

同一数据短时间内不要重复请求。缓存能显著降低访问量。

### 使用正式身份

内部或合作项目应使用：

- 专用 Token。
- API Key。
- 白名单。
- 合作接口。
- 数据导出。

不要用普通用户页面操作承载长期自动化任务。

### 错误退避

出现 429、403、验证码、异常跳转时，暂停或降速，不要继续加压。

## 自有系统如何降低误伤

### 不要单点拦截

单个字段异常只应加风险分，不应直接拦截。除非是明确恶意或高危动作。

### 分层处置

```text
低风险：放行
中风险：限速
较高风险：二次确认或验证码
高风险：人工审核
严重风险：临时阻断
```

### 给内部自动化专用通道

内部任务如果没有身份，就会被普通风控误伤。专用通道可以包括：

- 专用账号。
- 专用 Token。
- 固定出口。
- 独立限速。
- 审计日志。

### 保留申诉和复核

任何风控系统都有误伤。重要业务必须有人工复核和申诉路径。

## 常见错误

### 错误一：行为风控只看鼠标轨迹

鼠标轨迹只是行为信号之一。请求频率、访问路径、账号设备关系往往更重要。

### 错误二：所有接口使用同一个阈值

登录、短信、搜索、详情、静态资源的风险完全不同，不能用同一阈值。

### 错误三：只返回“风险高”

没有原因的结论无法排查。要记录命中规则和分数来源。

### 错误四：内部自动化没有明确身份

这会让审计和排障变困难，也会增加误伤。

### 错误五：采集侧没有退避

遇到 429、验证码、403 后继续请求，会加重风险。应退避、暂停、告警。

## 调试方法

### 关联多类日志

排查行为风控需要关联：

- 网关日志。
- 应用日志。
- 风控日志。
- 账号日志。
- 任务日志。
- 前端埋点。

只看客户端日志通常不够。

### 画访问路径

把访问路径按时间画出来：

```text
10:00:01 /search?q=python
10:00:03 /items
10:00:05 /item/1001
10:00:06 /item/1002
10:00:06 /item/1003
```

路径一画出来，异常通常很直观。

### 分桶统计

按账号、IP、设备、接口、任务 ID 分桶统计请求量、错误率、验证码触发率，能快速定位异常来源。

## 工程化扩展

### 风险评分服务

大型系统可以把风险评分做成独立服务：

```text
请求上下文 -> 风险评分服务 -> 分数和原因 -> 业务系统决定处置
```

这样多个业务线可以复用规则，也方便审计和回滚。

### 规则灰度

新规则不要直接全量拦截。先 Log 模式观察，再小流量灰度，最后再参与处置。

### 误伤分析

统计被人工放行的事件，反向优化规则。误伤是风控系统必须长期治理的问题。

## 安全与合规注意

行为数据可能涉及隐私。自有系统采集时应：

- 明确用途。
- 最小化采集。
- 设置保存期限。
- 控制访问权限。
- 对敏感字段脱敏。
- 在合规文档中说明。

采集侧则应坚持透明、低扰动、可授权、可审计，而不是伪装普通用户。

## 本章小结

行为风控看的是访问过程：频率、路径、停留、交互、账号、设备、网络之间的关系。它不是一个鼠标轨迹判断器，而是一套多信号风险评估体系。

对自有系统，行为信号应用于可解释评分和分层处置；对采集系统，理解行为信号应帮助我们降低扰动、明确身份、暂停异常，而不是规避规则。
