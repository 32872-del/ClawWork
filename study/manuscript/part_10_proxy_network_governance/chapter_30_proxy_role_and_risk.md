# 第 30 章：代理的作用与风险
## 本章在主流程中的位置

代理属于“发送请求”的网络出口治理，也会影响“监控维护”。第 1 章说爬虫要长期稳定运行，出口如果不可控，稳定性和合规性都会出问题。

本章会连接第 28、29 章的风险信号，也为第 31 章限速配额和第 32-34 章分布式采集做准备。分布式 worker 越多，出口治理越重要。

## 背景介绍

很多新手一遇到 403、429、超时，就第一反应“是不是要上代理”。这是一种很常见但危险的思路。代理确实是网络工程里的重要工具，但它不是万能钥匙，更不是解决所有访问问题的第一选择。

代理的本质是：你的请求不直接从本机发到目标服务器，而是先经过一个中间出口，再由这个出口访问目标。它可以用于网络隔离、出口治理、地区测试、内部系统访问、成本控制和故障排查。

在企业级采集里，代理更应该被理解成“网络出口治理工具”，而不是“绕过限制工具”。如果请求频率过高、权限不正确、接口未授权、任务没有限速，只换代理并不能解决根本问题，反而会带来账号风险、数据污染、成本浪费和合规风险。

本章会讲代理类型、适用场景、风险、健康检查、成本核算和工程化治理。重点是如何正确管理网络出口，而不是如何对抗第三方系统。

## 本章目标

学完本章后，你应该能做到：

1. 理解 HTTP 代理、HTTPS 代理、SOCKS 代理的区别。
2. 知道代理适合解决哪些问题，不适合解决哪些问题。
3. 理解代理质量比数量更重要。
4. 设计代理健康检查和评分。
5. 理解代理与账号、设备、频率之间的关系。
6. 为合规采集系统设计出口治理策略。

## 适用场景

代理适合：

- 公司内部统一出口治理。
- 地区可用性测试。
- 多机房网络质量测试。
- 隔离生产任务和办公网络。
- 访问自有内网或合作方专线。
- 控制不同任务的出口成本。
- 故障排查：判断问题是否与本机网络有关。

## 不适用场景

代理不适合：

- 未授权访问受保护资源。
- 绕过验证码、风控、WAF。
- 用大量低质量出口冲击目标系统。
- 替代限速、授权、缓存、增量采集。
- 掩盖账号滥用或高频请求。

如果问题根因是频率、权限、登录态、参数、合规边界，代理只会让问题更复杂。

## 代理类型

### HTTP 代理

HTTP 代理主要处理 HTTP 请求。客户端把完整 URL 发给代理，代理再请求目标。

Python `requests` 示例：

```python
import requests

proxies = {
    "http": "http://127.0.0.1:8080",
    "https": "http://127.0.0.1:8080",
}

response = requests.get("https://example.com", proxies=proxies, timeout=10)
print(response.status_code)
```

注意 `https` 的代理地址也常常写成 `http://proxy`，表示客户端通过 HTTP CONNECT 方法让代理建立到目标的隧道。

### SOCKS 代理

SOCKS 工作在更底层，可以代理更多协议。Python 使用时通常需要额外依赖：

```bash
pip install requests[socks]
```

示例：

```python
proxies = {
    "http": "socks5://127.0.0.1:1080",
    "https": "socks5://127.0.0.1:1080",
}
```

### 透明代理、匿名代理、高匿名代理

这些说法常用于描述代理是否暴露客户端真实信息：

- 透明代理：可能暴露原始 IP 或代理痕迹。
- 匿名代理：隐藏原始 IP，但可能表明自己是代理。
- 高匿名代理：尽量不暴露代理痕迹。

企业项目里，不要被营销词带偏。更重要的是可用性、稳定性、延迟、错误率、合规来源和审计能力。

## 代理质量指标

代理质量不能只看“有多少个 IP”。应关注：

- 可用率。
- 平均响应时间。
- P95 / P99 响应时间。
- 连接失败率。
- 超时率。
- 目标站点成功率。
- 地区和运营商。
- 出口稳定性。
- 并发承载能力。
- 成本。
- 合规来源。

一个稳定、可审计、低错误率的出口，比一万个不稳定出口更有价值。

## 自建代理健康检查示例

下面写一个代理健康检查框架。它不会提供真实代理，只展示如何评估。

```python
import time
import requests


TEST_URL = "https://example.com"


def check_proxy(proxy_url):
    proxies = {
        "http": proxy_url,
        "https": proxy_url,
    }
    started = time.perf_counter()

    try:
        response = requests.get(TEST_URL, proxies=proxies, timeout=8)
        elapsed = time.perf_counter() - started
        return {
            "proxy": proxy_url,
            "ok": response.status_code == 200,
            "status_code": response.status_code,
            "elapsed": round(elapsed, 3),
            "error": None,
        }
    except requests.RequestException as exc:
        elapsed = time.perf_counter() - started
        return {
            "proxy": proxy_url,
            "ok": False,
            "status_code": None,
            "elapsed": round(elapsed, 3),
            "error": type(exc).__name__,
        }


def score_result(result):
    if not result["ok"]:
        return 0
    if result["elapsed"] <= 1:
        return 100
    if result["elapsed"] <= 3:
        return 80
    if result["elapsed"] <= 6:
        return 50
    return 20


proxy_list = [
    "http://127.0.0.1:8080",
]

for proxy in proxy_list:
    result = check_proxy(proxy)
    result["score"] = score_result(result)
    print(result)
```

真实项目里，健康检查不应该只访问一个测试 URL。最好同时检查：

- 基础连通性。
- 目标域名可用性。
- 延迟。
- 错误类型。
- 最近一段时间成功率。

## 逐段解释

```python
response = requests.get(TEST_URL, proxies=proxies, timeout=8)
```

这里用代理请求测试地址。`timeout` 必须设置，否则坏代理可能让任务长时间卡住。

```python
except requests.RequestException as exc:
```

代理失败有很多类型：连接失败、读取超时、代理认证失败、TLS 错误等。不要只记录“失败”，要记录错误类型。

```python
score_result(result)
```

评分是为了让调度器选择更好的出口。评分规则可以按业务调整。例如某些任务更看重地区，某些任务更看重延迟。

## 代理与账号、设备、频率的关系

代理不是孤立变量。风控系统常常看组合：

```text
账号 + 设备 + IP + 行为 + 频率
```

如果同一个账号频繁切换出口，可能比固定出口更异常。如果同一个出口承载大量账号，也可能异常。如果请求频率过高，不管换不换代理，都会增加风险。

合规采集更好的方式是：

- 明确授权。
- 使用专用接口。
- 控制频率。
- 固定稳定出口。
- 记录任务身份。
- 和目标系统协商白名单或额度。

## 常见错误

### 错误一：把代理当成第一解决方案

遇到失败先排查：状态码、参数、登录态、频率、权限、目标是否变更。代理应该在明确网络出口问题时使用。

### 错误二：只追求数量

大量低质量代理会造成更多超时、重试、数据缺失和成本浪费。

### 错误三：没有健康检查

不健康的代理如果进入任务池，会拖慢整个采集系统。

### 错误四：没有成本核算

代理通常按流量、请求量、IP 数、并发或时间计费。没有成本指标，任务规模一上来就可能失控。

### 错误五：忽视合规来源

代理来源必须合规。不要使用来源不明、可能涉及滥用的网络资源。

## 调试方法

### 对比直连和代理

同一 URL 分别直连和代理访问，记录：

- 状态码。
- 响应时间。
- 响应头。
- 响应体摘要。
- 错误类型。

### 分目标域名统计

某个代理访问 A 站正常，访问 B 站失败，说明问题可能是目标相关，而不是代理整体坏。

### 记录出口信息

在授权环境中，可以访问自建 echo 服务，记录出口 IP、地区、请求头，用于排查出口配置。

## 工程化扩展

### 代理池表结构

```text
proxy_pool
  id
  proxy_url
  region
  provider
  status
  score
  success_count
  failure_count
  avg_latency
  last_checked_at
  last_error
```

状态可以是：

- active
- cooling
- disabled
- expired

### 调度策略

可以按任务类型选择出口：

- 内部 API：固定公司出口。
- 地区测试：指定地区出口。
- 低优先级任务：低成本出口。
- 高稳定任务：高评分出口。

### 熔断

如果某个代理连续失败，应进入冷却：

```text
连续失败 3 次 -> cooling 10 分钟
连续失败 10 次 -> disabled
```

不要让坏代理一直参与调度。

## 安全与合规注意

代理涉及网络出口和身份边界。企业使用代理应：

- 确认来源合法。
- 记录使用者和任务。
- 控制权限。
- 防止敏感数据经过不可信代理。
- 对账号和出口绑定策略做审计。
- 遵守目标系统访问规则。

## 本章小结

代理是网络出口治理工具，不是万能绕过工具。真正成熟的代理管理关注质量、稳定性、成本、合规和审计。

当采集任务失败时，先分析根因；确实是网络出口问题，再引入代理。引入后也要有健康检查、评分、熔断和成本统计。
