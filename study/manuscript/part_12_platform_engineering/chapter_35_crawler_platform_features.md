# 第 35 章：爬虫平台应该有什么
## 本章在主流程中的位置

本章进入第 1 章流水线的“监控维护”和“长期管理”。前面所有能力都是单个任务或单个系统模块，平台化要把这些能力变成可被团队使用和治理的产品。

它承接第 32-34 章的任务队列和编排，也连接第 36、37 章的监控、配置、密钥和权限。平台不是漂亮页面，而是把任务、数据、日志、风险和责任管起来。

## 背景介绍

一个爬虫脚本写到最后，通常会遇到两种命运。

第一种命运是它只服务一个小任务：某个同事运行一下，拿到一份数据，任务结束。这种脚本不一定需要平台，写清 README、保存结果、留好测试就够了。

第二种命运是它开始变成“长期任务”：每天跑、每小时跑、多人维护、多个目标、多个账号、多个数据表、多个失败原因、多个业务方使用。一旦进入这个阶段，单纯靠脚本和定时任务就会越来越吃力。

你会开始遇到这些问题：

- 任务在哪台机器上跑？
- 谁创建了这个任务？
- 任务现在是运行中、暂停中，还是失败了？
- 上次失败是什么原因？
- 采集到了多少数据？
- 数据字段是否完整？
- 任务频率是谁改的？
- 如果触发验证码或 429，谁会收到告警？
- 如何暂停某个目标，而不是停掉整台机器？
- 如何重跑失败任务，而不是全量重跑？

爬虫平台要解决的不是“如何写一个爬虫”，而是“如何管理一批爬虫”。它把任务配置、调度、运行、日志、数据预览、失败重跑、权限和审计集中起来，让团队能长期维护。

你可以把平台理解成采集系统的控制台。脚本像一台台机器，平台像车间里的调度室：谁开工、谁停工、产量多少、哪里报警、谁改了参数，都要看得见。

## 本章目标

学完本章后，你应该能做到：

1. 理解爬虫平台和脚本集合的区别。
2. 设计一个采集平台的核心模块。
3. 知道平台 MVP 应该先做哪些功能。
4. 理解任务、运行批次、日志、失败任务、审计记录之间的关系。
5. 设计基础数据表和 API。
6. 明确平台化带来的权限和合规要求。

## 适用场景

适合平台化的情况：

- 采集任务数量超过几个脚本。
- 任务需要定时运行。
- 任务有多人维护。
- 失败需要告警和重跑。
- 数据被多个业务方使用。
- 需要权限控制和审计。
- 需要统一限速、代理、队列、日志和监控。

## 不适用场景

不一定需要平台的情况：

- 一次性小脚本。
- 学习实验。
- 单人维护、运行频率很低。
- 没有长期数据交付要求。

平台不是越早越好。过早平台化会让简单问题复杂化。比较稳妥的路线是：先有稳定脚本，再抽象通用结构，最后平台化管理。

## 平台解决什么问题

### 可见性

没有平台时，任务状态经常藏在命令行、日志文件或某台服务器里。平台要让状态可见：

- 哪些任务正在跑。
- 哪些任务失败。
- 哪些任务暂停。
- 哪些任务最近没有产出数据。
- 哪些任务错误率升高。

### 可控制

平台不仅要能启动任务，还要能暂停、恢复、重跑、降频、禁用目标。

只会启动的平台很危险。出问题时停不下来，比跑不起来更麻烦。

### 可审计

企业环境里，必须知道：

- 谁创建任务。
- 谁修改频率。
- 谁导出了数据。
- 谁更新了密钥。
- 谁重跑了失败任务。

没有审计，就很难复盘事故。

### 可复用

平台可以统一封装：

- 请求层。
- 限速。
- 重试。
- 代理治理。
- 存储。
- 日志。
- 告警。

这样不同任务不需要重复造轮子。

## 核心模块

### 任务管理

任务管理回答“采什么、谁负责、当前状态是什么”。

任务状态可以设计为：

```text
draft      草稿
active     启用
paused     暂停
disabled   禁用
archived   归档
```

任务表：

```text
crawl_tasks
  id
  name
  description
  target_type
  target_value
  owner
  status
  schedule_type
  schedule_value
  config_json
  created_at
  updated_at
```

`config_json` 可以保存任务配置，例如并发、超时、起始 URL、输出表等。

### 运行批次

同一个任务会运行很多次，每次运行应该有独立记录。

```text
crawl_runs
  id
  task_id
  status
  trigger_type
  started_at
  finished_at
  total_requests
  success_requests
  failed_requests
  parsed_items
  saved_items
  error_summary
```

状态：

```text
pending
running
success
failed
cancelled
partial_success
```

为什么需要运行批次？因为任务配置会变，页面会变，错误会变。没有运行批次，所有日志混在一起，后面很难追踪。

### 配置管理

配置管理回答“这个任务怎么跑”。

常见配置：

- 起始 URL。
- 请求超时。
- 最大并发。
- 下载延迟。
- 是否走代理。
- 输出位置。
- 解析规则版本。
- 最大重试次数。
- 增量游标。

配置应该能版本化。否则今天配置改了，昨天的运行失败就很难解释。

### 调度管理

调度管理回答“任务什么时候跑”。

常见触发方式：

- 手动触发。
- 定时触发。
- 间隔触发。
- 上游事件触发。
- 失败后重跑。

调度系统必须支持暂停。暂停粒度可以是：

- 全局暂停。
- 任务暂停。
- 域名暂停。
- 账号暂停。
- 目标页面暂停。

### 日志管理

日志要按任务和运行批次查询。不要只把日志写在服务器文件里。

日志表：

```text
crawl_logs
  id
  run_id
  task_id
  level
  message
  context_json
  created_at
```

`context_json` 可以保存 URL、状态码、错误类型、重试次数等。

### 失败任务管理

失败任务不能只打印。要保存下来，支持重跑。

```text
failed_tasks
  id
  run_id
  task_id
  url
  error_type
  error_message
  retry_count
  status
  created_at
  updated_at
```

状态：

```text
pending_retry
retrying
resolved
ignored
dead
```

### 数据预览

平台需要让负责人快速查看样本：

- 最近采集了哪些字段。
- 字段是否为空。
- 是否乱码。
- 是否重复。
- 是否明显错位。

任务成功不等于数据正确。数据预览是发现解析错误的第一道窗口。

### 审计管理

审计记录所有关键操作。

```text
audit_logs
  id
  actor
  action
  resource_type
  resource_id
  before_json
  after_json
  created_at
```

例如：

- 修改任务并发。
- 暂停任务。
- 导出数据。
- 修改密钥引用。
- 重跑失败任务。

## 平台 MVP 应该先做什么

一个最小可用平台不需要一开始就很大。建议优先做：

1. 任务列表。
2. 任务详情。
3. 创建和编辑任务配置。
4. 手动启动任务。
5. 暂停任务。
6. 查看运行批次。
7. 查看运行日志。
8. 查看失败任务。
9. 重跑失败任务。
10. 数据样本预览。
11. 操作审计。

不要一开始就做复杂拖拽编排、低代码配置、权限工作流、可视化大屏。先把最基本的“看得见、管得住、能重跑”做稳。

## API 草案

```text
GET    /tasks
POST   /tasks
GET    /tasks/{task_id}
PATCH  /tasks/{task_id}
POST   /tasks/{task_id}/run
POST   /tasks/{task_id}/pause
POST   /tasks/{task_id}/resume

GET    /runs?task_id=...
GET    /runs/{run_id}
GET    /runs/{run_id}/logs
GET    /runs/{run_id}/failed-tasks

POST   /failed-tasks/{id}/retry
POST   /failed-tasks/{id}/ignore

GET    /tasks/{task_id}/items/preview
GET    /audit-logs?resource_type=task&resource_id=...
```

这些接口已经能支撑一个基础平台。

## 简化任务执行流程

```text
用户点击运行
  -> 创建 crawl_run
  -> 写入队列
  -> worker 领取任务
  -> 更新 run 状态为 running
  -> 执行采集
  -> 写日志和指标
  -> 保存成功数据
  -> 保存失败任务
  -> 更新 run 状态
```

这个流程里最重要的是状态更新。状态不清楚，平台就会出现“页面显示运行中，但实际已经挂了”的问题。

## 常见错误

### 错误一：平台只做启动按钮

只会启动任务的平台不完整。暂停、重跑、日志、失败任务和审计同样重要。

### 错误二：配置没有版本

配置被改后，旧运行批次就难以复盘。至少要在 `crawl_runs` 里保存当次配置快照。

### 错误三：没有 owner

每个任务都必须有负责人。没人负责的任务会变成系统债务。

### 错误四：失败任务不可重跑

失败任务如果只能全量重跑，会浪费资源，也容易造成重复数据。

### 错误五：没有数据质量入口

任务状态成功，但字段可能全空。平台必须能看数据样本和质量指标。

## 调试方法

平台排障要沿链路看：

```text
任务配置
  -> 调度触发
  -> 队列入队
  -> worker 执行
  -> 请求结果
  -> 解析结果
  -> 存储结果
  -> 指标和日志
```

每一步都要有状态和日志。缺哪一步，排查就会断。

## 工程化扩展

### 技术选型

MVP 可以使用：

- FastAPI：后端 API。
- PostgreSQL：任务元数据。
- Redis：队列、锁、状态缓存。
- Celery / Dramatiq / RQ：后台任务。
- React / Vue：管理前端。
- Docker Compose：本地开发环境。

### 插件化 Spider

平台可以把不同采集器注册为插件：

```text
spiders/
  product_spider.py
  news_spider.py
  review_spider.py
```

任务配置指定使用哪个 Spider。

### 规则审批

高风险操作可以要求审批：

- 新增目标域名。
- 提高并发。
- 开启代理。
- 导出敏感数据。
- 修改生产密钥。

## 安全与合规注意

平台化会集中能力，也会集中风险。必须有：

- 权限控制。
- 审计日志。
- 密钥管理。
- 数据脱敏。
- 任务限速。
- 停止开关。
- 合规审批。

采集平台不是“让所有人都能更方便地抓数据”，而是“让授权范围内的数据获取更可控”。

## 本章小结

爬虫平台的价值在于让任务可见、可控、可审计、可维护。MVP 先做好任务管理、运行批次、日志、失败任务、数据预览和审计，就已经能解决大量真实问题。

平台化不是为了炫技，而是为了团队长期协作。
