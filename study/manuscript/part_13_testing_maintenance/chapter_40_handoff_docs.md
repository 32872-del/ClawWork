# 第 40 章：代码规范与交接文档
## 本章在主流程中的位置

本章是第 1 章流水线的收束：一个采集系统要能交给别人继续运行。前面所有请求、解析、存储、队列、监控、配置和测试，如果没有文档和规范，都会变成只有作者懂的隐性知识。

本章承接全书所有工程能力，目标是把代码、数据、运行方式、风险边界和维护经验交接出去。到这里，爬虫才真正从个人脚本变成团队资产。

## 背景介绍

一个爬虫项目不是写完就结束。它会被同事运行，会被业务方依赖，会在几个月后因为页面变化而维护，会在数据异常时被追溯来源。

如果没有文档，未来维护者只能靠猜：

- 怎么启动？
- 配置在哪里？
- 密钥从哪里拿？
- 数据写到哪张表？
- 失败任务怎么重跑？
- 如何暂停？
- 哪些字段是核心字段？
- 哪些目标是授权范围？
- 出问题找谁？

交接文档不是形式主义，而是让别人能接住系统。企业级代码不仅要能跑，还要能被理解、被排查、被安全地停下。

本章是全书正文章节的收束。前面讲的是怎么开发爬虫，这一章讲怎么把爬虫交付成工程资产。

## 本章目标

学完本章后，你应该能做到：

1. 写清项目 README。
2. 编写运行手册。
3. 编写字段字典。
4. 编写故障排查手册。
5. 记录合规边界和授权说明。
6. 制作交接清单。
7. 让新同事能按文档运行和维护项目。

## README 应该包含什么

README 是项目入口。一个合格 README 至少回答：

- 这个项目做什么？
- 为什么存在？
- 采集范围是什么？
- 技术栈是什么？
- 如何安装？
- 如何配置？
- 如何运行？
- 如何测试？
- 输出在哪里？
- 出问题找谁？

模板：

```markdown
# product-crawler

采集授权商品列表和详情数据，用于内部价格分析。

## 采集范围

- 目标：授权商品列表和详情页
- 频率：每天 02:00
- 输出：PostgreSQL `products` 表

## 快速启动

```bash
python -m venv .venv
pip install -r requirements.txt
python -m product_crawler.main
```

## 测试

```bash
pytest
```

## 负责人

- Owner：data-team
- 告警群：crawler-alerts
```

README 不需要写成长篇论文，但必须让新人能跑起来。

## 运行手册

运行手册回答“日常怎么操作”。

示例：

```text
启动任务：
  python -m crawler run --task product_daily

暂停任务：
  python -m crawler pause --task product_daily

重跑失败：
  python -m crawler retry --task product_daily --run-id 1001

查看日志：
  logs/product_daily/{run_id}.log

查看数据：
  select * from products order by crawled_at desc limit 20;
```

如果是平台项目，运行手册应写页面路径和操作步骤；如果是 CLI 项目，写命令。

## 字段字典

字段字典说明数据含义。没有字段字典，使用数据的人会猜，迟早出错。

| 字段 | 类型 | 说明 | 示例 | 是否必填 |
| --- | --- | --- | --- | --- |
| product_id | string | 商品 ID | P1001 | 是 |
| title | string | 商品标题 | Python 课程 | 是 |
| price | number | 当前价格 | 99.0 | 是 |
| stock | string | 库存状态 | 有货 | 否 |
| crawled_at | datetime | 采集时间 | 2026-06-01T12:00:00 | 是 |

字段字典还应说明：

- 字段来源。
- 清洗规则。
- 空值含义。
- 更新频率。
- 唯一键。

## 故障排查手册

故障排查手册要具体，不要只写“检查网络”。

示例：数据量为 0。

```text
现象：
  任务运行成功，但新增数据量为 0。

可能原因：
  1. 目标页面返回空列表。
  2. 登录态过期。
  3. 解析规则失效。
  4. 数据被唯一键去重。
  5. 上游接口返回异常。

排查步骤：
  1. 查看 crawl_runs 中本次运行状态。
  2. 查看请求状态码分布。
  3. 打开失败样本或最新响应样本。
  4. 用解析器离线测试样本。
  5. 查看数据库 upsert 统计。
  6. 小流量重跑 10 条。
```

常见故障至少包括：

- 请求失败。
- 解析失败。
- 字段为空。
- 入库失败。
- 数据重复。
- 触发 429。
- 触发验证码。
- 队列积压。

## 合规说明

采集项目应写清：

- 数据来源。
- 授权依据。
- 采集范围。
- 采集频率。
- 数据用途。
- 数据保存期限。
- 数据访问权限。
- 停止机制。
- 联系人。

示例：

```text
数据来源：合作方授权 API
授权依据：合同编号 DATA-2026-001
采集范围：商品基础信息，不采集用户评论和个人信息
频率：每天一次
保存期限：180 天
停止方式：平台中暂停 task_id=product_daily
```

合规说明不是装饰，它能在项目被审计、交接或复盘时保护团队。

## 代码规范

### 分层清晰

建议分层：

```text
client.py     请求
parser.py     解析
cleaner.py    清洗
storage.py    存储
main.py       编排
config.py     配置
```

不要把请求、解析、清洗、入库都写在一个函数里。

### 命名表达意图

好命名：

```python
parse_product_detail
clean_price
save_failed_task
```

差命名：

```python
do_it
handle
run2
```

### 错误分类

不要所有异常都叫 `Exception`。至少区分：

- RequestError。
- ParseError。
- ValidationError。
- StorageError。

### 日志带上下文

日志要包含：

- task_id。
- run_id。
- url。
- status_code。
- error_type。

并发和分布式环境下，没有上下文的日志很难排查。

## 交接清单

交接时逐项确认：

```text
代码仓库地址
部署位置
任务负责人
运行命令
配置位置
密钥获取方式
数据库表
日志位置
监控面板
告警规则
测试命令
常见故障
停止方式
数据字典
合规说明
补采方式
失败任务位置
```

不要只发一个仓库链接。真正的交接，是让对方能独立运行、暂停、排查和恢复。

## 新手验收

交接前，找一个没参与开发的人按文档运行项目。如果他卡住，就说明文档缺东西。

新手验收非常有效，因为开发者自己很容易默认很多背景知识。

验收问题：

- 能否创建虚拟环境？
- 能否安装依赖？
- 能否找到配置项？
- 能否跑测试？
- 能否启动任务？
- 能否看到输出？
- 能否知道如何暂停？

## 常见错误

### 错误一：只有代码没有说明

未来维护者不知道怎么跑，也不知道出了问题怎么停。

### 错误二：文档过期

文档和代码不一致，比没有文档更危险。变更时要同步更新。

### 错误三：没有停止方式

任务出问题时，必须知道怎么停。

### 错误四：字段含义靠口头传

口头说明会丢失。字段字典必须写下来。

### 错误五：文档里写真实密钥

文档可以写密钥获取流程，不能写明文密钥。

## 工程化扩展

### 文档纳入 CI

可以检查：

- README 是否存在。
- `.env.example` 是否存在。
- 测试是否通过。
- 是否出现疑似密钥。
- 字段字典是否更新。

### 自动生成文档

部分内容可以从代码生成：

- CLI 命令帮助。
- 配置项说明。
- 数据表结构。
- API 文档。

自动生成能减少文档过期。

### 变更记录

维护 `CHANGELOG.md`：

```text
2026-06-01
- parser v3 支持新价格结构
- 增加 price 字段完整率告警
- 修复重复入库问题
```

## 安全与合规注意

文档中不要包含：

- 真实账号密码。
- API Key。
- Cookie。
- Token。
- 敏感用户数据样本。

如果必须展示样本，要脱敏。

## 本章小结

代码能跑只是第一步。企业级交付还需要 README、运行手册、字段字典、故障排查手册、合规说明和交接清单。

好的文档不是漂亮，而是让别人能接住系统。能运行、能暂停、能排查、能恢复、能审计，才是真正的交付。

## 课后练习
