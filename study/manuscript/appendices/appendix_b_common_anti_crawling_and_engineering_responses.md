# 附录 B：常见反爬现象与工程处理思路

本附录不是“绕过手册”，而是排障手册。真实企业项目里，采集系统要先回答三个问题：有没有授权，采集方式是否合规，系统是否足够克制。很多所谓“反爬问题”，最后排查下来其实是参数错了、登录态过期、页面改版、并发过高、字段解析脆弱，或者没有遵守对方提供的数据接口规范。

本附录的目标，是帮助你把模糊现象拆成可以验证的工程问题。

## 1. 排障总原则

遇到异常时，不要先加并发，不要先换出口，不要先堆浏览器实例。先保存样本、降低扰动、复现问题、确认授权边界。

推荐顺序：

1. 暂停或降低相关任务频率。
2. 保存失败请求和响应样本。
3. 对比同一 URL 在浏览器、脚本、不同账号下的表现。
4. 检查是否有公开 API、合作 API、导出功能或数据授权通道。
5. 区分技术错误、权限错误、频率错误、业务风控和页面改版。
6. 给出最小改动方案，而不是扩大系统扰动。

一个成熟采集系统最重要的能力不是“硬冲”，而是知道什么时候应该慢下来。

## 2. 现象：403 Forbidden

### 常见原因

`403` 可能来自权限不足、登录态不完整、CSRF Token 缺失、访问入口不对、频率过高、账号角色变化、地理或组织权限限制，也可能来自安全网关的规则判断。

### 合理处理

先确认采集对象是否在授权范围内。如果是内部系统或合作系统，优先查权限配置和接口文档。然后对比浏览器请求与脚本请求，重点看：

- URL 是否完全一致。
- 请求方法是否一致。
- 必要参数是否缺失。
- Cookie 是否完整且未过期。
- 是否缺少 CSRF Token。
- 是否直接访问了需要前置步骤的接口。
- 频率是否超过约定。

### 常见误区

新手常把 `403` 当成“只要伪装请求头就能解决”。实际上，请求头只是上下文的一部分。很多 `403` 是权限和业务规则问题，不是技术伪装问题。盲目修改请求头会让日志更难分析。

## 3. 现象：429 Too Many Requests

### 常见原因

`429` 是最直接的限速信号。可能按 IP、账号、接口、组织、Token、User-Agent、会话、时间窗口进行限制。

### 合理处理

尊重 `Retry-After`，并在调度层做限速，而不是在某个函数里随手 `sleep`。

工程做法：

- 为每个域名配置最大 QPS。
- 为敏感接口配置更低频率。
- 对账号、Token、出口分别记录请求量。
- 遇到 `429` 进入退避队列。
- 把连续 `429` 作为告警指标。

### 判断是否修复

不是“再次请求成功一次”就算修复，而是限速事件在稳定运行中明显下降，任务吞吐仍符合业务目标，并且对方系统没有出现异常压力。

## 4. 现象：返回 200，但数据为空

### 常见原因

这类问题最容易迷惑新人。状态码是 `200`，但是列表为空、字段缺失、页数为 0 或者返回了一个很短的 HTML。

常见原因包括：

- 参数缺失或默认值不同。
- 时间范围不对。
- 页码从 0 开始而不是从 1 开始。
- 接口需要登录态，但未登录时仍返回空数据。
- 数据由前端二次请求加载，HTML 里本来就没有。
- 命中了缓存或地区差异。
- 权限不足时业务层返回空列表。

### 合理处理

把“数据为空”当成一种独立异常，而不是成功。给采集器增加数据质量校验：

```python
def validate_items(payload):
    if not isinstance(payload, dict):
        return False, "响应不是对象"
    if "items" not in payload:
        return False, "缺少 items 字段"
    if payload.get("total", 0) > 0 and not payload["items"]:
        return False, "total 大于 0 但 items 为空"
    return True, "ok"
```

真实项目里，可以给每个接口定义最小字段集合和异常样本保存规则。

## 5. 现象：响应变成登录页

### 常见原因

登录态过期、Cookie 没有持久化、Token 刷新失败、账号被要求二次验证、访问了跨域子站、会话绑定了特定环境。

### 合理处理

不要把登录页当目标页面解析。解析前先判断页面类型：

- 标题是否包含登录相关词。
- URL 是否跳转到 `/login`、`/signin`、`/auth`。
- 页面是否出现用户名、密码输入框。
- JSON 是否包含 `unauthorized`、`login_required` 等字段。

如果是授权采集系统，登录态应有明确的刷新流程、过期告警和人工介入机制。不要在代码里硬编码个人账号密码。

## 6. 现象：验证码出现

### 常见原因

验证码通常是风险升高后的人工确认机制，也可能出现在登录、找回密码、敏感查询、批量访问、异常环境变化时。

### 合理处理

合规处理方式包括：

- 暂停自动任务，避免继续触发风险。
- 记录出现验证码前后的请求量和账号状态。
- 确认是否应改用官方 API、合作接口或数据导出。
- 在内部授权系统里，设计人工审核或人工确认流程。
- 对自建靶场，可以用于理解风控触发条件和用户体验。

本教程不建议把第三方验证码当作自动化对抗目标。验证码的存在往往意味着系统正在要求人工确认，继续自动化可能越过业务边界。

## 7. 现象：页面结构突然变化

### 常见原因

前端改版、AB 实验、地区差异、灰度发布、移动端/桌面端模板不同、登录态不同导致页面结构不同。

### 合理处理

工程上要保存 HTML 样本和解析失败样本，并写解析器测试。不要只在生产环境里临时改 CSS 选择器。

排查步骤：

1. 找出失败样本。
2. 和最近一次成功样本做对比。
3. 判断是字段改名、节点移动、接口变化还是页面类型变化。
4. 修改解析器。
5. 回放历史样本，避免修一个坏一个。

## 8. 现象：浏览器能打开，requests 抓不到

### 常见原因

浏览器不仅发一个 HTTP 请求，它还会执行 JavaScript、维护 Cookie、加载接口、携带复杂上下文。`requests` 抓不到，可能是因为：

- 数据由 XHR/fetch 接口返回。
- 页面需要执行 JavaScript 才生成参数。
- 接口依赖 Cookie、Token 或 CSRF。
- 返回内容经过压缩或编码。
- 浏览器走了重定向链路。

### 合理处理

优先从 Network 面板找真实数据接口。如果接口清晰、授权明确、参数可解释，优先走接口。如果数据确实只能通过页面渲染得到，再考虑 Playwright 等浏览器自动化。

判断路线：

- 接口直接返回结构化 JSON：优先接口。
- HTML 包含完整数据：优先 requests + 解析器。
- 必须交互后渲染：考虑浏览器自动化。
- 参数生成复杂但业务授权明确：做可维护的参数分析，不做黑盒堆砌。

## 9. 现象：同一代码有时成功有时失败

### 常见原因

偶发问题通常和时间、并发、网络、缓存、灰度、限流、任务顺序有关。它比稳定失败更难查，因为你需要找到触发条件。

### 合理处理

增加结构化日志，至少记录：

- task_id
- url
- status_code
- retry_count
- account_id
- proxy_id 或出口标识
- elapsed_ms
- response_size
- parser_version
- error_type

只要日志足够稳定，偶发问题会慢慢显形。

## 10. 现象：入库重复或数据覆盖

### 常见原因

这不是反爬，但在采集系统里非常常见。原因包括唯一键设计错误、分页重复、断点续爬重复、增量条件不严谨、重试导致重复写入。

### 合理处理

使用业务唯一键和幂等写入：

- 商品：平台 + 商品 ID。
- 文章：站点 + 文章 ID 或规范化 URL。
- 评论：平台 + 评论 ID。
- 价格快照：商品 ID + 采集时间窗口。

数据库层加唯一索引，代码层做 upsert。不要只靠“我觉得不会重复”。

## 11. 快速诊断表

| 现象 | 优先检查 | 不建议立刻做 | 合理动作 |
| --- | --- | --- | --- |
| 403 | 授权、登录态、权限、CSRF、入口路径 | 盲目加并发 | 保存样本，确认权限和规则 |
| 429 | 频率、Retry-After、账号/接口限额 | 继续压测 | 降频、退避、调度限速 |
| 200 空数据 | 参数、页码、权限、页面类型 | 当作成功入库 | 数据质量校验 |
| 登录页 | Cookie、Token、跳转链路 | 解析登录页 | 刷新授权或人工介入 |
| 验证码 | 风险触发、账号状态、频率 | 自动化对抗第三方验证码 | 暂停、审计、改用正式通道 |
| 结构变化 | 样本 diff、灰度、AB 实验 | 临时乱改选择器 | 回放测试后修解析器 |
| 偶发失败 | 日志维度、时间窗口、出口 | 猜原因 | 增加结构化日志 |
| 重复入库 | 唯一键、upsert、断点逻辑 | 手动删数据 | 幂等写入 |

## 12. 自建靶场建议

学习风控和反爬现象时，最适合使用自建靶场。你可以写一个本地服务，模拟以下规则：

- 每分钟超过 30 次返回 `429`。
- 未登录访问返回 `401`。
- 缺少 CSRF Token 返回 `403`。
- 随机 5% 返回 `500`。
- HTML 每次发布切换一个 class 名。
- 连续失败 3 次返回验证码提示页。

这样做的好处是边界清晰、可以重复实验、不会影响第三方系统。你学到的是排障方法，而不是冒险操作。
