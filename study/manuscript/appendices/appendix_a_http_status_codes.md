# 附录 A：HTTP 状态码速查与爬虫排障手册

HTTP 状态码是服务器给客户端的一句“简短答复”。它不会告诉你全部真相，但会告诉你第一步应该往哪里查。新手最容易犯的错误，是看到 `403` 就觉得“被反爬了”，看到 `500` 就觉得“网站坏了”，看到 `200` 就觉得“一定成功了”。真实项目里，状态码只是门牌号，不是屋里的完整地图。

做爬虫排障时，建议永远同时看四样东西：

- 状态码：请求在协议层面发生了什么。
- 响应头：服务器补充了哪些规则、缓存、跳转、限速、认证信息。
- 响应体：页面、JSON、错误提示、空数据、验证码页、登录页。
- 请求上下文：URL、参数、请求头、Cookie、登录态、频率、代理出口、任务批次。

如果只看状态码，就像医生只看体温，不问病史、不听心肺、不验血，容易误判。

## 1. 2xx：请求被服务器接受并处理

### 200 OK

`200` 表示请求成功返回，但它不等于“数据正确”。很多网站在异常时也会返回 `200`，只是在响应体里放一个错误页面、登录页、空列表或者风控提示。

在爬虫里遇到 `200`，还要继续验证：

- 页面标题是不是目标页面，而不是登录页。
- JSON 里是否存在业务字段，比如 `items`、`data`、`total`。
- 数据量是否合理，比如本来每页 20 条，现在突然 0 条。
- 响应体长度是否异常，比如以前 200KB，现在只有 2KB。
- 是否出现“请登录”“访问异常”“验证”“风险”等提示文本。

示例判断：

```python
import requests

url = "https://example.com/api/items"
resp = requests.get(url, timeout=10)

print(resp.status_code)
print(resp.headers.get("content-type"))
print(resp.text[:200])

if resp.status_code == 200:
    data = resp.json()
    if "items" not in data:
        raise RuntimeError("状态码是 200，但响应结构不是预期数据")
```

真实项目里，建议给每个采集器定义“成功判定函数”，不要只用 `status_code == 200` 判断成功。

### 201 Created

`201` 常见于创建资源，例如提交表单、创建任务、上传文件。普通只读爬虫不应该频繁遇到 `201`。如果你的采集脚本意外触发了 `201`，要立刻确认是否误调用了写接口。

排查重点：

- 请求方法是不是误用了 `POST`、`PUT`。
- 是否向接口提交了非预期数据。
- 是否违反了“只读采集”的边界。

### 202 Accepted

`202` 表示服务器收到了请求，但处理可能还没完成。它常见于异步任务接口，例如“提交导出任务后返回任务 ID”。采集这类接口时，不要以为第一次响应就能拿到结果，而是要按照官方或授权系统约定去轮询任务状态。

典型流程：

1. 提交任务，得到 `task_id`。
2. 定时查询任务状态。
3. 状态为 `done` 后下载结果。
4. 状态为 `failed` 时记录原因并停止重试。

### 204 No Content

`204` 表示请求成功，但没有响应体。它常见于删除、更新、心跳类接口。爬虫如果期待拿 JSON，却收到了 `204`，说明你可能请求错了接口，或者业务上确实没有数据。

不要对 `204` 调用 `resp.json()`，否则会报 JSON 解析错误。

## 2. 3xx：重定向，服务器让你去另一个地址

### 301 Moved Permanently

`301` 是永久重定向，常见于：

- `http` 跳到 `https`。
- 不带斜杠的 URL 跳到带斜杠版本。
- 旧域名迁移到新域名。
- 移动端、国际化、地区站点跳转。

爬虫处理 `301` 时要关注最终 URL。如果最终 URL 不是目标站点，而是登录页、错误页或地区选择页，就要检查 Cookie、请求头和访问入口。

### 302 Found

`302` 是临时重定向，在登录、权限、风控和活动页面里很常见。比如你访问一个详情页，服务器发现你没登录，于是把你跳到 `/login`。

调试方法：

```python
import requests

resp = requests.get("https://example.com/member/orders", allow_redirects=False)
print(resp.status_code)
print(resp.headers.get("location"))
```

把 `allow_redirects=False` 打开，可以看到服务器真正让你跳去哪里。很多“明明请求成功但拿不到数据”的问题，本质是中途跳转了。

### 304 Not Modified

`304` 表示资源未变化，可以使用缓存。它通常和请求头里的 `If-None-Match`、`If-Modified-Since` 有关。

对爬虫来说，`304` 有两种意义：

- 如果你主动做缓存，这是好事，可以减少重复下载。
- 如果你不理解缓存头，却总拿不到正文，就要检查是否带了浏览器复制来的条件请求头。

新手从浏览器复制请求头时，建议先去掉这些头：

- `If-None-Match`
- `If-Modified-Since`
- `Cache-Control`
- `Pragma`

## 3. 4xx：客户端请求有问题，或没有被允许

### 400 Bad Request

`400` 表示请求格式或参数不符合服务器预期。常见原因：

- 参数缺失。
- 参数类型错误。
- 时间戳格式错误。
- JSON 体不合法。
- URL 编码错误。
- 签名字段不匹配。

排查顺序：

1. 对比浏览器里的真实请求。
2. 检查 query 参数是否完整。
3. 检查 `Content-Type` 是否正确。
4. 检查中文、空格、特殊符号是否正确编码。
5. 检查请求体是表单、JSON 还是 multipart。

### 401 Unauthorized

`401` 通常表示未认证，也就是服务器不知道“你是谁”。它常见于需要登录态、Token、API Key 的接口。

排查重点：

- Cookie 是否过期。
- Authorization 头是否缺失。
- Token 是否需要刷新。
- 账号是否仍有权限。
- 本地时间是否错误，导致签名过期。

真实项目里，不要把账号密码、Token 写死在代码里。应使用环境变量、密钥管理服务或受控配置系统，并记录授权来源和使用范围。

### 403 Forbidden

`403` 表示服务器理解你的请求，但拒绝执行。它可能是权限问题，也可能是访问方式不符合规则，还可能是业务风控拦截。不要一看到 `403` 就盲目提高并发或更换出口，这通常会让情况更糟。

合规排查顺序：

1. 确认采集范围是否被授权。
2. 确认账号、角色、组织权限是否允许访问该资源。
3. 检查 URL 是否只能从特定入口访问。
4. 检查是否缺少必要请求头或 CSRF Token。
5. 检查频率是否超过对方公开或约定限制。
6. 检查响应体是否给出明确说明。
7. 必要时暂停任务，联系数据提供方或系统负责人。

### 404 Not Found

`404` 表示资源不存在，但在爬虫里它不一定是错误。比如采集商品详情时，商品下架后返回 `404` 是正常业务状态。

建议把 `404` 分成两类：

- 预期内 `404`：资源删除、下架、过期，记录状态即可。
- 异常 `404`：URL 拼接错误、路由规则变化、ID 生成错误，需要修复。

### 408 Request Timeout

`408` 表示服务器等待请求超时。它和客户端自己设置的 `timeout` 不完全一样。遇到它时，可以降低并发、缩短请求体、检查网络质量，并为请求设置合理重试。

### 409 Conflict

`409` 表示资源冲突。采集场景里常见于写入、更新、任务提交接口。如果只是读数据，很少遇到。入库时的唯一键冲突不一定会表现为 HTTP `409`，也可能是数据库异常。

### 410 Gone

`410` 表示资源曾经存在，但现在明确不存在。它比 `404` 更“确定”。如果站点使用得规范，可以把 `410` 作为删除状态写入数据库，避免反复请求。

### 413 Payload Too Large

`413` 表示请求体太大。常见于上传文件、批量提交 ID、一次性查询太多条件。解决方式不是硬重试，而是拆批。

### 415 Unsupported Media Type

`415` 表示请求体类型不支持。比如接口期待 JSON，但你传了表单；或者期待表单，但你传了 JSON。

检查：

- `Content-Type: application/json`
- `Content-Type: application/x-www-form-urlencoded`
- `Content-Type: multipart/form-data`

### 422 Unprocessable Entity

`422` 常见于后端校验失败。请求格式是对的，但业务字段不合法，例如日期范围错误、枚举值错误、页码超过限制。

### 429 Too Many Requests

`429` 表示请求过多，是爬虫最应该尊重的信号之一。它经常伴随 `Retry-After` 响应头，告诉你多久后再试。

正确处理方式：

```python
import time
import requests

resp = requests.get("https://example.com/api/items", timeout=10)

if resp.status_code == 429:
    retry_after = resp.headers.get("Retry-After")
    wait_seconds = int(retry_after) if retry_after and retry_after.isdigit() else 60
    print(f"被限速，等待 {wait_seconds} 秒后再试")
    time.sleep(wait_seconds)
```

工程上要做得更完整：

- 全局限速，而不是单个函数里 sleep。
- 按域名、接口、账号、出口分别限速。
- 指数退避，避免故障时形成请求风暴。
- 记录限速次数，作为调度和容量评估依据。

## 4. 5xx：服务器端或链路上的问题

### 500 Internal Server Error

`500` 表示服务端内部错误。采集器不应该因为少量 `500` 立刻失败，但也不应该无限重试。

建议：

- 对幂等 GET 请求做有限重试。
- 对写操作谨慎重试，避免重复提交。
- 记录响应体摘要、请求参数、时间和 trace id。
- 如果是内部授权系统，及时把样本交给服务端同事排查。

### 502 Bad Gateway

`502` 常见于网关、反向代理、上游服务异常。它不一定是目标业务服务的问题，也可能是 CDN、负载均衡、代理链路异常。

排查时要看：

- 是否只在某个出口出现。
- 是否只在某个地区出现。
- 是否集中在某个时间段。
- 是否所有接口都失败，还是单个接口失败。

### 503 Service Unavailable

`503` 表示服务暂时不可用，常见于维护、过载、限流、熔断。遇到 `503` 要降频和退避，不要继续加压。

### 504 Gateway Timeout

`504` 表示网关等待上游超时。它常见于查询太重、分页太深、服务端慢查询、网络链路不稳定。

处理思路：

- 缩小查询时间范围。
- 降低每页数量。
- 避免深分页，改用游标或增量字段。
- 加长客户端超时时间前，先确认服务器是否真的支持长查询。

## 5. 状态码与爬虫动作对照表

| 状态码 | 常见含义 | 建议动作 | 是否重试 |
| --- | --- | --- | --- |
| 200 | 请求成功 | 校验响应结构和数据质量 | 视业务而定 |
| 201 | 创建成功 | 确认是否误调用写接口 | 通常不重试 |
| 204 | 成功但无正文 | 不要解析 JSON，检查接口预期 | 不重试 |
| 301/302 | 重定向 | 查看 Location 和最终页面 | 通常不重试 |
| 304 | 缓存未变 | 检查条件请求头或使用缓存 | 不重试 |
| 400 | 参数错误 | 对比请求参数和编码 | 不重试 |
| 401 | 未认证 | 刷新登录态或 Token | 修复后重试 |
| 403 | 拒绝访问 | 检查授权、权限、频率和规则 | 不盲目重试 |
| 404 | 资源不存在 | 区分正常下架与 URL 错误 | 通常不重试 |
| 408 | 请求超时 | 降频、检查网络、有限重试 | 可重试 |
| 413 | 请求体过大 | 拆批 | 修复后重试 |
| 415 | 类型不支持 | 修正 Content-Type | 修复后重试 |
| 422 | 业务校验失败 | 修正字段 | 不重试 |
| 429 | 请求过多 | 按 Retry-After 退避 | 延迟重试 |
| 500 | 服务端错误 | 有限重试并记录样本 | 可重试 |
| 502/503/504 | 网关或服务不可用 | 降频、退避、观察趋势 | 可重试 |

## 6. 一个通用的响应分类函数

下面的示例不是完整框架，而是展示“如何把状态码翻译成采集动作”。真实项目可以把它放进重试模块、下载中间件或任务调度器里。

```python
def classify_response(resp):
    code = resp.status_code

    if code == 200:
        return "success_check_body"
    if code in {201, 204}:
        return "success_no_parse"
    if code in {301, 302, 303, 307, 308}:
        return "check_redirect"
    if code == 304:
        return "use_cache"
    if code in {400, 413, 415, 422}:
        return "fix_request"
    if code == 401:
        return "refresh_auth"
    if code == 403:
        return "check_permission_and_pause"
    if code in {404, 410}:
        return "mark_missing"
    if code == 429:
        return "rate_limited_backoff"
    if code in {408, 500, 502, 503, 504}:
        return "retry_with_backoff"

    return "unknown_inspect_manually"
```

这个函数最重要的不是代码本身，而是思路：不同状态码应该进入不同处理分支。把所有非 200 都当异常，把所有异常都塞进同一个重试队列，是很多新手爬虫失控的起点。

## 7. 排障记录模板

遇到状态码异常时，建议记录下面这些字段：

```text
时间：
任务名：
目标域名：
URL：
请求方法：
状态码：
最终 URL：
响应 Content-Type：
响应体前 500 字：
请求参数摘要：
登录态/账号标识：
出口/代理标识：
并发数：
最近一分钟请求量：
是否可复现：
初步判断：
下一步动作：
```

有了这些信息，问题会从“好像被拦了”变成“某账号在 10:30 后访问订单接口全部 401，Token 刷新失败”。后者才是工程师能处理的问题。

## 8. 课后练习

1. 写一个函数，输入状态码，输出建议动作。
2. 用 `requests` 请求一个不存在的 URL，观察 `404` 的响应体和响应头。
3. 构造一个本地 Flask/FastAPI 服务，分别返回 `200`、`401`、`429`、`500`，练习重试和限速逻辑。
4. 把第 9 章的重试代码改造为“按状态码分类处理”，不要对所有错误使用同一种重试策略。
