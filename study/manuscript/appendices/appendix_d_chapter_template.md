# 附录 D：章节写作模板与质量检查清单

本附录用于后续继续扩写、重写或审稿。它不是给读者看的“固定格式要求”，而是给作者和维护者用的写作脚手架。爬虫教程最容易写成两种极端：一种是流水账，把命令和代码堆在一起；另一种是大纲式短句，每个概念只写两句话。正式稿要避免这两种问题。

本书的章节目标是：让小白能跟着做，让真实开发者能迁移到项目里，让团队负责人能看出工程边界。

## 1. 每章必须回答的三个问题

写任何一章前，先问：

1. 这个主题解决什么真实问题？
2. 读者学完后能具体做什么？
3. 在真实项目里，哪里最容易踩坑？

如果这三个问题答不清楚，章节就容易变成术语介绍。

## 2. 推荐章节结构

### 本章在主流程中的位置

每章开头先说明它在第 1 章流水线里的位置。这个小节不需要很长，但要交代清楚：

- 本章对应哪一步。
- 它承接前面哪些章节。
- 它会把什么产出交给后面哪些章节。

这样做的好处是，读者不会把章节当成散落的知识点，而会一直知道自己在整条工程链路的哪一段。

示例：

```text
本章对应第 1 章流水线里的“保存数据”。前面章节已经能把字段解析出来，但数据只停留在内存或终端里，还不能算真正交付。

第 12 章会继续处理清洗和标准化，第 13 章会处理增量和断点。所以本章要解决的是：数据怎样稳定落地，并且能被后续系统继续使用。
```

### 背景介绍

说明为什么需要这个主题。不要一上来就贴代码。例如讲重试，先讲网络请求为什么会失败；讲数据库，先讲 CSV 在数据量变大后为什么不够；讲 Playwright，先讲浏览器到底帮我们做了什么。

好的背景应该让读者知道“我为什么要学这一章”。

### 本章目标

用具体动作描述目标：

- 能写一个带超时和重试的请求函数。
- 能把采集结果保存到 SQLite。
- 能识别动态页面的数据接口。
- 能用 Redis 队列分发任务。

不要写太空泛的目标，比如“掌握高级爬虫技术”。读者不知道什么叫掌握。

### 适用场景

告诉读者什么时候该用本章方法。比如：

- `requests` 适合接口清晰、页面静态、数据直接返回的场景。
- Playwright 适合必须执行浏览器交互才能得到数据的场景。
- Redis 队列适合任务量变大、需要多个 worker 协作的场景。

### 不适用场景

这部分很重要。新手常把刚学会的技术到处用，所以必须写清边界。

示例：

- 页面已经有清晰 JSON 接口时，不必优先使用浏览器自动化。
- 小规模一次性任务不一定需要分布式。
- 遇到验证码或风控拦截时，不应继续扩大自动化请求。
- 没有授权的数据源不应纳入采集任务。

### 核心概念

把术语讲成人话。可以用比喻，但比喻之后要落回技术事实。

示例：

队列可以比作取号机：任务先拿号排队，worker 按顺序处理。但真实系统里，队列还需要处理重复任务、失败重试、可见性超时和死信队列。

### 最小示例

给一个能独立理解的小例子。最小示例不追求完整工程，而是让读者看到核心动作。

要求：

- 代码尽量短。
- 变量命名清楚。
- 不依赖真实第三方敏感站点。
- 优先离线、本地或自建样例。
- 示例后必须解释每一段做什么。

### 完整开发过程

这一节是章节主体。要像带读者做项目一样写：

1. 建目录。
2. 写配置。
3. 写核心代码。
4. 运行。
5. 看输出。
6. 故意制造一个错误。
7. 展示如何排查。
8. 说明如何迁移到真实授权项目。

不要只给最终代码。真实学习发生在“为什么这么写”和“出错怎么办”里。

### 逐段解释

代码之后要解释，不要默认读者都懂。解释重点不是逐行翻译语法，而是说明设计原因：

- 为什么设置 timeout。
- 为什么不要无限重试。
- 为什么唯一键放在数据库层。
- 为什么日志要包含 task_id。
- 为什么选择接口而不是浏览器。

### 常见错误

每章至少列出 5 个常见错误，并写清后果。

示例：

- 错误：不设置超时。后果：一个请求卡住，整个任务停住。
- 错误：只用状态码判断成功。后果：登录页、验证码页、空数据被当作成功。
- 错误：没有唯一键。后果：重跑任务后数据重复。

### 调试方法

调试方法要具体到动作，不要只写“查看日志”。

例如：

- 打印最终 URL。
- 保存失败响应体前 500 字。
- 用浏览器 Network 对比请求参数。
- 把并发降到 1 复现问题。
- 用固定样本回放解析器。
- 检查数据库唯一索引是否生效。

### 工程化扩展

说明从教学示例到真实项目还差什么：

- 配置中心。
- 密钥管理。
- 任务队列。
- 监控告警。
- 样本回放测试。
- 权限和审计。
- 数据质量校验。

不要让读者误以为教学代码可以原封不动上生产。

### 安全与合规注意

涉及账号、登录、验证码、风控、代理、Cloudflare、指纹、动态参数时，必须写清边界：

- 只在授权系统、自建靶场、防御理解、合规采集和工程排障中展开。
- 不把第三方安全机制当作绕过目标。
- 记录授权来源、采集范围、频率限制和审计日志。
- 遇到风险拦截时优先暂停、降频、沟通或改用正式接口。

### 本章小结

小结不要重复目录。要提炼本章最重要的判断。

例如：

本章最重要的不是学会 `time.sleep()`，而是学会把失败分成不同类型：能重试的、需要修参数的、需要刷新授权的、应该暂停的。分类越清楚，采集系统越稳定。

### 课后练习

练习要能落地。每个练习最好有验收标准。

示例：

- 给请求函数增加超时和三次重试。
- 验收：连续访问一个会随机失败的本地接口，最终日志能看到重试次数。

## 3. 代码示例规范

代码要优先服务教学，不要炫技。

要求：

- 使用清楚的函数名和变量名。
- 不把多个概念塞进一个函数。
- 不依赖读者没有准备的外部服务。
- 对真实站点只描述迁移方法，不把第三方系统作为攻击或对抗对象。
- 示例可以简化，但必须说明简化了什么。
- 必须设置 timeout。
- 涉及文件路径时，使用相对项目目录的清晰路径。
- 涉及数据库时，说明表结构和唯一键。

## 4. 示例后的解释模板

每段关键代码后，可以按这个顺序解释：

```text
这段代码做了什么：
为什么要这样写：
如果不这样写会怎样：
真实项目里如何扩展：
```

例如讲请求函数：

```text
这段代码统一设置 timeout，避免请求无限等待。
真实网络一定会有抖动，如果没有 timeout，任务可能卡死在单个 URL 上。
生产环境还应该加重试、退避、状态码分类和失败样本保存。
```

## 5. 章节质量评分表

| 检查项 | 达标标准 |
| --- | --- |
| 主流程位置 | 开头说明本章对应第 1 章流水线哪一步，以及承前启后关系 |
| 背景 | 读者能理解为什么需要本章 |
| 目标 | 目标是具体动作，不是空泛口号 |
| 示例 | 至少一个离线或低风险可运行示例 |
| 解释 | 代码后有设计原因和错误后果 |
| 常见错误 | 至少 5 个，并说明影响 |
| 调试 | 给出可操作步骤 |
| 工程化 | 说明真实项目需要补哪些能力 |
| 合规 | 高风险主题有清晰边界 |
| 练习 | 有可验收任务 |
| 密度 | 不是大纲式短句，概念讲透 |

## 6. 审稿时重点看什么

审稿不要只看错别字，更要看读者能不能学会。

重点检查：

- 有没有直接从术语跳到代码。
- 有没有说明本章在第 1 章流水线中的位置。
- 有没有只写“是什么”，没写“为什么”和“怎么排障”。
- 有没有把教学代码包装成生产代码。
- 有没有缺少合规边界。
- 有没有示例无法运行或缺少依赖说明。
- 有没有章节之间重复但说法不一致。
- 有没有文件放错目录。
- 有没有编号断档。

## 7. 加厚薄章节的方法

如果某章太短，不要简单加废话。可以从这些方向扩展：

- 增加一个真实问题场景。
- 增加一个最小可运行示例。
- 增加一个“错误写法 vs 正确写法”对比。
- 增加排障流程。
- 增加工程化迁移说明。
- 增加数据表、配置文件或日志样例。
- 增加练习和验收标准。

例如一章只有“429 表示请求过多，应该限速”，可以加厚为：

- 为什么会出现 429。
- `Retry-After` 怎么读。
- 单函数 sleep 为什么不够。
- 如何按域名、接口、账号限速。
- 如何记录限速指标。
- 如何判断限速策略是否有效。

## 8. 文件组织规范

正式稿只放在：

```text
manuscript/
```

规划、审稿、路线放在：

```text
planning/
```

早期草稿放在：

```text
drafts/
```

不要把正式章节写到根目录，也不要在 `drafts/` 里继续扩正式稿。

章节命名使用：

```text
chapter_09_retry_rate_limit.md
```

综合项目命名使用：

```text
project_a_static_site_crawler.md
```

附录命名使用：

```text
appendix_a_http_status_codes.md
```

## 9. 每批写完后的验证清单

每次完成一批章节后，至少检查：

- 章节编号是否连续。
- 文件是否在正确目录。
- README 是否同步。
- 是否误写到根目录。
- 薄章节是否明显少于同类章节。
- 高风险主题是否保持授权、靶场、防御和合规语境。
- 示例代码变量是否完整。
- Markdown 标题层级是否清楚。

## 10. README 更新要求

README 不是摆设，它是项目导航。每次新增或扩写后，要同步：

- 当前正式稿范围。
- 新增文件列表。
- 当前缺口。
- 下一步建议。
- 写作标准是否变化。

如果 README 仍写着“项目 A-G 只是蓝图”，但实际项目已经扩成教程，后续维护者就会误判进度。
