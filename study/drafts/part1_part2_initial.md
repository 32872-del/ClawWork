# 企业级爬虫开发教程正文

## 第一篇：先建立正确直觉

### 第 1 章：爬虫开发的真实工作流

#### 1.1 背景介绍

很多人第一次接触爬虫时，会把它想成一件很轻的事：写几行代码，发一个请求，把网页内容打印出来，就算完成了。这个理解不算错，但只对了一小半。

真正做过项目的人会发现，爬虫更像一条流水线，而不是一个动作。它不是“拿一次数据”就结束，而是要长期、稳定、可维护地把数据拿回来。今天能跑，不代表明天还能跑；今天能抓到，不代表后天页面改了还能抓到；今天只抓一页，不代表一千页、一万页还能保持速度和质量。

所以，写爬虫最重要的第一步，不是急着敲代码，而是先把整个工作流想明白。你可以把它想成一个快递配送流程：

- 先知道仓库在哪里，也就是数据入口在哪里。
- 再知道怎么进门，也就是请求怎么发。
- 再知道怎么拆包，也就是解析怎么做。
- 再知道把东西放哪，也就是存储怎么做。
- 再知道如果路上出问题怎么办，也就是重试、限速、日志和监控。

只要这条链路清楚了，后面无论你用 `requests`、`httpx`、`Playwright` 还是 `Scrapy`，本质都还是在做同一件事。

#### 1.2 本章目标

学完这一章，你应该能回答下面几个问题：

1. 爬虫不是一个脚本，而是一条流程，这句话到底是什么意思。
2. 为什么“能抓一次”和“能稳定抓三个月”差别这么大。
3. 一个真实爬虫项目通常由哪些部分组成。
4. 为什么后面所有技术都要围绕“入口、请求、解析、存储、调度、监控”来展开。

#### 1.3 适用场景

这一章适合以下情况：

- 你刚开始接触爬虫，脑子里只有“发请求”这一个动作。
- 你写过一点脚本，但从没做过完整项目。
- 你想先建立整体认知，再去学具体技术。

#### 1.4 核心概念

一个完整爬虫项目，通常至少包含这些角色：

- 数据入口：列表页、详情页、接口、搜索页、文件下载地址。
- 请求层：负责把请求发出去，并拿到响应。
- 解析层：负责从 HTML、JSON、文本、文件里提取目标字段。
- 清洗层：负责把杂乱数据变成统一格式。
- 存储层：负责把结果放到文件、数据库或对象存储里。
- 调度层：负责决定哪些任务先做、哪些后做、失败后要不要重试。
- 去重层：负责避免同一条数据重复采集。
- 监控层：负责观察成功率、耗时、错误率和数据变化。

如果把它们压缩成一句话，那就是：

> 爬虫 = 找到数据 + 取回数据 + 处理数据 + 保存数据 + 盯住它别坏。

#### 1.5 类比说明

很多初学者一看这些模块名字就容易头大。其实你可以把它们想成一个小型工厂。

- 数据入口像原料仓库。
- 请求层像搬运工。
- 解析层像分拣台。
- 清洗层像质检员。
- 存储层像成品仓库。
- 调度层像车间主任。
- 监控层像值班室。

这个类比的重点是：爬虫不是“拿到内容就结束”，而是“把原始内容加工成能交付的结果”。

#### 1.6 最小认知图

```text
目标站点/接口
      ↓
发请求
      ↓
拿响应
      ↓
解析字段
      ↓
清洗标准化
      ↓
去重/校验
      ↓
保存到文件或数据库
      ↓
记录日志与监控
      ↓
失败任务重试或人工处理
```

#### 1.7 为什么“能跑一次”不等于“能上线”

新手常常在本地试一遍，打印出一段 HTML，就觉得项目差不多了。但真实环境里，问题往往从第二天才开始出现。

常见情况包括：

- 页面结构改了，解析器突然失效。
- 接口多了一个参数，返回结果变空。
- 登录态过期，后续请求全部失败。
- 网络抖动，导致一半任务超时。
- 数据重复写入，数据库里一堆脏数据。
- 某天并发太高，目标服务开始限流。

所以，一个成熟的爬虫项目不能只考虑“成功路径”，还要考虑“失败路径”。

#### 1.8 真实开发过程长什么样

一个企业里常见的开发顺序，大致是这样的：

1. 明确业务目标：要采哪些字段，多久采一次，结果给谁用。
2. 找到数据入口：页面、接口、文件、搜索结果页。
3. 验证采集方式：先用浏览器、抓包工具或接口调试确认入口能不能稳定拿到数据。
4. 写最小原型：先只抓一页，别急着上并发。
5. 设计数据结构：字段命名、类型、唯一键、存储格式。
6. 补上异常处理：超时、失败重试、空数据、编码问题。
7. 加入去重和断点续爬：避免每次都从头抓。
8. 加入日志和监控：方便排障和追踪。
9. 压测和扩展：看看在更多页数、更多任务下会不会炸。
10. 上线维护：页面变化后及时修。

你会发现，真正耗时间的，往往不是“写出第一版代码”，而是“让它长期不坏”。

#### 1.9 最常见的新手误区

##### 误区一：爬虫就是 requests

`requests` 只是最常见的一种工具，不是爬虫本身。它像锤子，不是房子。

##### 误区二：页面能打开就一定能抓

浏览器能打开，不代表代码能直接拿到同样内容。因为浏览器会执行 JavaScript，而普通请求默认不会。

##### 误区三：先追求技术炫技

新手很容易跳到“高级逆向”“浏览器指纹”“AST 混淆”这些话题，但真正企业里最值钱的，往往是稳定、准确、可维护。

##### 误区四：只关心成功率，不关心数据质量

爬到一万条数据，如果有三千条重复、两千条缺字段，那这批数据基本没法直接用。

#### 1.10 本章小结

这一章最重要的收获只有一句话：

> 爬虫不是“写一个请求”，而是“搭一条数据流水线”。

只要你把这个认知先立住，后面学任何技术都会更顺。因为你会知道每个工具在流水线里是干什么的，而不是见一个学一个。

#### 1.11 课后练习

1. 找一个你熟悉的网站，试着写出它的数据链路：入口、请求、解析、保存。
2. 想一想，如果这个网站明天页面改版，你的爬虫最可能坏在哪里。
3. 把“爬虫流程”用你自己的话重新讲一遍，最好能讲给一个没写过代码的人听。

### 第 2 章：网页、浏览器和服务器到底在做什么

#### 2.1 背景介绍

很多爬虫问题，本质上不是“不会写代码”，而是“不知道浏览器到底做了什么”。

比如：

- 你在浏览器里能看到内容，代码里却是空白。
- 你明明访问的是同一个 URL，返回结果却不一样。
- 你复制了请求头，还是拿不到数据。
- 页面一闪而过的数据，代码里怎么都抓不到。

这些问题的根源，大多都和浏览器、服务器、HTTP 之间的协作方式有关。

所以，在真正开始写爬虫之前，先搞懂“网页是怎么来的”非常重要。这个部分看起来像基础课，但其实是后面所有实战的地基。

#### 2.2 本章目标

学完这一章，你应该能理解：

1. 浏览器访问网页时，大概经历了哪些步骤。
2. HTML、JSON、DOM、接口分别是什么。
3. 为什么有些数据要去 Network 面板里找，而不是只看页面源码。
4. 什么时候适合用 `requests`，什么时候该考虑接口，什么时候才需要浏览器自动化。

#### 2.3 浏览器访问网页的流程

当你在浏览器里输入一个网址，背后大概会经历这些步骤：

1. 浏览器把 URL 解析成目标地址。
2. 通过 DNS 找到服务器。
3. 建立网络连接。
4. 发送 HTTP 请求。
5. 服务器返回 HTML、JSON 或其他资源。
6. 浏览器先拿到原始 HTML。
7. 浏览器再下载 CSS、JS、图片等资源。
8. 如果页面里有 JavaScript，浏览器还会继续执行脚本。
9. JavaScript 可能会再发接口请求，把更多数据补到页面里。
10. 最后你看到的是渲染完成后的页面。

这意味着，浏览器看到的“页面”，往往不是一份静态文件，而是“原始 HTML + 资源 + JavaScript 运行结果”的总和。

#### 2.4 HTML、DOM、JSON 分别是什么

##### HTML

HTML 是网页的骨架。它负责告诉浏览器：这里是标题、那里是列表、这里是按钮。

你可以把 HTML 理解成网页的“原始材料”，就像一栋房子的毛坯结构。

##### DOM

DOM 是浏览器把 HTML 读进来之后，在内存里形成的结构化表示。它更像“浏览器眼里的网页树”。

HTML 是文本，DOM 是结构。这个区别很重要。因为 JavaScript 可以动态修改 DOM，所以页面最终展示出来的内容，不一定和源代码里的 HTML 完全一样。

##### JSON

JSON 是一种结构化数据格式。它不像 HTML 那样主要负责展示，而是更像“数据包”。

如果说 HTML 是菜单，JSON 就更像厨房真正装菜的托盘。很多接口返回的内容就是 JSON，适合程序直接处理。

#### 2.5 为什么浏览器能看见，代码却拿不到

这是新手最常遇到的问题之一。

原因通常有这几种：

1. 数据根本不在初始 HTML 里，而是 JavaScript 后加载的。
2. 你抓到的是页面壳子，真正数据来自接口。
3. 页面需要登录态、Cookie 或 token。
4. 服务器根据请求头、频率、来源判断是否返回完整内容。
5. 页面内容依赖浏览器环境执行结果。

所以，看到页面空白时，不要急着怪代码。先判断数据到底是从哪来的。

#### 2.6 先看源码还是先看 Network

这两个地方都要看，但优先级不同。

- 如果是静态页面，先看网页源码，很多信息直接在 HTML 里。
- 如果是动态页面，先看 Network，因为真正的数据可能是接口返回的。

一个很好用的判断方法是：

- 页面打开就有完整内容，倾向于静态 HTML。
- 页面先空着，过一会儿内容才出现，倾向于 JS 渲染或接口加载。
- 页面内容和页面源码对不上，优先怀疑动态渲染。

#### 2.7 HTTP 是什么

HTTP 可以理解成浏览器和服务器之间的“对话规则”。

浏览器说：“我想要这个地址的数据。”
服务器说：“这是你要的内容。”

这种对话里面有几个常见部分：

- 请求方法：告诉服务器你要做什么。
- 请求头：告诉服务器你是谁、你想要什么格式。
- 请求参数：告诉服务器你具体要哪个资源。
- 响应状态码：告诉你这次请求成功了没有。
- 响应头：告诉你返回的内容类型、缓存策略等。
- 响应体：真正的数据内容。

#### 2.8 常见请求方法

最常见的是这四个：

- `GET`：获取数据。
- `POST`：提交数据。
- `PUT`：更新数据。
- `DELETE`：删除数据。

在爬虫里，最常见的是 `GET` 和 `POST`。但不要死记“GET 就是取，POST 就是发”。真实接口里，有些系统会把查询也做成 POST。判断方式还是要看页面和抓包结果，而不是只看名字。

#### 2.9 常见状态码

状态码就像服务器的反馈表情。

- `200`：成功。
- `301/302`：重定向，告诉你换个地方看。
- `400`：请求有问题，参数可能错了。
- `401`：没登录或认证失败。
- `403`：没权限或被拒绝。
- `404`：资源不存在。
- `429`：请求太多了。
- `500`：服务器内部出错。

这些状态码非常重要。很多时候，问题不是“程序没跑”，而是“服务器已经明确告诉你它不接受这次请求了”。

#### 2.10 请求头和响应头是什么

##### 请求头

请求头是你发给服务器的附加信息。常见的有：

- `User-Agent`
- `Accept`
- `Referer`
- `Cookie`
- `Accept-Language`

它们像你的“自我介绍”和“访问说明书”。

##### 响应头

响应头是服务器回给你的附加信息。常见的有：

- `Content-Type`
- `Set-Cookie`
- `Cache-Control`
- `Location`

它们告诉你：这份内容是什么格式，要不要缓存，要不要跳转，有没有给你新的 Cookie。

#### 2.11 `requests`、接口、浏览器自动化怎么选

这是后面实战里最重要的判断题之一。

##### 方案一：直接用 `requests`

适合：

- 页面是静态 HTML。
- 数据在接口里直接返回。
- 请求逻辑简单。

优点是轻、快、稳定、成本低。

##### 方案二：直接调用接口

适合：

- 页面是前端渲染，但接口清晰。
- 数据本来就是 JSON。
- 你不需要真的打开浏览器。

优点是比浏览器自动化更高效，维护也通常更简单。

##### 方案三：浏览器自动化

适合：

- 页面必须执行 JavaScript 才能看到数据。
- 页面交互复杂。
- 某些内容只有在真实浏览器环境里才会出现。

代价是慢、重、资源消耗大，维护成本也更高。

#### 2.12 一个很重要的判断标准

你可以问自己三个问题：

1. 数据是不是已经在 HTML 里？
2. 如果不在，接口是不是能直接拿到？
3. 如果接口也不好拿，才考虑浏览器自动化？

这套顺序非常实用，因为它基本符合“成本从低到高”的工程思路。

#### 2.13 最小示例：看懂一个简单请求

下面这段代码只是为了理解 HTTP 的基本动作。

```python
import requests

url = "https://example.com"
response = requests.get(url, timeout=10)

print("status:", response.status_code)
print("content-type:", response.headers.get("Content-Type"))
print(response.text[:300])
```

这段代码做了三件事：

1. 访问一个 URL。
2. 看服务器有没有成功返回。
3. 看响应头和响应内容是什么。

它非常简单，但意义很大。因为你后面所有复杂爬虫，本质上也是在重复这三件事，只不过会多一些登录、分页、解析、重试和存储。

#### 2.14 WebSocket、XHR、Fetch 是什么

这三个词经常出现在 Network 面板里。

- `XHR`：一种传统的异步请求方式。
- `Fetch`：更现代的请求接口。
- `WebSocket`：长连接，适合实时推送。

你现在不用一口气把它们全背下来，只需要知道：它们都可能是页面拿数据的通道。以后看到页面内容迟迟不在 HTML 里，就该去 Network 里找这些请求。

#### 2.15 本章最核心的结论

这一章你只要记住一句话：

> 浏览器看到的不一定等于源代码里写的，很多内容是“页面加载后才生成的”。

这句话会贯穿后面的所有实战。你以后遇到空白页、接口页、登录页、动态加载页，都可以先用这个思路排查。

#### 2.16 本章小结

这一章不是在教你具体工具，而是在帮你建立判断力。

如果你已经知道：

- 页面不是单纯的 HTML。
- 数据可能藏在接口里。
- 浏览器会执行 JavaScript。
- `requests` 不是万能的。

那你就已经比很多刚入门的人更接近真实开发了。

#### 2.17 课后练习

1. 打开一个普通网页，观察它的页面源码和浏览器里显示的内容是否一致。
2. 在 DevTools 的 Network 里找一个接口，看看它返回的是 HTML 还是 JSON。
3. 想一想，为什么某些页面需要先登录才能看到完整内容。
4. 试着用自己的话解释：HTML、DOM、JSON 三者的区别。

## 第二篇：从 `requests` 开始写第一个可用爬虫

### 第 3 章：环境搭建与第一个请求

#### 3.1 背景介绍

很多人学爬虫时，第一关不是技术，而是环境。

这件事看起来不起眼，但在真实项目里非常重要。因为一旦环境混乱，你今天写的代码能跑，明天换一台电脑就不一定能跑。团队协作时更麻烦，一个人缺包、一个人版本不一致、一个人 Python 版本过高，最后大家都在花时间修环境，而不是写业务。

所以，企业级开发里第一件事通常不是“直接写爬虫”，而是“先把环境搭好”。这就像盖房子前先打地基。地基不稳，后面写得再漂亮也没用。

#### 3.2 本章目标

学完这一章，你应该能：

1. 安装并使用 Python 虚拟环境。
2. 安装第三方库。
3. 写出第一段 `requests` 请求代码。
4. 看懂响应状态码、响应头和响应内容。
5. 明白为什么所有项目都应该尽早加上 `timeout`。

#### 3.3 为什么要用虚拟环境

虚拟环境可以理解成给每个项目单独准备一个小房间。

如果你把所有项目的依赖都装在同一个全局环境里，时间一长就会乱：

- A 项目需要某个版本的库。
- B 项目需要另一个版本。
- 你升级了一个库，另一个项目突然坏了。

虚拟环境的作用，就是把项目之间的依赖隔开，让每个项目都能有自己的“独立空间”。这在团队开发里尤其重要。

#### 3.4 推荐的项目准备步骤

1. 创建项目目录。
2. 建立虚拟环境。
3. 安装依赖库。
4. 写一个最小脚本。
5. 先确认请求能通，再考虑解析。

不要一上来就写上百行代码。先写最小可运行版本，能跑通以后再加功能。

#### 3.5 第一个请求

先看最简单的代码：

```python
import requests

url = "https://example.com"
response = requests.get(url, timeout=10)

print(response.status_code)
print(response.text[:500])
```

这段代码可以拆成三步理解：

1. `requests.get()`：向目标地址发一个 GET 请求。
2. `timeout=10`：最多等 10 秒，别无限卡住。
3. `response.text`：拿到返回的文本内容。

新手看到这段代码时，最重要的是不要把它背下来，而是知道每一行在做什么。

#### 3.6 为什么一定要加 `timeout`

很多初学者会忽略这个参数，觉得“反正等着呗”。但真实环境里，不加超时很危险。

如果网络抖动、服务器卡住、代理异常，程序可能一直挂着不动。这样会导致：

- 任务卡死。
- 队列堵住。
- 整个程序看起来像没反应。

超时就像给每次请求装一个闹钟。时间到了还没回来，就认为这次失败，交给重试或人工处理。

#### 3.7 状态码怎么看

`response.status_code` 是你判断请求有没有成功的第一眼信息。

比如：

- `200` 通常表示成功。
- `403` 说明服务器拒绝了你。
- `404` 说明地址可能不存在。
- `500` 说明服务端出错。

很多新手只会看“网页有没有打开”，但在程序里，状态码比肉眼更可靠。你要养成第一时间看状态码的习惯。

#### 3.8 响应头为什么也要看

响应头里经常藏着很有价值的信息，比如：

- `Content-Type`：返回的是 HTML 还是 JSON。
- `Set-Cookie`：服务器是不是给你发了新的 Cookie。
- `Location`：是不是发生了跳转。

这就像拆快递前先看外包装标签。虽然不是内容本身，但能帮你判断这包东西是什么、怎么处理。

#### 3.9 常见初学者问题

##### 问题一：请求成功了，但页面内容看起来很少

这可能是静态页面本来就少，也可能是动态内容还没加载。

##### 问题二：浏览器能看到内容，代码里没有

这通常说明数据不是直接放在 HTML 里，而是通过接口后加载的。

##### 问题三：返回乱码

这通常和编码有关。你不能只看眼前输出，要学会检查字符编码。

##### 问题四：一直超时

可能是网络问题、目标站点慢、代理有问题，或者目标本身就限制了访问。

#### 3.10 本章小练习

你可以先对一个公开测试站点做尝试，比如 `https://example.com` 或者你本地搭一个简单页面。目标不是抓数据，而是先完整看懂下面几件事：

1. 状态码是多少。
2. 响应头里有什么。
3. 返回文本前几百个字符长什么样。

#### 3.11 本章小结

这一章的重点不是“你已经会写爬虫了”，而是“你已经知道如何发出第一个稳定请求了”。

在企业开发里，这一步非常关键。因为后面不管是解析 HTML、调用接口，还是处理动态页面，底层都还是要先把这个请求发出去，并且确保它可控、可追踪、可调试。

### 第 4 章：请求头、参数和编码

#### 4.1 背景介绍

同样一个网址，浏览器能打开，代码却不一定能拿到一样的内容。很多时候，问题不在 URL 本身，而在你发出去的“说话方式”不对。

HTTP 请求不是简单地把地址丢出去就完事了，它还会带上很多附加信息。服务器会根据这些信息判断你是谁、你想要什么、你是不是一个正常访问者。

这也是为什么很多新手会遇到一个经典场景：明明复制了 URL，代码却返回 403，或者页面内容和浏览器不一致。

#### 4.2 本章目标

学完这一章，你应该能：

1. 理解请求头和请求参数的区别。
2. 会设置常见请求头。
3. 会通过 `params` 传递查询参数。
4. 明白编码问题为什么会导致乱码。
5. 先建立“浏览器请求”和“程序请求”差异的基本判断力。

#### 4.3 请求头像什么

你可以把请求头想成你去办事时递上的说明材料。

- `User-Agent` 告诉服务器：我是哪个浏览器。
- `Accept` 告诉服务器：我希望拿到什么格式。
- `Referer` 告诉服务器：我从哪里来的。
- `Cookie` 告诉服务器：我是谁，我有没有登录过。

这些东西不是装饰品。很多站点会根据它们做判断。

#### 4.4 Query 参数是什么

你在地址栏里看到的 `?page=1&size=20` 这类内容，就是查询参数。

它的作用很简单：告诉服务器你想要哪一页、多少条、哪个关键词、哪个排序方式。

比如：

```python
import requests

params = {
    "q": "python crawler",
    "page": 1,
}

response = requests.get("https://example.com/search", params=params, timeout=10)
print(response.url)
```

这里 `params` 的好处是，库会帮你把参数拼成正确的 URL，不用你手动拼接。

#### 4.5 为什么不要乱抄浏览器全部请求头

这是一个很常见的误区。

很多人喜欢把浏览器里看到的请求头一股脑复制出来，以为越全越好。其实不一定。

原因有三个：

1. 有些头是浏览器自动生成的，复制过去未必有意义。
2. 有些头之间要保持一致，乱改反而更怪。
3. 有些站点只关心少数几个关键头，不需要你全搬。

更稳妥的做法是：先从最必要的头开始，加最少的字段，逐步验证。

#### 4.6 编码是什么

编码问题，是新手最容易忽略但最常见的坑之一。

你可以把编码理解成“文字的翻译规则”。同样一串字节，如果用不同规则解释，显示出来的内容可能完全不同。

所以，当你看到乱码时，不要只盯着页面内容看，要先确认：

- 响应头里有没有说明编码。
- 代码库是不是自动识别错了。
- 页面原始内容是不是就是那个字符集。

#### 4.7 一个带请求头和参数的例子

```python
import requests

headers = {
    "User-Agent": "Mozilla/5.0",
    "Accept": "text/html,application/xhtml+xml,application/xml;q=0.9,*/*;q=0.8",
}

params = {
    "q": "python crawler",
    "page": 1,
}

response = requests.get(
    "https://example.com/search",
    headers=headers,
    params=params,
    timeout=10,
)

response.encoding = response.apparent_encoding
print(response.url)
print(response.text[:500])
```

这段代码可以学到几件事：

1. `headers` 用来模拟正常请求的基本信息。
2. `params` 用来传搜索词和页码。
3. `response.apparent_encoding` 可以帮助你先做编码判断。

#### 4.8 `Content-Type` 和 `Accept`

这两个字段很容易混。

- `Accept` 是你想要什么。
- `Content-Type` 是你实际发的是什么。

比如你去餐厅点餐：

- `Accept` 像“我想吃面食”。
- `Content-Type` 像“我端上来的是米饭还是面条”。

一个是期望，一个是结果。

#### 4.9 本章里你最该记住的事

不要把请求头当成装饰。它们是服务器判断请求的重要依据。

同时，也不要迷信“复制浏览器请求头”就一定能解决问题。真正要做的是理解每个字段的作用，然后只保留有效信息。

#### 4.10 本章小结

这一章讲的不是“怎么伪装”，而是“怎么理解请求是怎么被描述的”。

当你能分清请求头、参数、编码以后，很多看似诡异的问题其实就变得可解释了。你会开始像工程师一样排查，而不是像许愿一样试代码。

#### 4.11 课后练习

1. 找一个带搜索功能的网页，观察搜索词是放在 URL 里还是请求体里。
2. 打开 Network，看看请求头和响应头里分别有哪些字段。
3. 试着故意改一个参数，看返回结果会不会变化。
4. 对比两种编码下同一段文本的显示效果，理解乱码是怎么来的。

### 第 5 章：HTML 解析入门

#### 5.1 背景介绍

拿到网页内容之后，下一步通常不是“看一眼就完了”，而是要从一大堆标签、属性和文本里把有用字段提出来。

这件事就像从一间堆满杂物的仓库里找出你要的几件货。网页源码看起来很乱，但只要知道结构，很多信息其实都藏得很规律。

#### 5.2 本章目标

学完这一章，你应该能：

1. 理解为什么要解析 HTML。
2. 会用 BeautifulSoup 找元素。
3. 会用 CSS Selector 定位节点。
4. 会提取文本和属性。
5. 知道什么时候应该用 HTML 解析，什么时候不该硬解析。

#### 5.3 HTML 为什么需要解析

因为 HTML 不是给人直接阅读数据的，它更像给浏览器看的结构说明书。

比如你看到的一个商品标题，页面源码里可能藏在这样的结构里：

```html
<div class="item" data-id="1001">
  <h2>商品 A</h2>
  <span class="price">99.00</span>
</div>
```

人一眼能看出这是一个商品，但程序需要明确知道：

- 商品 ID 是什么。
- 标题在哪里。
- 价格在哪里。

这时候就需要解析器来帮你精确定位。

#### 5.4 最基础的解析思路

通常你会先做三件事：

1. 找标签。
2. 找属性。
3. 找文本。

比如：

- 标签：`div`、`h2`、`span`
- 属性：`class`、`data-id`
- 文本：`商品 A`、`99.00`

#### 5.5 一个最小示例

```python
from bs4 import BeautifulSoup

html = """
<html>
  <body>
    <div class="item" data-id="1001">
      <h2>商品 A</h2>
      <span class="price">99.00</span>
    </div>
  </body>
</html>
"""

soup = BeautifulSoup(html, "html.parser")
item = soup.select_one(".item")

print(item["data-id"])
print(item.select_one("h2").get_text(strip=True))
print(item.select_one(".price").get_text(strip=True))
```

这段代码最重要的地方，不是库名，而是思路：

- 先选中容器。
- 再在容器里找目标字段。
- 最后提取属性或文本。

这种分层写法，比直接一口气乱找节点更稳。

#### 5.6 CSS Selector 是什么

CSS Selector 本来是给浏览器选中样式用的，但在爬虫里常被借来做定位。

比如：

- `.item` 表示 class 为 item 的元素。
- `h2` 表示所有 h2 标签。
- `.price` 表示 class 为 price 的元素。

它的优点是简洁、直观，很适合新手先上手。

#### 5.7 XPath 是什么

XPath 更像是沿着树去找节点的路径。

你可以把它理解成“从根目录走到目标文件的路线图”。它定位能力强，适合复杂结构。

新手阶段不要求你立刻精通 XPath，但至少要知道它和 CSS Selector 都是在“找节点”，只是表达方式不同。

#### 5.8 为什么不要用正则硬抠 HTML

这个问题很值得专门说一下。

HTML 的结构是嵌套的，标签可能层层嵌套，属性顺序也不固定。如果你只靠正则去抓，代码很容易脆弱：

- 页面稍微改个层级就失效。
- 标签多嵌一层就匹配错。
- 文本里出现类似字符就可能误伤。

所以，HTML 解析最好交给专门的解析器，不要拿正则去做它不擅长的事。

#### 5.9 结构化写法更稳

一个常见的工程写法是：

1. 先定位列表容器。
2. 再循环每个条目。
3. 每个条目单独提取字段。
4. 缺字段时给默认值。

这种写法比“到处找”更容易维护。

#### 5.10 本章小结

HTML 解析是爬虫里的基本功。它不花哨，但很关键。

如果说 `requests` 负责把网页拿回来，那解析器就是帮你把网页里的数据“拎出来”。你以后会经常和它打交道，所以这一步一定要学扎实。

#### 5.11 课后练习

1. 随便找一个网页，试着列出你想提取的三个字段。
2. 观察这些字段分别在 HTML 的哪个标签里。
3. 用 `select_one` 或 `find` 试着把它们取出来。

### 第 6 章：JSON 接口采集

#### 6.1 背景介绍

如果说 HTML 是给人看的页面骨架，那 JSON 更像给程序看的数据包。

在真实项目里，很多采集任务并不需要处理复杂网页，只要找到接口，就能直接拿到结构化数据。这种方式通常比解析页面更稳定，因为字段相对清楚，数据层次也更规整。

#### 6.2 本章目标

学完这一章，你应该能：

1. 明白为什么很多项目优先找接口。
2. 会用 `requests` 请求 JSON 接口。
3. 会把返回结果当作字典来处理。
4. 学会判断接口里字段是否稳定。
5. 初步理解分页接口的基本思路。

#### 6.3 为什么接口更适合程序

接口和页面最大的区别是：接口通常返回的是结构化数据，而不是排版后的页面。

页面像报纸，排版漂亮，但信息不一定好拆。
接口像仓库清单，字段清楚，程序更容易直接处理。

这就是为什么很多企业爬虫项目会优先找接口，而不是先盯着页面源码硬解析。

#### 6.4 一个最简单的 JSON 请求

```python
import requests

url = "https://example.com/api/products"
params = {"page": 1, "size": 20}

response = requests.get(url, params=params, timeout=10)
response.raise_for_status()

payload = response.json()

for item in payload["items"]:
    print(item["id"], item["name"], item["price"])
```

这里最值得注意的是 `response.json()`。

它的作用是把返回文本直接转成 Python 里的字典或列表结构。这样你就不用自己手动解析字符串了，代码会清晰很多。

#### 6.5 分页是什么

很多接口一次不会返回全部数据，而是分成一页一页给你。

常见分页方式有几种：

- 页码分页：`page=1&page=2`
- 数量分页：`size=20`
- 游标分页：`cursor=xxx`
- 偏移分页：`offset=40`

你现在不用一下全记住，只要知道“分页”就是把大数据拆成多次返回，方便加载和展示。

#### 6.6 如何判断字段稳不稳定

一个字段稳不稳定，通常看三点：

1. 每次请求是不是都存在。
2. 值的类型是不是经常变化。
3. 页面改版后这个字段是不是还在。

比如 `id`、`title`、`price` 这类字段通常比“临时展示字段”更稳定。

#### 6.7 JSON 接口里常见的问题

##### 问题一：返回不是 JSON，而是字符串

有些接口返回的内容看着像 JSON，但实际上可能是前后包了一层别的格式。

##### 问题二：字段层级很深

这时不要急着写一大串索引，先打印整个结构，确认路径再取值。

##### 问题三：接口成功但内容为空

可能是参数不对、分页没传、登录态缺失，或者接口本身有过滤条件。

#### 6.8 本章小结

JSON 接口采集是爬虫里非常值得优先掌握的技能，因为它通常比解析网页更直接、更稳定。

你可以把它理解成：如果能直接找到“后厨窗口”，就先别在大厅里拆菜单。

#### 6.9 课后练习

1. 找一个公开接口，观察它返回的是对象还是数组。
2. 试着把返回结果打印成更容易读的结构。
3. 观察分页参数改动后返回数据会不会变化。
