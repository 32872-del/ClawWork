# 企业级爬虫开发教程正文

## 第三篇：把脚本变成一个可用的小系统

### 第 7 章：分页、详情页和任务拆分

#### 7.1 为什么分页是爬虫的日常

真实世界里，数据很少会一次性全摆在你面前。大多数站点都会把内容切成一页一页，原因很简单：

- 页面更快打开。
- 服务器压力更小。
- 用户看起来更舒服。
- 程序也更容易分批处理。

所以，分页不是“额外功能”，而是爬虫里最常见的结构之一。你以后看到列表页、搜索页、商品页、文章页，十有八九都会碰到分页。

分页的本质不是“翻页按钮”，而是“告诉服务器我要第几批数据”。这个批次可能用页码表示，也可能用游标、偏移量、时间戳，甚至用一个滚动加载接口不断拉取。

#### 7.2 分页的几种常见形态

**第一种，页码分页。**

最直观，也最适合新手理解。比如：

```text
/list?page=1
/list?page=2
/list?page=3
```

这种方式很好理解，就像翻书，一页一页往后翻。它的优点是简单，缺点是当数据量很大时，后面的页可能变慢。

**第二种，偏移分页。**

比如：

```text
/list?offset=0&limit=20
/list?offset=20&limit=20
/list?offset=40&limit=20
```

它的意思是“从第几个位置开始取，取多少条”。这在数据库和接口里都很常见。

**第三种，游标分页。**

比如：

```text
/list?cursor=abc123
/list?cursor=def456
```

这种分页方式更像“上一批数据的接力棒”。上一页会返回一个游标，下一页带着这个游标继续取。它比页码更适合动态更新的数据。

**第四种，滚动加载。**

这类页面不会老老实实给你翻页按钮，而是随着你往下滚动不断请求新数据。表面上像“无限滚动”，本质上还是分页，只不过触发方式换成了滚动。

#### 7.3 列表页和详情页为什么要拆开

很多项目会拆成两个层次：

1. 列表页负责发现链接。
2. 详情页负责提取完整信息。

这是非常常见的工程结构。因为列表页通常只提供少量摘要信息，而详情页才有完整字段。比如：

- 列表页给标题、缩略图、链接。
- 详情页给正文、价格、规格、评论、发布时间。

拆开的好处是结构清楚。列表页负责“找路”，详情页负责“取货”。这样后续维护时也更容易定位问题。

#### 7.4 一个最基础的分页采集例子

下面的示例只演示思路。你可以把它理解成一个“先抓列表，再抓详情”的小流程。

```python
import requests
from bs4 import BeautifulSoup


def fetch_list_page(page: int):
    url = "https://example.com/products"
    params = {"page": page}
    resp = requests.get(url, params=params, timeout=10)
    resp.raise_for_status()
    return resp.text


def parse_list_page(html: str):
    soup = BeautifulSoup(html, "html.parser")
    items = []
    for card in soup.select(".product-card"):
        link = card.select_one("a")
        if not link:
            continue
        items.append({
            "title": link.get_text(strip=True),
            "url": link.get("href"),
        })
    return items


def main():
    for page in range(1, 4):
        html = fetch_list_page(page)
        items = parse_list_page(html)
        print(f"page={page}, items={len(items)}")
        for item in items:
            print(item)


if __name__ == "__main__":
    main()
```

这段代码不复杂，但它体现了一个非常重要的思想：**请求和解析要分开写**。

为什么要分开？因为分开以后更容易维护：

- 请求坏了，查请求层。
- 解析坏了，查解析层。
- 列表页结构变了，改 `parse_list_page()`。
- 接口参数变了，改 `fetch_list_page()`。

如果你把所有逻辑都写在一个函数里，后面排查会非常痛苦。

#### 7.5 任务拆分是什么

任务拆分就是把“总工作”拆成更小的任务。

比如一个商品采集项目可以拆成：

- 任务 A：抓第 1 页列表。
- 任务 B：抓第 2 页列表。
- 任务 C：抓某个商品详情。
- 任务 D：抓商品评论。

拆分的好处是：

- 每个任务更简单。
- 可以并发执行。
- 失败了更容易重跑。
- 进度更容易记录。

企业项目里几乎不会只靠一个大函数把所有事情做完。那样代码会像一团线，改一处就容易牵动一大片。

#### 7.6 列表页抓到什么就够了

列表页通常不用抓太多字段。因为它的职责不是完整展示，而是“告诉你下一步去哪抓”。

所以列表页常见字段有：

- 标题
- 链接
- ID
- 缩略图
- 简单描述

这些字段足够你构建详情页任务了。真正细的内容，比如规格、正文、评论，通常放到详情页抓。

#### 7.7 本章小结

分页是爬虫世界里最常见的结构之一。你只要掌握“列表页发现任务，详情页补全信息”这条思路，后面很多项目都会更顺。别把分页当成一个按钮，把它当成任务切片的方式，会更接近真实工程。

### 第 8 章：Cookie、Session 和登录态

#### 8.1 为什么登录态这么重要

很多站点并不是“你来了就给你看全部数据”，而是要先确认你是谁。确认身份的方式，最常见的就是 Cookie 和 Session。

你可以把它们理解成门禁系统：

- 你第一次来，先办卡。
- 服务器给你一个标记。
- 后面你再来，带着这个标记，系统就知道你是谁。

对于爬虫来说，登录态是最常见的前置条件之一。没有登录态，很多内容要么看不到，要么看到的是不完整版本，要么直接被重定向到登录页。

#### 8.2 Cookie 和 Session 的区别先搞清楚

这个地方很容易混。

**Cookie** 通常是存放在客户端的少量信息，浏览器会在后续请求中自动带上它。  
**Session** 更像服务器端保存的会话状态。服务器通过某种标识，把你和它记住的状态对应起来。

你不需要一开始就抠得特别深，只要先记住这句话：

> Cookie 是你带着的证件；Session 是服务器那边记住你的档案。

这个理解就足够支撑大多数初学项目了。

#### 8.3 `requests.Session()` 为什么常用

普通请求每次都是“新来的”。而 `requests.Session()` 可以帮助你把一些状态连续保留下来，比如 Cookie。

这意味着：

- 你先访问登录页。
- 再提交登录表单。
- 然后访问个人中心。

中间的 Cookie 会自动延续，不需要你手工每次都复制粘贴。对新手来说，这能省掉很多麻烦。

#### 8.4 一个最小登录流程示例

下面这个例子只是演示流程，不代表具体站点都长这样。

```python
import requests


session = requests.Session()

# 1. 先访问登录页，拿初始 Cookie 或隐藏字段
login_page = session.get("https://example.com/login", timeout=10)
print("login page status:", login_page.status_code)

# 2. 提交登录表单
payload = {
    "username": "demo",
    "password": "demo123",
}
resp = session.post("https://example.com/login", data=payload, timeout=10)
print("login submit status:", resp.status_code)

# 3. 再访问受保护页面
profile = session.get("https://example.com/profile", timeout=10)
print("profile status:", profile.status_code)
print(profile.text[:300])
```

这段代码的关键不是“能不能直接用”，而是让你理解一个顺序：

1. 先建立会话。
2. 再完成登录。
3. 再访问需要身份的页面。

很多新手的错误是：跳过前两步，直接访问第三步，然后纳闷为什么全是登录页。

#### 8.5 为什么登录页有时候不只是用户名密码

真实网站的登录经常不止两项。

你可能还会碰到：

- 验证码。
- CSRF Token。
- 动态加密参数。
- 隐藏输入框。
- 二次验证。

这说明登录并不是“把用户名密码发上去”这么简单。它本质上是一次完整的身份认证流程。

#### 8.6 CSRF Token 是什么

你可以把它理解成“防伪签章”。

很多站点会在登录页或表单页里放一个临时 token，提交表单时必须带上它。服务器通过它判断这次请求是不是从正常流程发起的。

对新手来说，最重要的不是记名词，而是形成习惯：

- 先抓登录页。
- 看看页面里有没有隐藏字段。
- 看看表单提交时是不是带了额外参数。

#### 8.7 为什么登录态会过期

登录态不是永久的。它通常会因为以下原因失效：

- 时间到了。
- Cookie 过期了。
- 服务端更新了验证逻辑。
- 你连续请求太久，状态被回收。

所以不要把“登录成功”当成终点。登录只是爬虫工作的一个起点，后面你还得考虑续期、失效、重登和异常恢复。

#### 8.8 本章练习怎么做

建议你在一个你有权限访问的测试环境里做练习，观察以下内容：

1. 登录前访问受保护页面会发生什么。
2. 登录后 Cookie 有没有变化。
3. 访问个人页时请求头里是否带了 Cookie。
4. 登录态过期后，页面会不会跳回登录页。

这比只看教程里的概念更有效，因为你会亲眼看到“状态是怎么流转的”。

#### 8.9 本章小结

登录态的本质不是“绕过”，而是“让服务器记住你是谁”。理解 Cookie 和 Session 之后，你就能看懂很多需要身份的页面是怎么工作的。后面不管是分页后的详情、个人中心数据，还是受限接口，都会经常用到这套逻辑。

### 第 9 章：异常处理、重试和限速

#### 9.1 为什么“错一次”很正常

真实网络从来不是完美的。服务器会慢，接口会抖，代理会挂，目标站点会返回临时错误，甚至你自己的网络也会不稳定。

所以，成熟的爬虫不是“永远不出错”，而是“出错时知道怎么处理”。这点非常重要。因为如果你把异常当成罕见情况，程序一旦遇到网络波动就会整体停摆。

#### 9.2 哪些异常最常见

最常见的一类是请求超时。

超时不是“没数据”，而是“等太久”。还有几类也特别常见：

- 连接失败。
- DNS 解析失败。
- 返回 429，说明请求太快。
- 返回 500，说明服务端出错。
- 返回空页面，实际是错误页。

这些情况都需要你有一套统一处理方式，而不是每次都手工盯着。

#### 9.3 重试为什么需要，但不能乱用

重试的作用很简单：临时性失败不要直接放弃，先再试几次。

但重试不是万能药。因为如果失败的原因是参数错、权限错、登录态错、页面结构错，你重试一百次也没用。重试只适合“偶发性问题”，比如网络抖动、临时超时、服务器短暂不稳定。

所以重试要分情况看，不能把“任何错误都重试”当成原则。

#### 9.4 一个简单的重试示例

```python
import time
import requests


def fetch_with_retry(url, max_retries=3, timeout=10):
    for attempt in range(1, max_retries + 1):
        try:
            resp = requests.get(url, timeout=timeout)
            resp.raise_for_status()
            return resp
        except requests.RequestException as exc:
            print(f"attempt {attempt} failed: {exc}")
            if attempt == max_retries:
                raise
            sleep_seconds = 2 ** attempt
            time.sleep(sleep_seconds)


response = fetch_with_retry("https://example.com")
print(response.status_code)
```

这段代码里有几个值得学的点：

- 出错先打印。
- 最多重试几次。
- 每次失败后稍等一会儿再重试。

这个“等一会儿再试”的做法很重要。因为连续猛冲通常只会把问题放大。

#### 9.5 为什么要做退避

退避就是“越失败，下一次等得越久一点”。

它的好处是：

- 不会在目标服务已经很忙时继续猛打。
- 可以减少对方临时限流的压力。
- 让短暂故障有恢复时间。

最常见的是指数退避，也就是每次等待时间翻倍。比如 2 秒、4 秒、8 秒。

#### 9.6 限速为什么不是可有可无

很多新手会觉得“我又不是大流量，为什么要限速”。但限速不只是为了礼貌，它也是为了稳定。

如果你抓得太快，可能出现：

- 429。
- 连接中断。
- 账号风险升高。
- 数据不完整。

所以限速是为了给请求留呼吸空间。它不是拖慢你，而是让整个流程更稳。

#### 9.7 限速可以怎么理解

最简单的限速方式，就是每次请求之间睡一小会儿。

```python
import time
import requests

for page in range(1, 6):
    resp = requests.get("https://example.com/list", params={"page": page}, timeout=10)
    print(page, resp.status_code)
    time.sleep(1)
```

这看起来很朴素，但在很多小项目里已经够用了。真正复杂的限速，后面再加到队列、调度器或中间件里。

#### 9.8 什么时候该停下来，不要继续重试

出现下面这些情况时，通常不应该盲目重试：

- 参数明显错了。
- 返回的是登录页。
- 返回的是权限拒绝页。
- 页面结构已经变了。
- 接口地址已经失效。

因为这些不是“临时故障”，而是“逻辑错误”。重试只会浪费时间。

#### 9.9 本章小结

重试和限速是让爬虫变稳的两个基础动作。重试解决偶发错误，限速减少系统压力。两者配合起来，才能让一个脚本慢慢长成一个可以长期运行的小系统。

### 第 10 章：日志、配置和项目结构

#### 10.1 为什么项目一大就不能乱写

单文件脚本适合试验，真正的项目不能这样写。因为一旦代码开始变长，你就会遇到这些问题：

- 哪个函数负责请求。
- 哪个函数负责解析。
- 哪个地方在存储。
- 哪个地方在重试。
- 哪个地方在打印日志。

如果没有结构，后面维护就会很痛苦。你每次改代码都像在拆一团线。

#### 10.2 为什么日志特别重要

日志是爬虫的黑匣子。出了问题之后，你大概率不会去猜，而是要看它最后干了什么。

日志能帮你回答这些问题：

- 请求发到了哪里。
- 状态码是多少。
- 是哪一步失败了。
- 失败了几次。
- 最后卡在哪里。

没有日志，出错后你只能盲猜。有日志，你至少知道问题发生在哪一层。

#### 10.3 一个简单的日志例子

```python
import logging

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s %(levelname)s %(message)s"
)

logging.info("crawler started")
logging.warning("retrying request")
logging.error("request failed")
```

新手可以先不用把日志搞得很复杂，但至少要做到：重要事件要记录，失败信息要记录，关键 ID 要记录。

#### 10.4 配置为什么要单独放

很多项目一开始会把 URL、账号、密码、超时时间、并发数直接写在代码里。短期看方便，长期看很糟。

因为一旦这些值变了，你就得改代码。更麻烦的是，不同环境的配置可能完全不一样：

- 本地环境。
- 测试环境。
- 预发环境。
- 生产环境。

所以配置最好单独管理。这样代码和环境就可以分开，项目也更容易迁移。

#### 10.5 一个更像项目的目录结构

```text
my_crawler/
  pyproject.toml
  README.md
  .env.example
  my_crawler/
    __init__.py
    config.py
    http.py
    parser.py
    storage.py
    tasks.py
    main.py
  tests/
    test_parser.py
```

这个结构的好处是职责分开：

- `http.py` 管请求。
- `parser.py` 管解析。
- `storage.py` 管存储。
- `tasks.py` 管任务。
- `main.py` 管入口。

这样每一层都清楚，后面维护起来就不会一团乱。

#### 10.6 本章小结

当一个脚本开始有日志、有配置、有清晰目录时，它就已经从“试验代码”往“可维护项目”靠了一大步。这个变化看似不大，但在真实开发里很关键，因为它直接决定后续能不能多人协作、能不能长期维护。

### 第 11 章：从 CSV 到数据库

#### 11.1 为什么不能只把结果 `print()` 出来

`print()` 适合调试，不适合长期保存。因为输出到屏幕上的东西，程序一关就没了。

所以，采集到的数据一定要有落脚点。最基础的是文件，比如 CSV 或 JSONL；更进一步可以入库到 SQLite、MySQL、PostgreSQL、MongoDB。选哪种，取决于你的数据规模和使用方式。

#### 11.2 CSV 适合什么

CSV 很适合表格型数据，比如：

- 标题
- 价格
- 时间
- 链接
- ID

它的优点是简单，能直接打开看。缺点是表达能力有限，不适合层级很深的数据。

#### 11.3 JSONL 为什么很好用

JSONL 的意思是“每一行都是一个 JSON 对象”。

它非常适合爬虫中间结果，因为：

- 一行一条，方便追加。
- 结构比 CSV 灵活。
- 出错后容易恢复。
- 后续可以再清洗成表格。

比如：

```json
{"id": 1, "title": "A", "price": 99}
{"id": 2, "title": "B", "price": 88}
```

这类格式很适合做中间存储。

#### 11.4 一个保存 CSV 的小例子

```python
import csv

rows = [
    {"id": 1, "title": "商品A", "price": 99},
    {"id": 2, "title": "商品B", "price": 88},
]

with open("products.csv", "w", newline="", encoding="utf-8-sig") as f:
    writer = csv.DictWriter(f, fieldnames=["id", "title", "price"])
    writer.writeheader()
    writer.writerows(rows)
```

这里 `utf-8-sig` 的作用是兼容一些表格工具，避免中文打开后乱码。这种小细节在工程里很常见。

#### 11.5 数据库为什么比文件更适合长期使用

文件适合保存结果，数据库更适合查询、筛选、去重和增量更新。

比如：

- 你想查某个商品是否抓过。
- 你想按时间筛选最近 7 天的数据。
- 你想按 ID 更新一条记录。

这些操作在数据库里更自然。

#### 11.6 为什么很多项目先用 SQLite

SQLite 很轻，不需要额外部署数据库服务，适合本地练习和小项目验证。

等项目稳定后，再迁移到 MySQL 或 PostgreSQL 会更顺。这样做的好处是，你可以先把采集逻辑和数据结构跑通，不必一开始就被数据库部署拖住。

#### 11.7 本章小结

文件适合落地，数据库适合管理。爬虫项目里这两者经常一起用：先写 JSONL 做中间层，再清洗后进数据库。这个思路非常实用，也很符合真实项目节奏。

### 第 12 章：数据清洗、标准化和去重

#### 12.1 为什么原始数据不能直接用

原始数据通常是“能看”，但不一定“能用”。

比如价格可能长这样：

- `￥99`
- `99.00元`
- `99`
- `99.0`

时间也可能长这样：

- `2026-06-01`
- `2026/06/01 10:00`
- `June 1, 2026`

如果你不先统一格式，后面做查询、统计、比对都会很麻烦。清洗，就是把这些不统一的东西变成统一的。

#### 12.2 标准化的意义

标准化不是“看起来整齐”，而是“后面更好处理”。

比如：

- 价格统一成数字。
- 时间统一成标准时间。
- 地区统一成规范名称。
- 空值统一成 `None` 或空字符串。

只要统一了，后面筛选、排序、统计、去重就都方便了。

#### 12.3 去重为什么不能只看表面

去重不是“标题一样就算重复”这么简单。因为有些标题一样，但实际上是不同时间、不同来源、不同版本。

更稳妥的做法是根据业务来定唯一键，比如：

- 商品 ID + 来源站点
- 文章 URL
- 评论 ID
- 文件下载地址

去重规则定错了，后面数据不是重复太多，就是误删太多。

#### 12.4 一个简单的清洗示例

```python
def normalize_price(text):
    if text is None:
        return None
    text = text.replace("￥", "").replace("元", "").strip()
    try:
        return float(text)
    except ValueError:
        return None


print(normalize_price("￥99.00"))
print(normalize_price("99元"))
print(normalize_price("abc"))
```

这个例子很小，但它体现了清洗的一条基本原则：不要默认输入永远正确，要允许坏数据出现。

#### 12.5 本章小结

清洗和标准化的作用，是把“原始抓取结果”变成“可以被系统使用的数据”。如果不做这一步，你抓到的往往只是一堆看着像数据的文本。

### 第 13 章：增量采集和断点续爬

#### 13.1 为什么“每次从头抓”很浪费

很多新手写完脚本后，每次都从第一页开始抓，抓完全部数据再结束。练习阶段可以，真实项目里不行。

因为这会导致：

- 重复请求很多。
- 重复写入很多。
- 时间长。
- 成本高。

所以真正实用的系统，通常都会做增量采集和断点续爬。

#### 13.2 增量采集是什么

增量采集就是只抓“新增的部分”。

比如：

- 昨天已经抓过 1 到 100 页。
- 今天只抓 101 到 110 页。

或者：

- 上次已经抓到 ID 5000。
- 这次只抓 ID 大于 5000 的内容。

这就是增量的核心：尽量不重复做已经做过的工作。

#### 13.3 断点续爬是什么

断点续爬就是程序中途停了，下一次接着上次的进度继续，而不是从头来过。

它通常会保存一些状态，比如：

- 当前页码。
- 当前游标。
- 已完成任务列表。
- 最后成功写入的 ID。

有了这些状态，程序就能恢复。

#### 13.4 一个保存进度的小例子

```python
import json
from pathlib import Path

STATE_FILE = Path("state.json")


def save_state(page):
    STATE_FILE.write_text(json.dumps({"page": page}, ensure_ascii=False), encoding="utf-8")


def load_state():
    if not STATE_FILE.exists():
        return {"page": 1}
    return json.loads(STATE_FILE.read_text(encoding="utf-8"))


state = load_state()
print("resume from page:", state["page"])
save_state(state["page"] + 1)
```

这个例子很朴素，但它说明了一个很关键的思路：**把进度单独保存出来**。一旦程序中断，恢复时就不必重新从头跑。

#### 13.5 断点续爬为什么一定要和去重一起做

单独有断点续爬还不够。因为即使你记住了进度，数据也可能重复抓。比如：

- 网络断在写入前。
- 上一次其实已经抓到数据，但状态没来得及保存。
- 页面内容有重复项。

所以断点续爬最好和去重一起做。一个负责“从哪里继续”，一个负责“这条是否已经处理过”。

#### 13.6 本章小结

增量采集和断点续爬，是从“脚本思维”走向“系统思维”的关键一步。只有当系统知道自己做过什么、做到哪一步了，爬虫才真正具备长期运行的能力。
