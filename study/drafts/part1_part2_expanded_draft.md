# 企业级爬虫开发教程正文

## 第一篇：先建立正确直觉

### 第 1 章：爬虫开发的真实工作流

#### 1.1 先把话说透

很多人第一次学爬虫，脑子里想的是“我会发一个请求，就会爬虫了”。这句话不能说错，但它只说到了最外层。真实开发里，爬虫不是一次性的动作，而是一条长期运行的数据生产线。它要做的事情不是“拿到网页”，而是“持续、稳定、低成本地把目标数据拿回来，并且尽量不出脏数据”。

这两个目标看着很像，其实差得很远。

“拿到网页”解决的是能不能通。
“长期稳定拿数据”解决的是能不能用。

一个脚本在本地跑通，只代表你把门推开了；一个系统上线一个月还在稳定工作，才说明你真的把门后的路走通了。企业里大部分时间花在后者。真正费工夫的地方，往往不是第一版代码，而是页面变了、接口抖了、登录过期了、数据重复了、并发过高了之后，系统还能不能自己扛住。

#### 1.2 为什么这个认知这么重要

如果你把爬虫理解成一个“函数”，你会自然地往下问：参数是什么、返回值是什么、怎么调用。

但如果你把它理解成“一条流水线”，你会开始问更接近工程的问题：

- 数据从哪里进来。
- 数据什么时候进来。
- 进来的数据是什么形态。
- 这批数据要不要清洗。
- 什么时候写入数据库。
- 出错后能不能重试。
- 重试几次后要不要人工处理。
- 怎样知道今天有没有漏抓。

后面所有高级话题，比如分页、登录、动态页面、风控、指纹、分布式、监控，本质上都是在给这条流水线补能力。你越早建立这个认知，后面学得越顺。

#### 1.3 一个爬虫项目到底由什么组成

可以把一个爬虫想成一条从“原始信息”到“可交付数据”的工厂线。它通常会经过下面几个环节。

**第一步，找到数据入口。**

入口可以是列表页、详情页、搜索页、接口、文件下载地址、甚至 WebSocket 的推送消息。入口决定了你从哪里拿货。入口找错了，后面全白搭。

**第二步，发出请求。**

请求就是你向服务器说：“我要这个地址的内容。”看起来简单，但这里面包含了很多细节，比如请求方法、请求头、参数、Cookie、超时设置、编码、跳转处理。

**第三步，接收响应。**

服务器会回给你状态码、响应头和响应体。状态码告诉你这次有没有成功，响应头告诉你返回的是什么类型，响应体才是真正的数据。

**第四步，解析内容。**

如果是 HTML，你要从标签里找字段；如果是 JSON，你要从结构化对象里取值；如果是文件，你要按文件格式处理；如果是页面渲染后的 DOM，你可能还需要浏览器自动化。

**第五步，清洗和标准化。**

原始数据通常不适合直接入库。价格可能带货币符号，时间可能有多个格式，地区可能写法不统一，缺失值可能夹在各种字段里。清洗就是把这些“杂质”去掉。

**第六步，去重和校验。**

如果同一个商品、同一篇文章、同一条记录被采了两次，数据就会脏。系统必须知道哪些是重复任务，哪些是重复结果，哪些是错误内容。

**第七步，存储。**

数据可以先落地为 JSONL、CSV、SQLite、MySQL、PostgreSQL、MongoDB，也可以进对象存储。不同场景选不同存法，不是越重越好。

**第八步，调度。**

调度决定任务先后顺序、重试策略、并发数量、失败回收。它像车间主任，负责让整条线不停下来。

**第九步，监控和告警。**

系统是否正常，不是靠“程序没崩”判断，而是靠成功率、失败率、耗时、延迟、异常值、数据缺口等指标判断。

#### 1.4 用一个更接地气的比喻

你可以把爬虫想成一个小型物流公司。

- 数据入口像仓库地址。
- 请求像派快递员去提货。
- 响应像快递员把包裹带回来。
- 解析像拆箱分拣。
- 清洗像质检。
- 存储像入库上架。
- 调度像派单系统。
- 监控像值班大厅的监控屏。

这个比喻的好处是，它能帮助你理解：爬虫的难点并不只在“拿”。真正难的是“拿回来以后怎么处理、怎么保持稳定、怎么处理异常、怎么规模化”。

#### 1.5 为什么“能跑一次”和“能稳定跑”完全不是一回事

新手最容易掉进一个坑：把“本地跑通一次”当成“项目完成”。

这在练习阶段没问题，但在真实项目里，这只是第一小步。因为现实世界的变化很多：

- 页面结构会改。
- 参数会变。
- 登录态会过期。
- 接口会限流。
- 网络会抖。
- 数据源会下线。
- 返回格式会从 HTML 改成 JSON，或者反过来。

所以企业里真正有价值的，不是“能写出一个请求”，而是“能让这个请求长期保持正确”。这就像修路。修通一条路不难，难的是这条路一年四季都能走。

#### 1.6 真实开发通常怎么推进

一个成熟项目，往往不是上来就写一大堆代码，而是按下面的顺序推进。

**第一阶段：确认业务目标。**

先搞清楚你到底要采什么。是商品标题、价格、评论、作者、发布时间，还是文件下载地址。字段不同，采集方案可能完全不同。

**第二阶段：确认入口。**

列表页还是接口？详情页还是搜索页？是静态渲染还是动态加载？是否需要登录？是否有分页？这些问题不先搞清楚，后面很容易绕远路。

**第三阶段：做最小原型。**

先只抓一页，先不管并发，不管去重，不管数据库，不管定时任务。只验证一件事：能不能稳定拿到正确的数据。

**第四阶段：补工程能力。**

当你确认入口正确了，再补重试、日志、超时、去重、断点续爬、异常报警。

**第五阶段：考虑扩展。**

这时候才去想并发、异步、队列、分布式。很多新手一开始就想上这些，最后往往把问题弄复杂了。

**第六阶段：上线后持续维护。**

页面一变，接口一改，脚本就要修。一个真正上线的爬虫项目，维护时间往往远多于初次开发时间。

#### 1.7 新手为什么容易学乱

新手学爬虫最容易乱的地方，不在代码，而在顺序。

常见的错误顺序是：

1. 先听说高级逆向。
2. 再听说浏览器指纹。
3. 再听说 AST。
4. 再听说验证码和风控。
5. 最后回头补 `requests` 和 HTML 解析。

这样学，容易把自己学成“会听名词，但不会做项目”。

更合理的顺序应该是：

1. 先会发请求。
2. 再会读响应。
3. 再会找数据。
4. 再会解析页面和接口。
5. 再会处理登录、分页、错误和存储。
6. 再去接触动态页面、自动化和逆向。

这不是保守，而是省力。因为后面的高级问题，其实都建立在前面的基本功上。

#### 1.8 什么时候你已经开始像“工程师”而不是“试代码的人”

一个很实用的判断标准是：你是否开始主动思考失败路径。

比如你会不会问：

- 这个接口超时怎么办。
- 这个字段缺失怎么办。
- 这一页空了是不是数据真没了，还是解析错了。
- 重试会不会让服务压力更大。
- 这批任务怎么知道哪些抓过了。
- 明天页面改版，我该从哪里发现变化。

当你开始问这些问题，你就已经开始在做工程，而不是单纯写脚本了。

#### 1.9 这一章最该记住的核心

如果只能记一句话，那就是：

> 爬虫不是“把网页拿下来”，而是“把数据流水线搭起来”。

这个认知会贯穿后面所有章节。你以后学任何技术，都不要只问“这个工具会不会用”，而要问“它在流水线里负责什么，替代了哪一步，解决了什么问题”。

#### 1.10 课后练习

1. 随便找一个网站，把它的数据流程写成“入口-请求-响应-解析-清洗-存储-监控”的链条。
2. 想一想，如果页面改版一次，你的脚本最容易坏在哪一步。
3. 想一想，如果数据重复了，应该是在请求层去重，还是在存储层去重，为什么。

### 第 2 章：网页、浏览器和服务器到底在做什么

#### 2.1 先解决一个最常见的困惑

很多人学爬虫卡住，不是因为不会写 Python，而是因为对网页的形成过程没有直觉。

最典型的现象就是：

- 你在浏览器里看到完整内容。
- 你用代码请求同一个网址，却拿到一堆空壳 HTML。
- 你复制了请求头，结果还是 403。
- 你明明看到了数据，代码里就是提不出来。

这通常说明：你以为“网页就是网页”，但实际上网页可能是由多个部分拼出来的。

#### 2.2 一个页面是怎么来的

当你输入一个网址后，浏览器并不是一下子就把“网页”拿回来。它会经历一串动作。

1. 浏览器先根据 URL 找到目标地址。
2. 通过 DNS 找服务器。
3. 建立连接。
4. 发出 HTTP 请求。
5. 服务器返回一个初始 HTML。
6. 浏览器拿到 HTML 后开始解析标签。
7. 浏览器继续请求 CSS、JS、图片、字体等资源。
8. JavaScript 运行起来，可能再去请求接口。
9. 接口返回 JSON，脚本再把数据塞进页面。
10. 最终你看到的是“渲染之后”的内容。

这意味着，浏览器里看到的页面，常常不是一个静态文本，而是一个“动态拼装结果”。

#### 2.3 HTML、DOM、JSON 的区别

这三个词是后面特别重要的基础。

**HTML** 是网页的原始结构。它像房子的骨架，定义了哪里是标题、哪里是段落、哪里是列表。

**DOM** 是浏览器把 HTML 读进去之后形成的树状结构。它不是文本，而是浏览器内部对网页的组织方式。JavaScript 会直接修改 DOM，所以页面最终显示出来的内容可能和源代码并不一样。

**JSON** 是一种结构化数据格式。它像一份规整的数据清单，适合程序读取，不适合直接做页面展示。很多接口返回的就是 JSON。

这三者之间的关系很像这样：

- HTML 是“原料”。
- DOM 是“浏览器加工后的结构”。
- JSON 是“数据包”。

#### 2.4 为什么“浏览器能看到”不等于“代码能拿到”

这个问题必须讲透。

有些内容并不直接写在初始 HTML 里，而是由 JavaScript 在页面加载后再请求接口补出来。浏览器会执行脚本，所以你看到的是最终结果；普通请求只是拿静态内容，它不会自动执行 JS，所以你可能只能拿到一个壳。

这就是为什么很多时候你明明访问的是同一个 URL，看到的却不是同一个结果。

造成这种差异的常见原因有：

- 内容是 JS 渲染后插入的。
- 接口请求需要额外参数。
- 登录态、Cookie、token 没带上。
- 服务器根据请求来源决定返回什么。
- 页面依赖浏览器环境里的执行结果。

所以遇到空白页时，第一反应不要是“代码坏了”，而应该先判断“数据是不是根本不在这个层面上”。

#### 2.5 先看源码还是先看 Network

这一步很关键。

**如果页面是静态的**，先看网页源码，因为数据往往就写在 HTML 里。  
**如果页面是动态的**，先看 Network，因为真正的数据多半是后续接口拿到的。  
**如果页面既有 HTML，又有动态加载**，那就两边都看，但优先看数据实际从哪里来。

一个简单的判断方式是：

- 打开页面就能看到内容，可能偏静态。
- 打开后先空着，过一会儿才出现内容，可能偏动态。
- 页面展示和源码明显对不上，优先怀疑动态加载或接口补数据。

#### 2.6 HTTP 到底是什么

HTTP 可以理解成浏览器和服务器之间的交流规则。

浏览器说：“我想要这个地址的内容。”
服务器说：“可以，这是我给你的响应。”

这段交流里有几个核心部分：

- 请求方法：我想做什么。
- 请求头：我是谁、我想要什么、我从哪里来。
- 请求参数：我具体要哪一份数据。
- 状态码：这次访问成功了吗。
- 响应头：返回的是什么格式、是否跳转、是否缓存。
- 响应体：真正的数据内容。

你可以把 HTTP 想成一封有固定格式的信。信封上写的是请求头，信纸内容是请求体，回信则带着响应头和响应体。

#### 2.7 请求方法不要死记

最常见的是四种：

- `GET`：取数据。
- `POST`：提交数据。
- `PUT`：更新数据。
- `DELETE`：删除数据。

但在真实项目里，不要只靠方法名字判断用途。因为很多接口设计并不完全“教科书化”，有些查询也会用 POST，有些更新也会带上复杂参数。你要看的是接口实际行为，不是名字。

对爬虫来说，最常见的还是 `GET` 和 `POST`。GET 往往用于查询列表、详情、搜索结果；POST 往往用于提交表单、搜索条件、分页请求、登录请求。不过这不是死规矩，只是常见情况。

#### 2.8 状态码是服务器的态度

状态码是你第一眼该看的东西，因为它非常诚实。

- `200`：请求成功。
- `301/302`：重定向，服务器让你去别的地方。
- `400`：请求本身就有问题，参数可能错了。
- `401`：没认证，或者认证失效。
- `403`：被拒绝访问。
- `404`：地址不存在。
- `429`：请求太频繁。
- `500`：服务器内部报错。

很多新手会把 `403` 理解成“代码错了”，其实不一定。它更多是在说：对方不让你这样访问。至于为什么不让，可能是权限问题、频率问题、请求格式问题、身份问题，甚至只是规则不匹配。

#### 2.9 请求头和响应头分别是什么

**请求头** 是你发给服务器的附加说明。它告诉服务器你是谁、你想要什么格式、你从哪来。常见字段有：

- `User-Agent`
- `Accept`
- `Referer`
- `Cookie`
- `Accept-Language`

**响应头** 是服务器回给你的说明。它告诉你返回内容的类型、是否设置了新 Cookie、是否跳转、是否缓存。常见字段有：

- `Content-Type`
- `Set-Cookie`
- `Location`
- `Cache-Control`

理解这两者的差别很重要。请求头是“我说给你听的”；响应头是“你回给我看的”。

#### 2.10 为什么要看 `Content-Type`

`Content-Type` 这个字段特别实用，因为它会告诉你服务器返回的到底是什么。

- 如果是 `text/html`，说明返回更像网页。
- 如果是 `application/json`，说明返回更像接口数据。
- 如果是文件类型，说明可能是下载内容。

这在排查问题时很有用。比如你以为自己拿的是 JSON，结果响应头告诉你其实返回的是 HTML，这通常意味着你可能被重定向到了登录页、错误页或者挑战页。

#### 2.11 `requests` 什么时候够用

`requests` 的定位很简单：轻量、直接、适合基础请求。

它特别适合以下场景：

- 静态页面。
- 直接返回 JSON 的接口。
- 简单的登录态维持。
- 请求逻辑比较朴素的页面。

它的优势是学习成本低，适合打基础，也适合大多数稳定项目的第一版实现。很多企业级项目，底层抓取部分其实就是 `requests` 或同类库，只是外面包了更多工程能力。

#### 2.12 什么时候要考虑接口，而不是页面

如果你发现：

- 页面内容是后加载的。
- 页面源码很空。
- 真正的数据在 Network 里出现。

那通常就应该优先考虑接口，而不是死磕页面结构。

这背后的原因很朴素：页面是给人看的，接口是给程序和前端交互的。程序更适合直接处理接口，因为接口更规整、更清晰、字段更稳定。只要能直接拿接口数据，就尽量别绕远路。

#### 2.13 什么时候才轮到浏览器自动化

浏览器自动化不是第一选择，它通常是“最后上”的那种方案。

适合它的情况包括：

- 页面必须执行 JavaScript 才会显示内容。
- 页面交互步骤很多，比如滚动、点击、输入、切换。
- 某些内容只能在真实浏览器环境里出现。

但浏览器自动化有明显代价：

- 速度慢。
- 占资源。
- 更容易受页面变化影响。
- 排查问题更麻烦。

所以工程上常见的顺序是：先看能不能直接请求，再看能不能找接口，最后才考虑浏览器自动化。

#### 2.14 一个最小例子：从请求到响应

```python
import requests

url = "https://example.com"
response = requests.get(url, timeout=10)

print("status:", response.status_code)
print("content-type:", response.headers.get("Content-Type"))
print(response.text[:300])
```

这段代码表面上很短，但它实际上已经包含了爬虫最基本的四个动作：

1. 发请求。
2. 看状态码。
3. 看响应头。
4. 看响应体。

以后你碰到任何页面，都可以先用这个思路做最初判断：它到底是不是你真正要的数据入口。

#### 2.15 WebSocket、XHR、Fetch 这几个词怎么看

这些词会经常出现在开发者工具的 Network 面板里。

- `XHR`：传统的异步请求方式，很多老项目和通用接口里还会看到。
- `Fetch`：现代浏览器里更常见的请求方式。
- `WebSocket`：长连接，适合实时数据推送。

你现在不用把它们背成百科。只要记住一件事：它们都是“页面拿数据的通道”。以后如果你在 HTML 里找不到数据，就该去 Network 看是不是这些请求拿回来的。

#### 2.16 本章最核心的思路

你只要记住这一句就够了：

> 浏览器看到的内容，不一定就是源代码里最初写的内容；很多页面是“加载后再拼出来”的。

这句话会在后面反复救你。你一旦有了这个意识，就不会再一看到空白页就怀疑自己代码写错，而是会先去追数据到底从哪里来。

#### 2.17 课后练习

1. 找一个普通网页，比较“页面源码”和“浏览器里最终看到的内容”是否一致。
2. 打开 Network，找一个请求，看它返回的是 HTML 还是 JSON。
3. 试着用自己的话解释一次：HTML、DOM、JSON 各自负责什么。
4. 看一个页面时，先判断它更像静态页、接口页还是动态渲染页。

## 第二篇：从 `requests` 开始写第一个可用爬虫

### 第 3 章：环境搭建与第一个请求

#### 3.1 为什么环境这件事不能省

很多人第一次写爬虫时，特别想赶快看到结果，觉得环境只是开胃菜。但在真实项目里，环境往往决定了后续是不是能长期稳定推进。

如果环境不稳定，就会出现这些非常烦人的问题：

- 今天能跑，明天不能跑。
- 你电脑能跑，同事电脑不能跑。
- 线上环境和本地环境行为不一致。
- 升级一个库，另一个项目就坏了。

所以企业开发特别强调“可复现”。可复现的意思是：别人照着你的步骤，尽量能得到同样的结果。环境如果不统一，后面排查问题会非常痛苦。

#### 3.2 虚拟环境为什么值得用

你可以把虚拟环境理解成“项目专属小房间”。

每个项目都住在自己的房间里，各自装自己的依赖，不互相打架。这样做的好处是：

- 项目之间不会互相污染。
- 依赖版本更容易固定。
- 迁移、部署、交接都更简单。

对于爬虫项目来说，这一点尤其重要。因为爬虫常常会依赖多个库：请求库、解析库、异步库、数据库库、自动化库……如果这些库全部混在全局环境里，迟早会乱。

#### 3.3 第一步不要急着写代码

正确的顺序应该是：

1. 建项目目录。
2. 建虚拟环境。
3. 安装依赖。
4. 写一个最小脚本。
5. 确认能发出请求。
6. 再谈解析、存储和扩展。

这听起来慢一点，但后面会省很多时间。很多新手的问题，不是“不会写”，而是“边写边修环境，最后不知道到底坏在代码还是环境”。

#### 3.4 第一个请求到底在干什么

看这段代码：

```python
import requests

url = "https://example.com"
response = requests.get(url, timeout=10)

print(response.status_code)
print(response.text[:500])
```

表面上只有三行核心逻辑，但它已经把一个完整请求链路跑起来了。

`requests.get()` 的意思是向目标地址发出一个 GET 请求。  
`timeout=10` 的意思是：这次请求最多等 10 秒。  
`response.status_code` 是服务器给你的第一层反馈。  
`response.text` 则是返回的正文内容。

你可以把这个过程理解为：你给服务端发了一封信，服务端回了你一封回信，而 `response` 就是这封回信的全部内容。

#### 3.5 为什么超时必须写

超时不是可选项，而是基本配置。

如果没有超时，程序可能会在网络卡住、代理异常、服务器不响应时一直等待。对于单个脚本来说，这只是“卡住”；对于队列系统来说，这可能是“整个队列被堵住”；对于定时任务来说，这可能是“下一轮任务都开始不了”。

所以超时就像给每个请求装一个限时器。时间到了还没回来，就判定失败，进入下一步处理，比如重试、跳过或人工介入。

#### 3.6 状态码不是摆设

很多人看见状态码只知道 `200`，其实其他状态码更能帮你定位问题。

- `200` 说明请求成功。
- `301/302` 说明发生了跳转，可能从页面跳到登录页、错误页或别的地址。
- `401` 说明认证失败，通常和登录态有关。
- `403` 说明被拒绝，可能是权限、规则或风控。
- `404` 说明地址不对，或者资源不存在。
- `429` 说明请求太频繁，服务器开始限制你。
- `500` 说明服务端自己出问题了。

在工程里，状态码很像温度计。你不需要靠感觉判断“是不是发烧了”，看它就行。

#### 3.7 响应头里为什么有时候藏着答案

很多初学者只看响应正文，其实响应头也很有价值。

比如：

- `Content-Type` 可以告诉你返回的是 HTML 还是 JSON。
- `Set-Cookie` 能告诉你服务器是不是给你发了新的会话信息。
- `Location` 会告诉你是不是跳转了。

如果你拿到的不是预期内容，先看响应头通常比盲目猜测更快。

#### 3.8 初学者常见的第一批错误

**错误一：没有超时。**  
结果是程序卡死，看起来像“没反应”。

**错误二：只看网页，不看状态码。**  
结果是其实请求已经被拒绝了，你却还在怀疑解析器。

**错误三：拿到文本就以为任务完成。**  
结果是返回的是错误页、登录页或者空壳页。

**错误四：一上来就追求复杂功能。**  
结果是代码还没稳定，思路先乱了。

#### 3.9 本章练习应该怎么做

不要一上来就选复杂目标。最好的练习对象是一个公开测试页或者一个本地简单页面。目标不是抓复杂数据，而是先把“发请求-看状态码-看响应头-看响应正文”这一套流程做顺。

你至少要能回答：

- 请求打到了哪里。
- 服务器回了什么状态。
- 返回内容大概是什么类型。
- 这次请求成功了吗。

#### 3.10 本章小结

这一章其实只讲了一件很小但很核心的事：你已经会发出第一个可靠请求了。

这不是“会爬虫了”的终点，但它是所有后续内容的起点。因为无论你以后面对的是 HTML、JSON、动态页面还是复杂接口，最底层的动作都还是这件事：把请求发出去，把响应拿回来，把状态看明白。

### 第 4 章：请求头、参数和编码

#### 4.1 为什么“同一个 URL，不同结果”很常见

新手最困惑的一件事，就是“我明明请求的是同一个网址，为什么浏览器能看到，代码却不行”。

这个问题的答案通常不是“URL 错了”，而是“你发出去的请求不够像一个正常访问”。这里的“不够像”，不只是 `User-Agent` 的问题，还包括参数、头部、Cookie、编码、来源信息等很多细节。

HTTP 请求不是只有地址，还有一整套配套信息。服务器往往是结合这些信息一起判断的。

#### 4.2 请求头到底在表达什么

请求头可以理解成“我是谁、我要什么、我从哪里来、我能接受什么格式”。

几个最常见的字段：

- `User-Agent`：告诉服务器你大概是什么浏览器或客户端。
- `Accept`：告诉服务器你希望接收什么类型的内容。
- `Referer`：告诉服务器你从哪里点过来的。
- `Cookie`：告诉服务器你是不是已经登录过，或者有没有会话信息。
- `Accept-Language`：告诉服务器你更偏好哪种语言。

这些字段不是装饰，它们都可能影响返回结果。

#### 4.3 参数是怎么传的

很多查询类请求都会带参数，比如：

```python
params = {
    "q": "python crawler",
    "page": 1,
}
```

你可以把参数理解成“你不是只说要这个页面，还要说明你要哪一页、哪个关键词、哪个排序”。没有参数，服务器只能给你默认结果；参数不对，服务器给你的也可能不是你要的那页内容。

`requests` 里用 `params` 传参数的好处是，它会帮你把内容正确地拼到 URL 后面，不用你自己手工处理编码和拼接细节。

#### 4.4 编码为什么总会出问题

编码问题是爬虫新手的经典坑。

文字本身不是问题，问题是“字节该怎么解释成文字”。如果编码规则错了，同样一串数据会显示成乱码。很多时候，代码不是没拿到内容，而是拿到了但解释错了。

当你看到乱码时，应该先检查：

- 响应头有没有明确编码。
- 页面是否声明了字符集。
- 代码是否自动猜错了编码。

这类问题很常见，而且很容易误导人。新手往往会以为“页面坏了”，其实只是“翻译规则错了”。

#### 4.5 一个更完整一点的例子

```python
import requests

headers = {
    "User-Agent": "Mozilla/5.0",
    "Accept": "text/html,application/xhtml+xml,application/xml;q=0.9,*/*;q=0.8",
}

params = {
    "q": "python crawler",
    "page": 1,
}

response = requests.get(
    "https://example.com/search",
    headers=headers,
    params=params,
    timeout=10,
)

response.encoding = response.apparent_encoding
print(response.url)
print(response.status_code)
print(response.headers.get("Content-Type"))
print(response.text[:500])
```

这段代码比最小例子多了几个关键点：

- 加了请求头，让请求更完整。
- 通过 `params` 传了查询条件。
- 主动处理了编码。
- 打印了更多诊断信息。

这些习惯在小项目里看起来不起眼，但在大项目里会非常救命。因为你以后调试时，最想看到的就是“请求到底长什么样、服务器到底回了什么”。

#### 4.6 为什么不要盲目复制浏览器全部请求头

这是一个非常容易踩的坑。

很多人喜欢把浏览器里所有请求头复制过去，觉得越完整越好。实际上不一定。原因是：

1. 有些头是浏览器自动维护的，复制过去并不会带来帮助。
2. 有些头之间要保持内部一致性，乱改反而更怪。
3. 有些站点真正关心的只是少量关键字段。

更稳妥的方法是：先从最必要的信息开始，确认数据是否正常，再逐步补充。这样更容易知道是哪一个字段真正起作用。

#### 4.7 `Content-Type` 和 `Accept` 很容易混

这两个字段要分清。

- `Accept` 是你想接收什么。
- `Content-Type` 是实际传过去或返回来的内容类型。

你可以把它理解成：

- `Accept` 是“我想吃什么”。
- `Content-Type` 是“这道菜实际是什么”。

一个是期望，一个是事实。搞混这两个字段，会让很多判断失真。

#### 4.8 本章最重要的调试习惯

以后你只要碰到请求异常，就先问自己四个问题：

1. 请求发到哪里去了。
2. 状态码是什么。
3. 响应头说了什么。
4. 返回内容是不是你以为的那个内容。

这四个问题能帮你排掉大多数初级故障。很多时候，问题根本不在解析，而是在请求层。

#### 4.9 本章小结

这一章不是在教你“伪装技巧”，而是在教你“怎么理解请求”。

你一旦能分清请求头、参数、编码和响应信息，很多看起来玄乎的问题就会变得可解释。爬虫的排障能力，往往就是从这一步开始建立的。

### 第 5 章：HTML 解析入门

#### 5.1 为什么拿到 HTML 之后还要解析

HTML 不是给程序直接吃的，它更像一份排版后的说明书。人看起来有层次感，程序看起来却很乱。你真正需要的字段，往往只是其中一小部分：标题、价格、链接、发布时间、作者、编号。

所以解析的任务，本质上就是“从一大堆结构里，精确把目标字段挑出来”。

#### 5.2 先理解结构，再动手

很多新手一上来就想“用一个函数把整个页面全抓出来”。但 HTML 解析最关键的能力，其实不是函数，而是结构感。

你要先知道：

- 哪个元素是容器。
- 哪个元素是标题。
- 哪个元素是价格。
- 哪个元素是链接。
- 这些字段之间是什么层级关系。

如果结构看不懂，解析器再强也没用。

#### 5.3 一个非常简单的页面结构

```html
<div class="item" data-id="1001">
  <h2>商品 A</h2>
  <span class="price">99.00</span>
</div>
```

人一眼能看懂这是什么，但程序必须明确知道：

- `data-id` 在哪。
- 标题在哪个标签里。
- 价格在哪个标签里。

这就是解析的起点。

#### 5.4 先找容器，再找字段

一个稳定的解析思路是：

1. 先定位列表容器或单个条目的外层块。
2. 再在这个块里找具体字段。
3. 字段找不到时要能优雅处理。

这种写法的好处是清晰。你以后页面改版时，也更容易知道坏在哪一层。

#### 5.5 一个最小例子

```python
from bs4 import BeautifulSoup

html = """
<html>
  <body>
    <div class="item" data-id="1001">
      <h2>商品 A</h2>
      <span class="price">99.00</span>
    </div>
  </body>
</html>
"""

soup = BeautifulSoup(html, "html.parser")
item = soup.select_one(".item")

print(item["data-id"])
print(item.select_one("h2").get_text(strip=True))
print(item.select_one(".price").get_text(strip=True))
```

你现在不用急着记库名，先理解动作：

- 先把 HTML 变成可操作对象。
- 再找到目标节点。
- 再取属性或文本。

这就是最基本的解析流程。

#### 5.6 CSS Selector 为什么很好用

CSS Selector 的优点是直观。

- `.item` 表示 class 是 item 的元素。
- `h2` 表示所有 h2 标签。
- `.price` 表示 class 是 price 的元素。

新手用它很容易建立结构感，因为它写出来就像“人话”，更容易读懂。

#### 5.7 XPath 是什么

XPath 可以理解成“在树上走路径”。它很适合复杂结构，尤其是在一些层级特别深、位置比较固定的页面里很有用。

你现在不需要把 XPath 全背下来，但至少要知道：它和 CSS Selector 一样，都是定位元素的方法，只是表达方式不同。

#### 5.8 为什么不建议靠正则硬解析 HTML

HTML 的结构不是平铺文本，而是嵌套树。正则不是不能碰它，但容易脆。

问题在于：

- 标签层级一变，规则就可能失效。
- 属性顺序变化，匹配就可能出问题。
- 内容里出现相似字符，规则容易误伤。

所以，解析 HTML 时更推荐用专门的解析器，而不是把正则当万能工具。

#### 5.9 解析结果要考虑缺失值

真实页面里，不是所有字段都永远存在。

有时候会出现：

- 某些条目没有价格。
- 某些条目没有作者。
- 某些条目没有链接。
- 某些字段被前端改名了。

因此解析时不要默认“字段一定在”。更稳妥的做法是：如果找不到字段，就给一个默认值，并记录下来，方便后续排查。

#### 5.10 本章小结

HTML 解析是爬虫最基础的能力之一。它不炫，但非常核心。你以后会反复做同样的事：先看结构，再定位元素，再提取文本和属性。这个能力越扎实，后面做任何页面都会更稳。

### 第 6 章：JSON 接口采集

#### 6.1 为什么接口通常比页面更适合采集

如果说 HTML 是给人看的页面，JSON 就更像给程序看的数据包。很多采集任务，真正值钱的数据并不在页面排版里，而是在接口返回的结构化内容里。

接口采集的优势很明显：

- 字段结构更清楚。
- 不用处理复杂页面布局。
- 通常更稳定。
- 解析更直接。

所以企业项目里，经常会优先找接口，而不是硬啃页面。

#### 6.2 JSON 接口长什么样

```python
import requests

url = "https://example.com/api/products"
params = {"page": 1, "size": 20}

response = requests.get(url, params=params, timeout=10)
response.raise_for_status()

payload = response.json()

for item in payload["items"]:
    print(item["id"], item["name"], item["price"])
```

这段代码看起来和 HTML 请求差不多，但思路完全不同。这里不是去找标签，而是直接把返回内容当成结构化对象处理。

#### 6.3 为什么 `response.json()` 很重要

`response.json()` 的意思是：把返回内容直接转换成 Python 字典或列表。

这一步很重要，因为它让你不用自己切字符串、找标签、拆文本。你能直接像访问字典一样访问字段。

例如：

- `payload["items"]`
- `item["name"]`
- `item["price"]`

这比从 HTML 里一层层找标签要省很多力气。

#### 6.4 分页是接口采集的日常

大多数接口不会一次把所有数据都给你，而是分成多页返回。常见分页方式有：

- 页码分页：`page=1`、`page=2`
- 数量分页：`size=20`
- 游标分页：`cursor=xxx`
- 偏移分页：`offset=40`

分页的核心本质是：把大数据切成一块一块给你，既方便浏览器展示，也方便程序逐页拉取。

#### 6.5 如何判断字段是否稳定

字段稳不稳定，决定了你的采集逻辑会不会经常坏。

判断时可以看三点：

1. 它是不是每次都有。
2. 它是不是老变类型。
3. 页面改版后它是不是还在。

像 `id`、`name`、`title`、`price` 这类字段通常比较稳定；像展示文案、临时标签、推荐字段，往往不那么稳。

#### 6.6 接口采集里常见的坑

**坑一：返回的不是你想象中的 JSON。**  
有些接口会包一层外壳，或者返回的其实是跳转页、错误页、登录页。

**坑二：字段层级很深。**  
这时候不要一口气写很长的索引，先打印结构，确认路径，再提取。

**坑三：分页参数没传对。**  
结果就是你看起来在翻页，其实总拿到同一批数据。

**坑四：接口返回空。**  
这不一定是“没有数据”，也可能是参数、权限、登录态、过滤条件的问题。

#### 6.7 本章小结

JSON 接口采集是爬虫里非常值得优先掌握的一类能力，因为它通常比 HTML 更干净、更直接、更适合程序处理。你可以把它理解成：如果能直接从后厨窗口拿到菜，就不要先在大厅里拆菜单。

到这里，你已经完成了很关键的基础铺垫：

- 知道爬虫不是一个动作，而是一条流水线。
- 知道网页、HTML、DOM、JSON、接口之间的关系。
- 能发出第一个稳定请求。
- 能读懂状态码、响应头和编码问题。
- 能做基础 HTML 解析。
- 能直接处理 JSON 接口。

这意味着你已经有了后面继续扩展的地基。后续章节里，不管是登录、分页、存储、重试，还是动态页面、自动化、逆向分析，本质上都只是把这套基础链条补得更完整。
